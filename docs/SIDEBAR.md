# 左侧栏：调研与设计

> 目标：让左侧栏像用户自己的收藏夹——结构由用户决定，任何时候都知道「我在哪」，并且能一站完成日常整理动作。
>
> 本文调研了 9 个主流产品，给出共性规律、本项目的差距，以及分阶段方案。**P0 已经在本次改动里实现**，P1 需要先做一个架构决定（见 §8）。

---

## 1. 结论（先给答案）

1. **主流产品的共识是「树 + 收藏 + 搜索」三件套**，不是只给一棵树。树回答「结构在哪」，收藏回答「常用在哪」，搜索回答「我记得有但找不到」。
2. **拖拽移动是所有能做结构的产品都有的能力**，并且是主要操作方式，不是一个附加功能。
3. **没人推荐深层嵌套**。Evernote 明确限制两层（笔记本 → 堆叠），思源默认限制 7 层，实践建议 2–3 层。所以我们的目标不是「支持无限深度」，而是「让 2–3 层的操作足够顺手」。
4. **「你在哪」需要三个信号叠加**：展开的路径 + 高亮当前项 + 一行路径文字（面包屑）。只做高亮，用户在深目录里会迷失。
5. **手动排序不是必需品**。主流做法是自动排序（名称/时间）+ 收藏置顶作为补偿；只有 Notion、思源原生支持拖拽排序，Obsidian 需要装插件。
6. 能改结构的操作（新建/重命名/拖拽/删除）会写用户的笔记文件，所以必须先解决两件事：**笔记身份**和**链接改写**。两件都已经落地——id 优先取 front matter，路径变更前先把当前 id 写进去；移动/重命名时全库改写 `[[...]]` 和 Markdown 相对链接（见 §8）。

## 3. 共性规律

### 3.1 结构由用户决定，应用只提供操作

所有产品的树都是「用户摆成什么样就是什么样」。没有产品会根据 front matter 自动分组——自动分组只出现在「智能文件夹」这种**显式的、用户自己命名的**视图里（Apple Notes 的 Smart Folder 是最好的例子：它是一个保存下来的检索条件，出现在侧栏里，但和真实文件夹并列、可区分）。

对照本项目：改动前的侧栏是按 `领域/xxx` 标签自动分组的，这是行业里不常见的做法，也是用户觉得「限制太死」的根本原因。

### 3.2 拖拽移动是主要操作，不是附加功能

Obsidian、Notion、Apple Notes、Evernote、Raindrop、VS Code、思源都支持拖拽移动文件/文件夹。VS Code 甚至专门提供了 `explorer.enableDragAndDrop` 开关来关掉它——说明这是默认拳头功能。

同时有两处一致的风险处理：
- **拖拽需要明确的落点提示**（思源用户反馈「定位线不明显」，VS Code 的 compact folders 会导致拖错层级）。
- **移动后要处理引用**：Obsidian 移动文件会更新 `[[wiki link]]`，Notion 移动页面不影响链接。

### 3.3 收藏/置顶是「第二套索引」，不是树的替代品

- Notion：星标不移动原位置，同一个页面可以同时出现在 Favorites 和原位置。
- Bear：置顶分「全局置顶」和「在某个标签内置顶」两种粒度。
- Evernote：Shortcuts 是独立区域，放笔记和笔记本混排。
- Apple Notes：置顶只影响笔记列表排序。

共同点：**收藏是引用，不是移动**。用户对「收藏后原件还在原处」有明确预期。

### 3.4 手动顺序 vs 自动排序：主流选自动 + 收藏补偿

| 做法 | 产品 | 代价 |
| --- | --- | --- |
| 完全手动拖拽排序 | Notion、思源 | 条目一多就难维护，顺序存在哪里也是个问题 |
| 自动排序为主 | Obsidian、VS Code、Apple Notes | 想要固定顺序时只能靠置顶/收藏 |
| 需要插件 | Obsidian（Custom Sort） | 顺序写在 front matter（`sorting-spec:`）或文件夹笔记里 |

如果以后要支持手动顺序，成熟做法是把顺序**存进笔记库本身**（front matter 的 `order` 字段，或文件夹里的 `.navigation.md` 这类 sidecar），而不是只存在应用数据库里——否则换个编辑器/换台机器顺序就丢了。这一点对本项目尤其重要，因为数据主体是用户自己的 Markdown。

### 3.5 「你在哪」= 路径展开 + 当前项高亮 + 面包屑

这是 Obsidian 论坛里争得最细的一个点：**reveal（显示位置）和 expand（展开内容）是两件事**。主流处理是：

- 打开一个深层笔记时，自动展开它的各级父目录（不然根本看不见）。
- 当前项要有稳定的视觉标记，且不能被折叠状态藏起来。
- 面包屑单独给一行路径文字；点面包屑的某一级，应该**定位到那一级**（并展开它），而不是简单地切换选中。

VS Code 还额外做了 **compact folders**（单链目录合并成 `a/b/c` 一行），用来压缩无效层级——这一点在本项目里属于可选优化，先不做。

### 3.6 嵌套深度不是卖点

- Evernote 官方只允许「笔记本 → 堆叠」两层，不提供更深层级。
- 思源默认 7 层上限。
- 实践建议普遍是 2–3 层，更深的层级用标签/搜索解决。

所以侧栏的设计目标应该是「2–3 层内操作顺滑 + 深层可折叠」，而不是追求无限深度。这也会影响我们是否需要「紧凑目录」（§9 不推荐项）。

## 4. 用户心智模型：三种「我知道我在哪」的信号

| 信号 | 回答的问题 | 本项目现状 |
| --- | --- | --- |
| 树的层级位置 | 这篇属于哪个主题 | ✓ 已有（按文件夹） |
| 当前项高亮 | 我正在看哪一篇 | ✓ 已有 |
| 路径文字（面包屑） | 我从哪进来的、上层是什么 | ✗ 缺失 |
| 折叠记忆 | 我上次把哪些收起来了 | ✓ 已有（localStorage） |
| 收藏区 | 我常用但不在当前位置的 | ✗ 缺失 |
| 筛选/搜索 | 我记得有这篇但找不到 | ◐ 顶栏有全库搜索，但侧栏内不能就地筛 |

## 5. 差距清单（本次改动前）

已有：目录树、递归计数、折叠 + 持久化、打开深层笔记自动展开、当前项高亮、按日期倒序。

缺失且**不涉及写文件**的：侧栏内筛选、收藏/置顶、全部折叠/展开、排序切换、面包屑、键盘导航、空文件夹显示。

缺失且**涉及写文件**的：新建笔记/文件夹、重命名、拖拽移动、删除。

## 6. 方案分级

### P0（本次已实现，纯前端）

1. **侧栏筛选框**：按标题（以及文件夹名）就地过滤，匹配时自动展开、文件夹名命中则整棵子树展开。
2. **收藏区**：星标笔记，出现在树的顶部；星标是引用不是移动（符合 §3.3 预期），存在 localStorage。
3. **全部折叠 / 全部展开**：一键收起，配合自动展开当前项使用。
4. **面包屑**：显示当前笔记所在的目录路径，点某一级会展开并滚动定位到那个文件夹。
5. **排序切换**：名称 ↑ / 名称 ↓ / 时间（新→旧）三态循环，同时作用于文件夹和笔记。

验收标准：见 §7。

### P1（需要先做架构决定，见 §8）

- 新建笔记 / 新建文件夹
- 重命名、拖拽移动
- 删除（进回收站而不是直接删）
- 空文件夹显示
- 多选批量移动
- 键盘导航（↑↓ 移动、←→ 折叠展开、回车打开）与 `role="tree"` 语义

### P2（可选）

- 智能文件夹（保存的检索条件，和标签台联动）
- 最近打开
- 文件夹图标/颜色
- 紧凑目录（单链合并）

## 7. P0 交互细节

### 7.1 筛选

- 位置：侧栏标题下方一行，占位文字「筛选笔记…」。
- 匹配：笔记标题包含查询（不区分大小写）；文件夹名命中时显示该文件夹及其全部内容。
- 行为：进入筛选时忽略折叠状态，结果全部展开；清空后恢复原来的折叠状态。
- 空结果：显示「没有匹配的笔记」。
- 筛选时隐藏收藏区和面包屑，避免同一屏出现两套结构。

### 7.2 收藏

- 入口：笔记行右侧的星标按钮，悬停/聚焦时出现；已收藏的笔记星标常驻显示。
- 收藏区固定在树上方，带计数；点击星标取消收藏。
- 收藏不改变笔记在树里的位置（§3.3）。
- 持久化：localStorage（按笔记 id），随笔记库切换仍然有效；换机器不跟随。

### 7.3 全部折叠 / 展开

- 侧栏标题右侧一个图标按钮，点击时若当前有展开项则全部折叠，否则全部展开。
- 折叠全部后当前笔记仍然高亮，但可能被折叠隐藏——这是预期行为（和 Obsidian 的 collapse all 一致），面包屑仍能告诉用户它在哪。

### 7.4 面包屑

- 位置：筛选框下方，只在当前笔记位于子目录时显示。
- 形式：`根 › 研究 › AI`，每一级可点击；点击会展开该级的所有祖先并滚动到它。
- 当前笔记在根目录时整行隐藏。

### 7.5 排序

- 三态循环：名称升序 → 名称降序 → 时间（新→旧）。
- 文件夹和笔记使用同一规则；文件夹始终排在笔记前面。
- 选择存在 localStorage。

## 8. P1 的三个坑（已实现）

这一节记录实现时真正撞上的三个问题，以及现在各自的处理方式。

### 8.1 笔记 id 是路径哈希，移动文件等于换了一篇笔记

`vault.rs:36` 的 `note_id(rel_path)` 用相对路径算哈希。现在重命名或移动文件，id 就变了，SQLite 里以 `note_id` 关联的标注会全部变成孤儿——README 的「已知限制」里已经记了这一条。

三个选项：

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| A. 迁移 | 移动时在同一个事务里把 `notes.id` 和 `annotations.note_id` 一起改成新哈希 | 简单，但只有应用自己移动时才有效；在资源管理器里移动仍然会丢 |
| B. 稳定 id | 用 front matter 里写入的 `id: uuid` 作为主键，路径只做展示 | 需要给存量笔记补 id，并且要处理「复制文件导致 id 重复」 |
| C. 路径 + 内容指纹 | 用「正文首段哈希」做兜底匹配，移动后重新关联 | 模糊匹配有误判风险，只适合作为兜底 |

建议 **B 为主 + A 兜底**：新笔记写入 `id`，旧笔记在移动时按 A 迁移；资源管理器里的移动仍然无法感知，需要在 README 里写明。

**已实现**：`id` 优先取 front matter 的 `id:`，缺失时回退到路径哈希。应用内移动/重命名前，先把当前 id 写进 front matter（`vault::ensure_id`），再改路径，所以标注不丢；文件夹移动会给子树里每个笔记都补 id。资源管理器里的移动用**正文指纹**做配对回填（1:1 且唯一时才迁移，否则放弃），补上的 id 会写回文件，后续就稳定了。重复 id（复制文件造成）会给后一篇重新分配 uuid 并写回。

### 8.2 移动会破坏正文里的链接

如果笔记里写 `[[某篇笔记]]` 或相对路径链接，移动后链接会失效。Obsidian 的做法是移动时全库更新。本项目目前没有解析/改写链接的能力，需要决定：要么不做链接改写（并在 UI 上提示），要么先做链接解析。

**已实现**：`links.rs` 解析 wikilink（含 `#锚点`、`|别名`）和 Markdown 内联链接/图片，跳过代码块与行内代码。改写规则是「用旧路径解析目标 → 套用移动映射 → 按新路径重新渲染」，因此同时解决两类情况：指向被移动目标的外链，以及被移动文件内部的相对链接。光标式解析歧义时宁可不改；跨出笔记库的相对链接不会被猜。

### 8.3 删除是不可逆动作

主流做法是回收站（Raindrop 的 Trash、Apple Notes 的最近删除）。建议：
- 删除 = 移动到库内的 `.trash/` 目录（索引器已经跳过 `.trash`，见 `SKIP_DIRS`）。
- 提供「撤销」提示条，而不是只弹确认框。
- 不做「永久删除」入口，交给文件系统。

**已实现**：删除移动到 `.trash/<时间戳>-<随机>/<原路径>`，提示条提供 8 秒撤销（`restore_entry` 原路移回，冲突时报错而不是覆盖）。

## 9. 不推荐的做法

1. **虚拟文件夹**（只在应用里存在、不落到磁盘）：用户换 Obsidian/编辑器就看到另一套结构，违背「用户自己的收藏夹」这个前提。
2. **按标签自动分组作为主结构**：本次改动前就是这个问题，各组顺序跟着最新笔记日期漂移，用户无法预测。
3. **把文件夹和智能文件夹混在一起、不加区分**：Apple Notes 用不同图标区分；我们要做的话必须有明显视觉差异。
4. **无限深度 + 紧凑目录**：紧凑目录（`a/b/c` 合并）会让拖拽落点变模糊，VS Code 自己都有这个反馈。深层嵌套本身不是目标。
5. **拖拽排序把顺序只存在应用里**：换设备就丢。要做就写进笔记库（front matter），见 §3.4。

## 10. 诚实清单

- **调研来源以官方帮助文档和厂商/实践者文章为主，没有找到严格的人机交互实验**。「2–3 层更好用」「置顶比手动排序更可维护」这类结论是行业共识与实践经验，不是受控实验数据。
- **Obsidian 官方文档页抓取失败**（站点是 JS 渲染，WebFetch 只拿到标题），其能力矩阵依据的是搜索摘要中对官方文档的转述；具体细节（例如多选拖拽的修饰键）未逐条核实。
- **矩阵里的 ◐ 是判断，不是精确核实**，尤其 Bear/思源的置顶粒度、Raindrop 的免费版嵌套限制，厂商说法存在冲突（Raindrop 是否有付费墙就有两种说法）。
- **P0 只在前端验证**，没有在真实大库（千篇以上）上跑过；筛选和折叠的性能结论基于 10k 条合成数据的建树/拍平耗时，不含 DOM 渲染。
- **P1 已按 `tools/verify-sidebar.mjs` 在 release 原生窗口跑过**：新建/重命名/拖拽/删除/撤销 20/20，链接改写与标注跟随核对通过（2026-11-05）。验收用 CDP 合成 DOM 事件，不是物理鼠标；8 秒撤销边界和千篇级真实库没有覆盖。

## 11. 样式与交互重做（2026-11-05）

> 触发：P1 的逻辑验收做到了 20/20，但侧栏在视觉和交互上仍是「能点」的水平。20/20 只证明文件真的移动了、标注真的跟着走了，不证明它好用。这一节记录重做前的测量、调研依据、设计取值和复验结果。

### 11.1 重做前测到了什么

测量环境：dev WebView2 156，视口 1456×939（dpr 1.0），`tools/ui-shots.mjs before`，12 篇夹具（`tools/make-ui-fixture.mjs`）。

| 项 | 重做前 | 具体问题 |
| --- | --- | --- |
| 笔记行高 | 64–110px（长标题 87px） | 15px serif 标题最多两行 + 12px meta 再换行；一屏只放 7–9 篇 |
| 文件夹行高 | 36px | 与笔记行不是同一套密度；文件夹名 12.5px，笔记标题 15px，层级关系靠字号反了 |
| 文本对齐 | 文件夹在 12px chevron + 6px gap 之后；笔记没有 lead 槽 | 文本不共享列；Fluent 2 的 leaf «+24px» 规则没有实现 |
| 命中目标 | pin 20×20；side-tool 31×24（11.5px 文字）；filter 26px；rename 24px | 均低于或刚好卡在 WCAG 2.5.8 的 24×24，且小组件靠文字说明 |
| 树语义 | `role=tree/treeitem` 都没有；33 个可 Tab 元素 | 无 `aria-expanded`/`aria-selected`/`aria-level`；不能用方向键 |
| hover | `#f6f7f4` on `#fff`，标题色不变 | 几乎看不见；唯一反馈是 pin 出现 |
| focus | filter 2px `#c8d5f7`，约 1.5:1 | 低于 WCAG 2.4.11 的 3:1；树行没有自定义焦点环 |
| 拖拽 | 目标只有 1px 内描边；源行 opacity 1 | 没有「移入」文案、没有自动展开、没有边缘自动滚动；源行看起来没被拿起 |
| 右键菜单 | 160×119，36px 项，无图标/快捷键 | 和系统菜单的习惯不一致，键盘只能 Tab |
| 阅读页/图谱 | 笔记页 16/124 个文字节点 <12px；图谱页 7/43 个 | 早上的 readability 层没有真正清到 12px 门槛；`tools/audit-text.mjs` 退出 1 |

### 11.2 调研结论

| 来源 | 取到的规则 | 用在哪 |
| --- | --- | --- |
| [W3C WAI-ARIA APG — Tree View](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/) | `role=tree/treeitem/group`；父节点 `aria-expanded`；`aria-selected`；roving tabindex（整棵树一个 Tab 停点）；↑↓/←→/Home/End/Enter/Space/type-ahead；焦点与选中是两件事 | 树语义、键盘模型、焦点环与选中态分开 |
| [Fluent 2 — Tree usage](https://fluent2.microsoft.design/components/web/react/core/tree/usage) | medium 每级缩进 24px、small 12px；叶子节点额外补 24px 以抵消 chevron 占位；hover 才出现 quick actions | 留出 16px lead 槽（chevron / 文档图标共用），文本按层级对齐 |
| [Apple HIG — Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars) | 侧栏选择驱动相邻内容；拖拽有 lift / move / drop / cancel 四个状态；spring-loaded 文件夹；选择态与焦点态都要可见 | 拖拽源变暗（lift）、目标整行高亮（move）、拖入后 toast + 撤销（drop）、Esc 取消 |
| [VS Code](https://github.com/microsoft/vscode/issues/66485) / `workbench.tree.indent` | 列表行高约 22px；树缩进 8–20px 可调；拖到未展开文件夹上会自动展开；拖拽落点要有明确反馈 | 30px 文件夹 / 46px 笔记的桌面密度；650ms 自动展开；整行蓝框 + 「移入」 |
| [WCAG 2.2 2.5.8](https://webaim.org/standards/wcag/wcag22) / 2.4.11 | 指针目标至少 24×24 CSS px；焦点指示器至少 2px 厚、与背景 3:1 | pin/clear 24px，工具 26px，菜单项 32px；焦点环 2px `--blue` |
| 拖拽实践（Scalar / SaaS UI Design 等） | 三向反馈：上方线、下方线、作为子项的整块覆盖；拿起时有阴影/描边；4–8px 阈值；Esc 取消；边缘自动滚动；必须提供非拖拽路径；误放要能撤销 | 本应用只支持「移入文件夹」，所以用整行覆盖而不是插入线；4px 阈值；`Esc`；32px 边缘自动滚动；右键「移动到…」；移动 toast 可撤销 |
| [NN/g — Vertical Navigation / Tree Testing](https://www.nngroup.com/articles/tree-testing/) | 左栏适合宽/增长的层级；结构和标签先用树测试验证；渐进披露优于一次铺满 | 保留「折叠 + 面包屑 + 筛选」；不引入无限深度和手动排序 |
| Obsidian 社区反馈 | 原生文件树拖拽的落点反馈经常「没有反馈 / 拖了没动」，社区插件才补上蓝色落点线 | 不把「有 `dragover` 就算完成」当验收；必须有可见的落点、文案和撤销 |

> 说明：Apple HIG 的具体行高没有公开数值（官方页面按 small/medium/large 分级，且是 JS 渲染页）；Fluent 2 的 medium/small 缩进是页面原文，行高数值没有在抓取到的内容里出现。本项目的 30/46px 是按桌面密度、自身 12.5/14px 字号和 1456×939 视口定的，不是对某一家数值的照抄。

### 11.3 设计取值

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 文件夹行 | 30px | 与 VS Code/Obsidian 的 22–30px 区间一致；12.5px 字号下不挤 |
| 笔记行 | 46px（实测 48px，含 line box） | 单行标题 + 12px meta；一屏 13 篇，比原来的 7–9 篇多 |
| 侧栏宽度 | >1180px 时 260px；更窄回落到 app.css 的 200px | 给中文标题和「作者 · 日期」留出完整一行；窄窗口不抢正文 |
| 缩进 | 每级 14px | 2–3 层内清楚，又不把深层标题压到无空间 |
| lead 槽 | 16px + 6px gap | chevron 和文档图标共用同一列，文件夹名与同级笔记标题对齐 |
| 字号 | 文件夹 12.5、笔记标题 14 serif、meta 12、计数 12 mono | 全侧栏 ≥12px；标题保持阅读端的 serif 气质，UI 文本用 sans |
| 状态 | rest `surface` / hover 5.5% ink 混色 / active `blue-soft` + 2px 左条 / focus 2px `blue` 内描边 | hover 从「几乎看不见」变成可辨；选中与焦点用不同视觉通道 |
| 命中目标 | pin 24、clear 24、工具 26、菜单项 32、行 30/48 | 全部 ≥24px；小图标不再靠文字撑 |
| 菜单 | 190px 宽、32px 项、图标 + F2/P/M/Del | 和桌面应用习惯一致，键盘可读 |
| 键盘 | roving tabindex；↑↓←→ Home End Enter Space F2 Delete M P；type-ahead | W3C APG 的树模型；不把拖拽作为唯一移动路径 |
| 拖拽 | 源 .42 透明度；目标整行 `blue-soft` + 1.5px `blue` 内框 + 「移入」chip；650ms 自动展开；32px 边缘自动滚动；Esc 取消；移动 toast 可撤销 | 三分区反馈中「作为子项」的形态；误放可恢复 |
| 空文件夹 | 折叠时显示「空」，展开时显示一行「空文件夹」 | 不再同时出现两个「空」 |
| 动效 | 120–160ms ease-out；`prefers-reduced-motion` 由全局规则关闭 | 快、短、不抢注意力 |
| 路由 | 切库后当前 id 不存在时落到第一篇 | 不再让正文区停在「没有找到这篇笔记」 |

| 图谱页 | 明 | 30 | 0 | 0 |
| 笔记页 | 暗 | 77 | 0 | 0 |

**交互走查**（CDP 合成事件）：

### 11.5 诚实清单

- **没有做受控用户测试**。「2–3 层够用」「30/46px 比 64px 好」来自规范、竞品和工作经验，不是任务成功率数据；NN/g 的树测试方法适合下一步做，但这次没做。
- **拖拽是合成事件**：`DragEvent` + `DataTransfer`，不是物理鼠标；真实鼠标的 4px 阈值、落点抖动、跨窗口拖拽没有验证。
- **键盘 type-ahead 实现了但没有逐字验证**，中文输入法下的组合输入没有测；`*` 展开同级也未实现。
- **没有用 NVDA/Narrator 验收 ARIA 树**；`role=treeitem` 里嵌了 `tabindex=-1` 的 pin 按钮，屏幕阅读器的实际播报未确认。
- **暗色通过 CDP `Emulation.setEmulatedMedia` 验证**，没有在系统主题切换/重启原生窗口后逐项看。
- **夹具只有 12 篇**；1k/10k 的侧栏没有跑，仍是一次性渲染全部可见行（没有虚拟滚动）。
- **没有 visual-judge**：它不支持原生窗口/HTML；截图是人工检查。已检查默认、hover、菜单、重命名、焦点、拖拽、折叠、空文件夹、收藏、暗色十种状态。
- **移动撤销只测了一次**（根目录 ↔ 归档）；目标已有同名文件、链接改写失败等边界没有覆盖。
- **12px 门槛的改动波及笔记页和图谱页**：静态截图没有溢出，但没有用 50k 字长文或极端窄窗口做压力测试。
- **侧栏宽度只在 >1180px 变 260px**；更窄仍回落到 200px，长标题会更早截断。
- **本轮只改了样式与交互，没有改性能**：没有重跑启动/内存/图谱构建；CSS/JS 体积变化见 `dist` 构建输出，不影响已记录的 release 性能数字。
