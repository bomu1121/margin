# 技术小册子笔记：从「一次生成」到「渲染—检查—修补」循环

> 2026-11-17 · 依据：会话 `sess_320b28bf-…` 的完整工具记录（90 条消息 / 337 个 part）与产物文件；本期制作台实跑 `run_976ae0ea…`
> **结论**：那个会话真正的产物不是那份 HTML，而是它跑的那条循环——**写 → 渲染 → 量 → 看像素 → 打补丁 → 再渲染**。复现它需要三件基础设施：可无头渲染的构建产物、能看图的检查者、可被打补丁的源。现有的制作台三件都没有，所以只能产出「一次成文的散文」。

### 1.2 顺序

1. 环境探测：`node -v`、字体清单、Playwright 是否存在（11.6s）。
2. `TodoWrite` 立四项：版式系统 / 内容结构 / 图示 / 验收。
3. 加载 `visualize` skill（35,565 B），据此判定交付形态为自包含 HTML。
4. **一次 Write 写骨架**（含 `<!-- PART2 -->` 占位），随后 22 次 Edit 填章节、改图、修 CSS。
5. 自写 `_qa/shot.mjs`：CDP 启动 Chrome，按 1200px 切片截图，输出指标 JSON：`height / width / figs / serif / sans / chapters / outOfBounds / overflow`。
6. 逐张 Read 切片 → 在 reasoning 里列问题 → Edit → 重跑 `shot.mjs`。共 5 轮。
7. 自写 `_qa/pdf.mjs` 打印 PDF；`_qa/pdfview.html` + `pdfview.mjs` 用 pdf.js 逐页渲图并算墨迹覆盖率。
8. 交 `pdf:visual-judge`（433.5s，25 页全 pass），但**它自己不信这个全 pass**，又继续修了几轮。

## 2. 复现这条循环需要什么

### 2.1 渲染器：一个能被无头浏览器打开的自包含 HTML

- 输入是笔记源文件（Markdown + 图 spec），输出是一份**自包含 HTML**（内联 CSS/字体/SVG）；
- 用本机 Edge headless（Windows 必有）走 CDP 截图与取指标，不引入 Playwright；
- 指标口径照抄会话那套：`height / figs / chapters / outOfBounds / overflow`，再加 `under12px`（本项目已有的门槛）。
- **关键约束**：这份 HTML 必须和 app 阅读页**共用同一套 CSS 与图组件**，否则 QA 通过的是另一份东西，等于没验。

### 2.2 检查者：一个能看图的模型（当前没有）

- 会话里 43 次 Read 全是图片，9 类缺陷只有看图才能发现；
- 现在制作台配的是 `deepseek-v4-flash`，**是否支持图片输入没有验证**；设置页的 13 个 provider 里也没有配置视觉模型；
- 没有视觉检查者时的退化方案：只跑指标循环（溢出、空页、字号、图数），能抓 2/11 类，其余交人工。这不是降级选项，是**必须明说的能力边界**。

### 2.3 补丁接口：源必须是可局部重写的

会话里 22 次 Edit 改的是 HTML，内容和样式混在一起；我们要改的是 **Markdown 的某一节**或 **某个图 spec**。所以：

- 图的源是 spec（`kind/nodes/edges/note`），不是坐标；
- 章节各自独立成块，允许只重写一章；
- 每轮只改一处，改完立刻复测——会话就是这么做的（一次 Edit 对应一次 reasoning 里的单一问题）。

### 2.4 循环预算

会话用 26.6 分钟、5 轮渲染、43 张图。产品的目标是：**最多 6 轮、每轮 ≤90s、总时长 ≤20 分钟**；超预算就以「指标通过 + 人工待办清单」交付，不无限迭代。

## 3. 内容契约与存储（沿用上一版，不变）

### 3.1 三层读法

`## 一页看懂`（六条短句）→ 章节标题即结论 → `## 三句话` + `## 自检问题`。这是那个会话最值钱的内容结构，和排版无关。

### 3.2 图是内容

图注必须是一句判断；图由 spec 渲染，不手写 SVG。

```markdown
```figure
kind: flow
title: 图 2 所有渠道先汇到 Router，由它派活
nodes: 渠道|Router|Worker A|Worker B|你
edges: 渠道->Router; Router->Worker A; Router->Worker B; Worker A->Router; Worker B->Router; Router->你
note: Worker 之间一般不直接沟通；同一 PR 时两人会同时收到动态，自行协调。
```
```

### 3.3 判断与事实分开

`> 我的理解：……` 渲染成带标签的块；文末 `## 出处与边界` 声明哪些是二次分组、哪些数字没有测试条件。

### 3.4 存储

`某篇.md` + `某篇.assets/fig-02.svg`（同目录，随笔记搬家）；索引只收 `.md`（`indexer.rs:447`），assets 不进 FTS，不污染搜索。

## 5. 分期

### M1 渲染与构建（**已实现，2026-11-17**）

- 图块：`src/lib/figures.mjs` 四种模板（flow / layers / bar / quote），spec → SVG，阅读页与构建工具共用；`markdown.ts` 识别 ```` ```figure ```` 并开 DOMPurify 的 svg profile。
- 存储：仍是一篇 Markdown，图 spec 写在笔记里，不产生 assets 目录。
- 阅读页：`book.css` 提供图块、「一页看懂」两列、三句话/自检编号、术语表两列；右栏新增「目录」tab。
- 构建：`tools/booklet/build.mjs` 输出自包含 HTML（内联全部 CSS，字体指向本地文件）。
- 测量与打印：`measure.mjs`（屏幕 + `--print` 模拟）、`shot.mjs`（切片）、`print.mjs`（A4 PDF）、`run.mjs`（一条命令跑完）。
- 验收实测：样例小册子 15 节 / 8 图 / 306,148 B；屏幕 820 宽 0 溢出 / 0 越界 / 0 个 <12px / 0 处 SVG 裁切；打印 17 页且无单节超页；应用内 8 图 + 目录 14 项 + 点击跳转高亮。

### M2 生成流水线（未做）

- `booklet` 模板：outline → chapter×N → figures → assemble → **measure** → 发布
- 未做的原因：measure 要调浏览器，Rust 侧还没有无头渲染通道；先验证了「产物 + 测量 + 打印」这一段。

### M3 视觉循环（未做，依赖视觉模型）

- 切片交视觉模型逐图判断「重叠 / 空框 / 压线」→ 结构化问题列表 → 定点重写 → 重渲染。
- 没有视觉模型时，M3 不成立；当前只能做 M1 + 人工看图。

## 6. 风险与边界

- **视觉模型是硬门槛**：没有它，M3 不成立，产品只能做到「指标版」，无法替代 ZCode 那类 agent。是否接、接哪个 provider，需要单独定。
- **双渲染器分叉**：app 阅读页与 build 产物必须共用 CSS 与图组件，否则 QA 验的是另一份东西。
- **循环发散**：每轮只允许改一处并复测；会话里一次 Edit 对应一个明确问题，这一点必须写进循环约束。
- **8k 输出上限**：分章生成是必需，不是优化。
- **不做**：图可视化编辑器、跨笔记合集、EPUB。

## 7. 诚实清单

- 过程数字全部来自会话库 `message`/`part` 表（工具调用、耗时、次数），是可复算的；「9 类必须看图」是我按缺陷性质分类，不是会话里的统计。
- 会话输入是**粘贴的文案**，不是视频；如果换成视频，前面还要加 ASR 与校对两段（本期实跑 154s）。
- `deepseek-v4-flash` 是否支持图片输入**未验证**；M3 的可行性取决于这一点。
- 自包含 HTML build、figure 渲染器、Edge headless PDF 都**没有实现**，也没有做过视觉验收。
- 「26.6 分钟」是消息时间跨度，不等于纯工作时长（含思考与等待）。
