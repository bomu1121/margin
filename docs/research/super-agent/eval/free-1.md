# Super Agent 的价值不在更聪明的模型，而在把 agent 从「一次性外包」改造成一支有项目经理的常驻团队

## 结论

- **瓶颈已经从模型能力转移到人的注意力。** DeepSeek 的观察是：单任务的上限取决于模型能力，多任务的上限取决于人的注意力；一个人通常只能同时跟进 3 到 5 个活跃会话。会话制 agent 越多，人越像 AI 之间的传话筒。
- **核心解法是把「连续性」和「并发」拆给两种角色。** 上层 router 常驻、用轻量模型就够了，只负责沟通与派活；下层 worker 各自独立上下文、配最强的模型，决定交付质量。用户始终只面对同一个对接人。
- **收益有数字，代价也有数字。** DeepSeek 的对比试验里，Super Agent 比传统单对话 agent 速度快了一倍、工作更稳定；代价是读缓存的 token 是单会话方案的 2 倍到将近 4 倍。

## 问题：会话制 agent 的天花板

现在主流 agent（Claude Code、CodeX、DeepSeek Harness）都以会话 session 为单位干活：开一个会话、布置一个任务，agent 在里面「想一步、做一步、看结果、再想下一步」，直到干完。这个循环叫 react loop。单个任务上它很好用，所以流行了很久。

问题出在多任务并行时。你开一个会话修 bug、一个写文档、一个跑测试，群里同事一句「这个需求改一下」又要新开一个会话；这些会话互相不知道对方在干什么，跨任务的信息只能靠人记住再手动搬运。

即使给 agent 接上飞书、借 CLI 和 MCP 让它自己去群里接活，只要底层还是单个会话，就会撞上三个结构性限制：

1. 执行耗时命令时整个循环卡住，命令跑完才能处理新消息；
2. 多个需求塞进同一个会话，上下文越来越乱；
3. agent 跑在本地电脑上，电脑一休眠它就罢工。

所以 DeepSeek 的判断是：必须把 agent 和单次会话解绑，让它成为能跨会话记住上下文、同时推进多件事且互不干扰的连续工作者。这就是 Super Agent。按素材的类比，传统 agent 是「一次只能干一件事的外包」，Super Agent 是「配合默契的项目团队」——团队内部很多人，但你只跟一个对接人打交道。

DeepSeek 给它总结了四个基础特征：**连续**（在飞书群还是 GitHub 聊都行，群里说用方案 A、后来 PR 里改成方案 B，它能跟上）、**高效**（上一件没干完也能接下一条指令）、**主动**（自己盯群消息和工单，该处理的处理，不该管的保持安静）、**持久**（一直在线，出问题能自己恢复）。

## 机制：router 层与 worker 层

为什么不是「一个人全干」或「每件事都找个新人」？素材给了一个很直白的权衡：二十件事全交给一个人，信息不断但只能排队做；每件事都找新人，能同时开工但互不同步，最后一人一嘴来找你汇报。DeepSeek 的选择是两者都要——招一个项目经理，再配几个工程师。

| 维度 | 传统单会话 Agent | Super Agent |
| --- | --- | --- |
| 工作单元 | 一个 session 一个任务 | router + 多个独立 worker |
| 上下文 | 多需求塞进同一会话会变乱 | worker 各自独立上下文，干完向 router 汇报 |
| 用户接口 | 每个会话各说各话 | 始终是同一个对接人（router） |
| 模型配置 | 单一模型承担全部 | router 轻量模型即可，worker 配最强模型 |
| 在线方式 | 绑在本地电脑上 | 计算在云端容器，状态入库，经 Daemon 调用本地环境 |

两个细节值得记下来：

- **router 不亲自干活。** 它只负责沟通和派活，所以用轻量模型就够；真正决定交付质量的是 worker。
- **router 不会因为消息多而过载。** DeepSeek 实践中发现，router 处理上一批消息时，新消息先攒着，等它忙完再一起看、一起派活；采用这种批处理机制后，消息越多，平均处理反而越快。
- **worker 之间一般不直接沟通。** 两个 worker 同时改同一个 PR 时，会同时收到该 PR 的新动态，自己协调；任务太复杂时 worker 还能再拉几个 sub agent，相当于工程师自己带实习生。

### 事件驱动：trigger 的两级过滤

传统 agent 是你说一句它才干一次，Super Agent 由环境里发生的事情驱动——群里来新消息、PR 下有人评论、代码构建失败，DeepSeek 把这些事件统一叫 trigger。

但直接让大模型盯群消息不现实：群里废话太多，每条都让模型判断要不要管，又慢又烧钱。DeepSeek 用两级过滤：门卫只看消息来源（是不是监听的群、发消息的人在不在白名单），用普通代码秒判；通过门卫的消息再交给「秘书」，由大模型按提示词里写好的规则判断要不要处理。这就是计算机系统里 fast path / slow path 的快慢路径思想。

### 派活：thread 订阅

如果每条消息都要过 router 一手，router 压力会很大。素材的类比是：一个工单第一次进来时经理分给小王，之后这个工单的消息直接抄送小王。Super Agent 里，同一个 PR、同一个群话题、同一串邮件里的连续消息构成一个 thread（可理解为一个工单）；worker 接手后订阅这个 thread，后续新消息由程序直接送到他手上，不再经过 router，能省大量 token。

### 喂料：inline 与 spill，链式召回

给多了重点被淹没，给少了干活的人反复回头问。DeepSeek 的口径是「浪费上下文窗口就是浪费模型的智能」，并借用了编译器里的两个概念：

- **inline 内联**：像同事转消息时顺手附上前后几句聊天和相关工单号，一眼看懂来龙去脉；
- **spill 溢出**：几万字的文档只给摘要和一句「完整内容见这里」，需要时再去翻。

把这个思路用到系统层面就是**链式召回（chain of recall）**：系统给每条消息、每个工单、每个 worker 都编号，每张卡片上只写摘要和关联编号；你跨平台提起一件旧事时，router 不需要背下全部历史，顺着编号一路往下翻即可。

### 主动：投机执行 + 观察模式

素材借用了 CPU 的「投机执行」：不确定某段计算会不会用上时先提前算好，用上了就赚、用不上就扔。用在干活上，比如收到会议邀请，先在后台核对日程、查背景资料、备好回复草稿，你确认一下就能发。

但主动不等于乱来，这里有两个明确的限制条件：DeepSeek 开源的原型里，**没人要求的主动工作必须有团队提前写好的规则才能做**；而且**默认先跑观察模式**，只记录自己打算做什么、并不真的动手，等你确认判断靠谱了再放开。

### 全双工：把对讲机换成电话

传统 agent 一干活就忽视新消息，根源是 react loop 是半双工的——像对讲机，同一时间只能一方说话。Super Agent 要做全双工：把耗时的工具调用改成异步，命令一启动就立刻返回，agent 可以继续跟你聊，命令跑完结果再作为一条新消息送回来。素材也承认，这个机制在很多 AI 工具中已经实现。

能边干活边聊天之后，还要管渠道表达：终端里长篇大论的思考过程原样发到群里会炸群，好在冗长的推理都关在 worker 里，只有 router 对外说话。DeepSeek 给不同渠道定了规矩——飞书里只在需要你拍板时才发消息，单次回复不超过一百个词；GitHub 和邮件里则要写清问题背景、改动和验证结果。

## 部署：把计算、状态、执行环境拆开

本地 agent 把三样东西绑在同一台电脑上：负责干活的计算、会话记录这类状态、代码与工具构成的执行环境。电脑一休眠，三样全停。DeepSeek 借存算分离分两步拆：

1. **计算与状态分开。** 计算放在云端可随时替换的容器里，会话状态存进数据库；容器挂了换一个，记录一条不丢。
2. **计算与执行环境分开。** 代码、密钥、内网服务很难完整搬到云端，那就别搬：大脑留在云端，本地只装一个很轻的 Daemon——不保存会话记录，只按云端指令执行命令、回传结果。DeepSeek 称之为 **BYOM（Bring Your Own Machine）**。哪怕笔记本今天没开机，等它重新上线，云端会自动把该在这台电脑上做的事做完。

另外，主系统之外单独配了一个 **Watchdog（看门狗）会话**当值班主管，定时巡查。它不只看员工在不在岗，更看任务有没有进展——因为 agent 出问题很多时候不是程序挂了，而是模型在原地打转或跑偏；发现异常就及时介入修复。

```figure

title: 一个事件从进入系统到交付的路径
items:
  - trigger：群消息 / PR 评论 / 构建失败
  - 快慢路径过滤：门卫看来源，秘书用模型看内容
  - router：常驻、轻量模型，只沟通与派活
  - thread 订阅：后续消息直达 worker，绕过 router
  - worker：独立上下文、最强模型，可再拉 sub agent
  - router 统一对外回复，按渠道规范表达
```

## 数字与代价

| 指标 | 数值 | 口径 |
| --- | --- | --- |
| 速度 | 比传统单对话 Agent 快一倍 | DeepSeek 做的对比试验 |
| 稳定性 | 更稳定 | 同上，原文未给出具体量化指标 |
| 读缓存 token | 单会话方案的 2 倍到将近 4 倍 | 同时维护多个会话带来的成本 |
| 人的并行上限 | 3 到 5 个活跃会话 | DeepSeek 的观察 |
| 渠道回复长度 | 飞书单次不超过 100 个词 | DeepSeek 为渠道定的规矩 |

速度翻倍伴随缓存 token 涨 2 到近 4 倍，这是这套架构最需要提前算清的一笔账：省下的是人的注意力与等待时间，付出的是 token 成本。素材没有给出这两者在什么任务分布下划算的进一步拆分，原文未说明。

## 边界与开放问题

DeepSeek 自己抛出、且素材未给出答案的四个问题：

1. 任务规模继续变大，一个项目经理还够用吗？连续跑上几个月，长期记忆怎么办？
2. 不再盯着会话之后，人该用什么方式跟 agent 协作？聊天窗口还是最好的界面吗？
3. 每个人的私人助理和团队共用的 Super Agent 之间，怎么在不泄露隐私的前提下互相配合？
4. agent 越主动，接触的不可信信息就越多，万一被提示词注入攻破怎么办？

素材作者把安全视为「Agent 工作最大的一道坎」，并给了一个很实际的追问：敢不敢让 AI 全天 24 小时盯着群聊、操作你的电脑？一条恶意消息把 AI 忽悠了，数据和隐私怎么办。这个判断与原型里的两个设计约束互为呼应——主动行为必须先有团队写好的规则，且默认只观察不动手。就本次素材能确认的范围而言，这条防线目前是规则 + 观察模式，而不是模型层面的保证。

从工程视角看，这套架构真正可迁移的不是某个模块，而是三个思路：把「跟人打交道」和「把活干完」拆成两种角色、两种模型；用快慢路径和订阅把大模型的调用次数压下去；用存算分离与 BYOM 让长时在线不再依赖某台机器的开机状态。素材提到这是一个开源的研究原型，感兴趣可以到 GitHub 上看，但原文未给出仓库地址与具体实现细节。
