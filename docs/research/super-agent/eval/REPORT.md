# Super Agent 笔记对照实验（2026-11-18）

## 1. 实验设计

- **素材**：`run_54c3d3ec…/transcribe/transcript-01.md`（Super Agent 那期口播稿），12,050 B / 3,342 CJK。
- **模型**：制作台与 ZCode 都是 `deepseek-flash`。
- **组**：5 组 × 3 次，共 15 次运行。
  - `minimal`：目标只有一句“把素材生成一份美观的笔记”，工具 `write_note / patch_section / finish`，6 回合，门禁只要“有标题 + ≥200 字”。
  - `plan`：在 minimal 上增加 `todo_write` 和“先列 3–6 步计划”的指示，8 回合。
  - `audit`：在 minimal 上开放 `audit_note`（结构自查），8 回合，门禁仍是 minimal。
  - `free`：中等 brief（结构建议、1,500–4,000 字、可用表格/图）+ 强制 `audit_note`，10 回合，门禁要求 audit 清零。
  - `zcode`：只给一句“把这段文字生成一份美观的笔记”+ 素材文件；general-purpose 子会话，使用 ZCode 自己的系统提示和通用工具。
- **测量**：产物 CJK/小节/表格行/图；12 个要点的关键词覆盖；回合（模型请求数）；输入/输出 token；成本；耗时；失败原因。

失败原因（都来自任务日志）：

- `minimal-2`：连续 5 次 `patch_section` 重写第 4 节，达到 6 回合上限，没有 `finish`。没有 audit 可以告诉它“已经够了”。

## 4. 结论

1. **ZCode 明显更“厚”**：3,696 CJK（比 minimal +47%，比 free +24%）、14 个二级小节、58–71 行表格、mermaid/ASCII 示意图、术语表、取舍说明。代价是输入 token 5–15 倍（147,867 vs 10,174–27,170）和 2–3 倍耗时。
2. **制作台的瓶颈不是写作约束，是可靠性**：12 次里 3 次失败（25%），两次是回合耗尽循环，一次是 JSON 解析失败；ZCode 3/3。所有成功产物都覆盖了 12 个要点，长度差距主要来自展开和图示，不是漏掉事实。
3. **plan 档不值得**：输入 token 最高（27,170）、成本最高（¥0.0557）、2/3 成功，覆盖率与 minimal 相同。加规划没有带来更好的笔记，只带来更多回合和一个循环失败。
4. **free 档是制作台里最好的平衡**：3/3 成功、最长（2,988）、每次 1 张图、成本 ¥0.0379。它的结构/字数提示不是主要功劳，强制 audit（眼睛）和 10 回合预算才是。
5. **minimal 最便宜也最薄**：¥0.0324、2,520 字，但 2/3 成功；没有 audit 时，模型会在某节上反复改到回合耗尽。
6. **要接近 ZCode 的厚度，下一步是 harness，不是再加写作规则**：原生 tool calling（消除 JSON 解析失败）、更多工具/回合、允许 ASCII/mermaid 或应用内图块生成；写作规则这一轴已经饱和（12 个要点全中）。

## 5. 实验后的修复（2026-11-19）

### 5.1 写完自动回结构状态

`write_note` / `patch_section` 的观察现在自动附一行确定性结构状态，例如：

```
已写入 3839 字符；结构：H1 1 · H2 13 · 2367 字 · 图问题 0；问题：二级小节 13 个，超过 12
```

模型不用额外调用 `audit_note` 就知道自己是否写完、哪里超限；它也仍然可以主动调用 `audit_note` 看完整小节清单。同时把审计上限从 12 节 / 5,000 字放宽到 **20 节 / 6,000 字**（ZCode 的厚笔记是 14–18 节，旧上限会逼模型压缩）。

修复后 `minimal` 3 次：

| 运行 | 状态 | CJK | H2 | 回合 | 输入/输出 tok | 成本 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| minimal-4 | ok | 2,419 | 12 | 4 | 19,826/6,538 | ¥0.0497 | 首版 13 节，audit 提示超限，自己改到 12 节 |
| minimal-5 | ok | 2,636 | 12 | 2 | 8,639/2,694 | ¥0.0210 | 一次成稿，问题：无，直接结束 |
| minimal-6 | ok | 2,875 | 10 | 2 | 9,114/3,461 | ¥0.0248 | 一次成稿，问题：无，直接结束 |

3/3 成功；后两次都是 2 回合。修复前同一档是 2/3（一次 patch 循环耗尽回合）。

### 5.2 失败也记账、也留轨迹

失败路径现在把 worker 的 `run`（含 usage、turns、draft）写回 `production_agent_tasks.run_json`；Rust 在返回失败前把 token 计入任务用量，并落 `agent-run.json` + 失败草稿 `note.md`。

| --- | --- | --- |
| 任务用量 | 0/0，¥0 | **3,044/2,988 tok，¥0.0162** |
| 失败轨迹 | 无 | `agent-run.json` 33.5 KB |
| 失败草稿 | 无 | `note.md` 10.2 KB |

### 5.3 仍未修

- 长 `write_note` 的 JSON 字符串仍可能解析失败（`audit-2` 的失败原因）；这是 JSON-in-text 协议问题，根治要原生 tool calling。
- 自动结构状态是“软提示”：模型可以选择不理会；门禁仍只有标题 + ≥200 字。

## 6. 边界

- 每组 3 次、一个模型、一份素材；没有统计显著性，失败率只能当方向。
- 12 要点覆盖是关键词语义启发式，不是人工评分；“写得好不好”仍要人读。
- 制作台失败运行的 token 未入账，成本列低估了失败成本。
- ZCode 侧是 general-purpose 子会话，素材通过 Read 读取（不是粘贴），系统提示与主会话不完全相同。
- ZCode 的 mermaid/ASCII 图在制作台笔记阅读器里不能渲染；制作台的 `figure` 块可以。可移植性相反。
- 制作台产物带 front matter（id/标题/类型/来源/日期），ZCode 产物没有；CJK 统计含 front matter。
