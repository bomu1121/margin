| :--- | :--- |

## 1. 先看清问题：现在 Agent 是怎么干活的

主流 Agent（Claude Code、CodeX、DeepSeek Harness）都以**会话（session）**为单位工作：

```
你开一个会话 → 布置任务 → Agent 想一步、做一步、看结果 → 再想下一步 → 直到干完
                              └──────────── ReAct Loop ────────────┘
```

单任务场景下这套模式很好用，所以流行了很久。**问题出在「同时有好几件事」的时候。**

- 一个会话修 bug，一个会话写文档，一个会话跑测试；
- 同事在群里说「这个需求改一下」，你又得新开会话；
- 这些会话**互相不知道对方在干什么**，跨任务的信息只能靠你记住、手动搬运。

> 单任务的上限取决于模型能力，多任务的上限取决于人的注意力。
> —— DeepSeek 官方

结果就是你不知不觉成了**「一群 AI 之间的传话筒」**。官方观察：一个人通常只能同时跟进 **3～5 个**活跃会话。AI 越来越能干，人反而越来越累。

---

## 2. 那给 Agent 接上飞书、让它自己去群里接活呢？

借助 CLI 和 MCP 确实能做到，但**只要底层还是单个会话**，就会撞上三个硬伤：

| # | 症状 | 根因 |
| :-: | :--- | :--- |
| **1** | 跑耗时命令时整个循环卡住，命令跑完才能看新消息 | ReAct Loop 是**半双工**的 |
| **2** | 好几个需求塞进同一个会话，上下文越来越乱 | **一个会话 = 一个上下文**，没有隔离 |
| **3** | 电脑一休眠它就罢工 | 计算 / 状态 / 执行环境**绑在同一台机器**上 |

三个症状，对应后面三个解法：**全双工**、**Router/Worker 分层**、**存算分离**。

---

## 3. 定义：Super Agent 是什么样的

必须把 **Agent 和单次会话解绑**，让它变成一个能跨会话记住上下文、同时推进多件事、彼此互不干扰的**连续工作者**。

文章给了四个基础特征：

| 特征 | 含义 | 具体表现 |
| :-: | :--- | :--- |
| **连续** | 跨渠道、跨时间保持同一份认知 | 群里说用方案 A，后来在 PR 里改成方案 B，它跟得上 |
| **高效** | 多任务并行，互不阻塞 | 上一件没干完，也能接下一条指令 |
| **主动** | 由环境事件驱动，而不是你说一句才动一下 | 自己盯群消息和工单，该处理的处理，不该管的保持安静 |
| **持久** | 一直在线，出问题能自愈 | 本地电脑关机也不掉线，恢复后自动补做 |

### 一个真实运行的例子

```
用户在群里提需求：正文、代码、终端的字体希望能分开配置
        ↓  维护者 @ 了一下 Super Agent
Super Agent 到 GitHub 提交改进代码
        ↓  群里追问 + PR 里维护者提建议
持续修改，一直推进到代码合并
```

更强的一次：它**自己从产品用户群里识别出 bug** → 后台自主复现 → 找到根因 → 直接把修复代码和前后对比截图发出来。**不用人催。**

## 4. 架构总览：一张图看完

```
渠道消息（飞书群 / GitHub / 邮件 / IDE）
   │
   ▼
【门卫】fast path ── 纯代码判断：是不是监听的群？人在不在白名单？秒判、不烧 token
   │ 放行
   ▼
【秘书】slow path ── 大模型按提示词规则判断：这条到底要不要管
   │ 是需要处理的事件
   ▼
【Router｜项目经理】常驻在线 · 轻量模型 · 记住全局 · 对外沟通 · 派活
   │ 首次派活
   ├──▶【Worker A】最强模型 · 独立上下文 · 干完汇报
   ├──▶【Worker B】
   └──▶【Worker C】──▶【Sub Agent】任务太复杂时按需拉人

   同一 thread（同 PR / 同群话题 / 同邮件串）的后续消息
   ──▶ 程序直送已订阅的 Worker，绕过 Router，省下大量 token
```

整套架构可以归纳成**五件事**（编号按原文叙述顺序，原文只说了「拆成五个模块」，未逐一命名）：

| # | 模块 | 要解决的问题 | 关键机制 |
| :-: | :--- | :--- | :--- |
| 1 | **分层编排** | 「连续」和「速度」二选一 | Router（项目经理）+ Worker（工程师） |
| 2 | **事件驱动** | 被动等指令；群消息噪音太大 | Trigger + 门卫/秘书两级过滤 |
| 3 | **任务路由** | 所有消息都过 Router 会压垮它 | Thread 订阅，后续消息直送 Worker |
| 4 | **上下文管理** | 资料给多看不过来，给少反复来问 | Inline / Spill / Chain of Recall |
| 5 | **运行形态** | 卡死、休眠、跑偏 | 全双工异步 + 存算分离 + Watchdog |

## 5. 拆开看：五个模块怎么工作

### 5.1 分层：招一个项目经理，再配几个工程师

假设你手里同时有 **20 件事**：

- 全交给一个人 → 信息不断，但只能排队一件件做（**连续但慢**）
- 每件事找个新人 → 能同时开工，但互不同步、都来找你汇报（**快但乱**）

DeepSeek 的选择是「我全都要」——现实团队早就有答案：**招一个项目经理，再配几个工程师。**

| 角色 | 类比 | 职责 | 模型 |
| :--- | :--- | :--- | :--- |
| **Router** | 项目经理 | 常驻在线，收所有渠道消息，记全局，跟你沟通，派活 | **轻量模型足够**（不亲自干活） |
| **Worker** | 工程师 | 独立上下文，专心干好一件事，干完汇报 | **最强模型**（决定交付质量） |

几条关键设计：

- **对外始终是同一个人**：团队内部怎么分工你不用关心。
- **Router 会不会忙不过来？** 不会。它处理上一批消息时，新消息先**攒着**，忙完一起看、一起派活。批处理之后，**消息越多，平均处理反而越快**。
- **Worker 之间不直接沟通**：两个 Worker 改同一个 PR 时，会同时收到该 PR 的新动态，自己就能协调。
- **Worker 还能再拉 Sub Agent**：相当于工程师自己带了实习生。

### 5.2 事件驱动：Trigger 与两级过滤

传统 Agent 是你说一句才动一次；Super Agent 由**环境里发生的事**驱动——群里来了新消息、PR 下有人评论、构建失败了。这些统一叫 **Trigger（触发事件）**。

但群里的废话太多，每条都丢给大模型判断又慢又烧钱。解法是**两级过滤**，也就是计算机系统里的快慢路径思想：

| 关卡 | 类比 | 看什么 | 成本 |
| :--- | :--- | :--- | :--- |
| **Fast path** | 门口门卫 | 只看**来源**：是不是监听的群、人在不在白名单 | 普通代码，秒判 |
| **Slow path** | 里面秘书 | 读**内容**：大模型按提示词里写好的规则判断要不要处理 | 贵，但只处理通过门卫的消息 |

### 5.3 任务路由：Thread 订阅

每条消息都经 Router 转手，项目经理也会被压垮。现实中的做法是：工单第一次进来时经理分给小王，之后**这个工单的消息直接抄送小王**。

Super Agent 里，**同一个 PR、同一个群话题、同一串邮件里的连续消息**构成一个 **Thread**（可以理解为一个工单）。Worker 接手后**订阅**这个 Thread，后续新消息由程序直接送到它手上，不再经过 Router——**能省下大量 token**。

### 5.4 上下文管理：Inline / Spill / Chain of Recall

**浪费上下文窗口，就是浪费模型的智能。** 资料给多了重点被淹没，给少了干活的人反复回头问。DeepSeek 借用了编译器里的两个概念：

| 概念 | 类比 | 做法 |
| :--- | :--- | :--- |
| **Inline（内联）** | 同事转消息时顺手附上前后几句聊天和相关工单号 | 该带的上下文直接塞进去，一眼看懂来龙去脉 |
| **Spill（溢出）** | 几万字的文档，只给摘要 + 「完整内容见这里」 | 主体压缩，原文留在外面，需要时再去翻 |

两者合起来，就是全系统的 **Chain of Recall（链式召回）**：

> 系统给每条消息、每个工单、每个 Worker 都编了号，每张卡片上只写**摘要 + 关联编号**。
> 你跨平台提起一件旧事，Router 不用背下全部历史，**顺着编号一路往下翻**就行——像侦探找线索。

### 5.5 主动但不乱来：投机执行 + 观察模式

借鉴 CPU 的**投机执行**：不确定会不会用上，先提前算好，用上了赚到，用不上就扔掉。

> 收到一封会议邀请 → 后台核对日程、查好背景资料、备好回复草稿 → 你确认一下就能直接发。

但**主动 ≠ 乱来**，开源原型里有两条硬约束：

1. **规则先行**：没人要求的主动工作，必须有团队提前写好的规则才允许做；
2. **默认观察模式**：只记录「我打算做什么」，不真的动手；等你确认它的判断靠谱了，再放开。

### 5.6 全双工：把对讲机换成电话

传统 Agent 一干活就看不见新消息，因为 ReAct Loop 是**半双工**的——像对讲机，同一时间只能一方说话。

具体做法：**把耗时的工具调用改成异步**。命令一启动就立刻返回，Agent 继续跟你聊天，等命令跑完，结果作为**一条新消息**送回来。

> 这个机制在很多 AI 工具里其实已经实现了——难的不是技术，而是把它接到「多会话、多渠道」的架构上。

### 5.7 分渠道说话：别把终端里的长篇大论发到群里

冗长的推理过程都关在 Worker 里，**只有 Router 对外说话**，而且每个渠道有各自的规矩：

| 渠道 | 规矩 |
| :--- | :--- |
| **飞书** | 只在需要你拍板时才发消息；**单次回复不超过 100 个词** |
| **GitHub / 邮件** | 写清楚**问题背景、改动内容、验证结果** |

### 5.8 持久在线：存算分离分两步走

本地 Agent 把三样东西绑在同一台电脑上——**计算**（干活）、**状态**（会话记录）、**执行环境**（代码、工具）。电脑一休眠，三样全停。

```
第一步：计算  ⟂  状态
  计算 → 云端可随时替换的容器（挂了就换一个）
  状态 → 数据库（换容器，记录一条都不丢）
  「靠谱的团队会把工作记录放进档案室，谁来接班都能接着干」

第二步：计算  ⟂  执行环境
  代码 / 密钥 / 内网服务搬不上云 → 那就别搬
  大脑留在云端，本地只装一个很轻的 Daemon：
    · 不保存会话记录
    · 只做两件事：按云端指令执行命令、回传结果
  「远程专家指挥现场的助手」
```

这套叫 **BYOM —— Bring Your Own Machine（带上你自己的电脑）**。哪怕笔记本今天没开机，等它重新上线，云端也会自动把该在这台电脑上做的事做完。

### 5.9 自愈：Watchdog 看门狗

主系统外面单独配一个 **Watchdog 会话**，相当于**值班主管**，定时巡查。

关键点：它**不只看员工在不在岗，更看任务有没有进展**。因为 Agent 出问题，很多时候程序并没有挂，而是**模型在原地打转或者跑偏**。一旦发现异常，及时介入修复。

## 6. 收益与代价

DeepSeek 做的对比试验（原文只给了相对倍数，没有给绝对数值和测试细节）：

| 指标 | Super Agent 对比单对话 Agent |
| :--- | :--- |
| **速度** | **快 1 倍（即 2×）** |
| **稳定性** | 更稳定 |
| **读缓存 token** | **2× ～ 接近 4×**（因为同时维护多个会话） |

**一句话总结：拿 token 换并发和稳定。**

## 7. 四个开放问题（原文自己承认没解决）

| # | 问题 | 本质 |
| :-: | :--- | :--- |
| 1 | 任务规模继续变大，一个项目经理还够用吗？连续跑上几个月，长期记忆怎么办？ | **扩展性 + 长期记忆** |
| 2 | 不再盯着会话之后，人该用什么方式跟 Agent 协作？聊天窗口还是最好的界面吗？ | **交互范式要重设计** |
| 3 | 私人助理和团队共用的 Super Agent 之间，怎么在不泄露隐私的前提下配合？ | **多 Agent 的权限边界** |
| 4 | Agent 越主动，接触的不可信信息越多，被提示词注入攻破了怎么办？ | **安全** |

> **我的看法**：安全是 Agent 落地最大的一道坎。就问一句——你敢不敢让 AI 全天 24 小时盯着群聊、操作你的电脑？万一来了条恶意消息把 AI 忽悠了，数据和隐私怎么办？
>
> 但整体仍然看好：它本质上是**把一套成熟的团队管理方法搬进了 AI 的世界**。

## 8. 术语速查

| 术语 | 大白话 | 类比 |
| :--- | :--- | :--- |
| **Session** | 一次对话窗口 | 一个人一次只能干一件事 |
| **ReAct Loop** | 想一步 → 做一步 → 看结果 | 边做边想的工作循环 |
| **Router** | 统一对外的调度者 | 项目经理 |
| **Worker** | 真正干活的最小单元 | 工程师 |
| **Sub Agent** | Worker 临时拉来的帮手 | 工程师带的实习生 |
| **Trigger** | 触发 Agent 干活的事件 | 工单来了 |
| **Fast / Slow Path** | 便宜的先筛、贵的再判 | 门卫 + 秘书 |
| **Thread** | 一串相关消息（同 PR / 同话题 / 同邮件） | 工单 |
| **Inline / Spill** | 直接塞进去 / 只给摘要和引用 | 转发消息带上下文 / 附文档链接 |
| **Chain of Recall** | 靠编号一层层找回历史 | 侦探顺着线索查案 |
| **投机执行** | 先算好，用不上就扔 | 提前备好会议回复草稿 |
| **BYOM** | 云端的脑子 + 你本地的机器 | 远程专家指挥现场助手 |
| **Watchdog** | 定时巡查、看进展不看存活 | 值班主管 |

## 9. 三句话记住这篇

1. **痛点**：单会话 Agent 让「人的注意力」变成多任务的上限——你成了 AI 之间的传话筒。
2. **解法**：Router（项目经理，轻量模型）+ Worker（工程师，最强模型）+ Thread 订阅 + 存算分离 + Watchdog，让 Agent 变成 7×24 的连续工作者。
3. **代价**：速度 2×，但读缓存 token 2×～4×；而真正的天花板是**安全**——越主动，越容易被提示词注入。
