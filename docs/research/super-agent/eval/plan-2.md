# Super Agent：把 Agent 从「会话」里解绑

> 素材来源：讲解 DeepSeek Harness 团队提出的 Super Agent 架构的科普视频转述。本文只做结构化重述，未补充素材以外的数字、书目与链接。

## 一句话结论

传统 Agent 以**单次会话（session）**为工作单位，单任务上限取决于模型能力，**多任务上限取决于人的注意力**。Super Agent 的思路是把 Agent 和单次会话解绑，让它成为一个**跨会话记上下文、并行推进多件事、彼此互不干扰的连续工作者**。

---

## 一、问题：会话制 Agent 卡在哪

主流 Agent（Claude Code、CodeX、DeepSeek Harness 等）都在会话里跑 **ReAct Loop**：想一步 → 做一步 → 看结果 → 再想下一步，直到任务完成。

单任务下这套循环很好用，但多任务时：

- 修 bug、写文档、跑测试各开一个会话；
- 群里同事一句「需求改一下」，又要新开一个会话；
- 会话之间互不知情，跨任务信息全靠人脑记、手工搬。

于是人变成了「一群 AI 之间的传话筒」。DeepSeek 的观察是：**一个人通常只能同时跟进三到五个活跃会话**——AI 越能干，人越累。

给 Agent 接飞书、靠 CLI + MCP 让它自己看群消息接任务，看似可行，但只要底层还是单个会话，就会撞上三个硬问题：

| # | 问题 | 表现 |
|---|---|---|
| 1 | 半双工阻塞 | 执行耗时命令时整个循环卡住，跑完才能处理新消息 |
| 2 | 上下文污染 | 多个需求塞进同一会话，上下文越来越乱 |
| 3 | 依赖本地机器 | Agent 跑在本地电脑，电脑休眠就罢工 |

## 二、架构：一个项目经理 + 若干工程师


素材提到，DeepSeek 把整套架构拆成五个模块；理解它最省力的方式，是类比成一个现实项目团队。

如果二十件事全交给一个人，信息不断但只能排队做；每件事都找新人，能并行但信息不同步、汇报混乱。DeepSeek 的选择是「我全都要」——照搬现实团队：招一个项目经理，配几个工程师。

```
渠道消息（飞书群 / GitHub / 邮件 …）
        │
        ▼
┌───────────────────────────┐
│  Router 层（项目经理）      │  常驻在线 · 记住全局 · 对外沟通 · 派活
│  轻量模型即可              │
└───────────────────────────┘
        │  派活          ▲ 汇报
        ▼                │
┌──────────┐  ┌──────────┐  ┌──────────┐
│ Worker A │  │ Worker B │  │ Worker C │   各自独立上下文
│ 最强模型  │  │          │  │  可再拉  │
└──────────┘  └──────────┘  │ sub agent│
                             └──────────┘
```

- **Router = 项目经理**：不亲自干活，只负责沟通与派活，所以**轻量模型就够**。
- **Worker = 工程师**：每人独立上下文，专心干一件事，干完向 Router 汇报，由 Router 统一回复你。
- **交付质量由 Worker 决定**，因此最强模型配在 Worker 上。
- 你面对的始终是同一个「对接人」，团队内部怎么分工不用关心。

### 四个基础特征

1. **连续**：在飞书群还是 GitHub 跟它聊都行；群里说用方案 A，后来在 PR 里改成方案 B，它跟得上。
2. **高效**：同时推进好几件事，上一件没干完也能接下一条指令。
3. **主动**：自己盯着群消息和工单，该处理的处理，不该管的保持安静。
4. **持久**：一直在线，出问题能自己恢复。

## 三、消息怎么进来：Trigger + 两级过滤

传统 Agent 是你一句它动一次；Super Agent 由**环境事件驱动**，这些事件统一叫 **trigger**：群里来了新消息、PR 下有评论、代码构建失败……

但群消息里废话太多，每条都过大模型判断又慢又烧钱。DeepSeek 用**两级过滤**（快慢路径思想）：

| 层级 | 类比 | 判断依据 | 成本 |
|---|---|---|---|
| Fast path | 门卫 | 消息从哪来：是否监听的群、发送者是否在白名单 | 普通代码，秒判 |
| Slow path | 秘书 | 读内容，按提示词里写好的规则判断要不要处理 | 大模型 |

## 四、派活之后：Thread 订阅与上下文配给

### Thread：工单式直连

同一个 PR、同一个群话题、同一串邮件里的连续消息构成一个 **thread**（可理解为工单）。Worker 接手后**订阅**该工单，后续新消息由程序直接送到它手上，**不再经过 Router**，省下大量 token。

补充两点：

- **批处理**：Router 处理上一批消息时，新消息先攒着，忙完一起看、一起派。消息越多，平均处理反而越快。
- **Worker 之间一般不直接沟通**；若两个 Worker 在改同一个 PR，会同时收到该 PR 的新动态，自己协调。任务太复杂时，Worker 还能再拉几个 **sub agent**（相当于工程师自己带实习生）。

### 上下文配给：Inline / Spill / Chain of Recall

资料给多了重点被淹没，给少了干活的人反复回头问。DeepSeek 的判断是：**浪费上下文窗口就是浪费模型的智能**。借自编译器的两个概念：

- **Inline（内联）**：像同事转消息时顺手附上前后几句聊天和相关工单号，一眼看懂来龙去脉。
- **Spill（溢出）**：几万字的文档只给摘要 + 「完整内容见这里」，需要时再翻。

系统化之后就得到 **链式召回（chain of recall）**：给每条消息、每个工单、每个 Worker 编号，卡片上只写摘要和关联编号。跨平台提起旧事时，Router 不必背下全部历史，顺着编号一路往下翻即可。

## 五、主动与全双工

### 投机执行

借 CPU 的**投机执行**思想：不确定会不会用上，先提前算好，用上就赚，用不上就扔。例：收到会议邀请，先在后台核对日程、查背景资料、备好回复草稿，你确认一下就能发。

**主动 ≠ 乱来**。在 DeepSeek 开源的原型里：

- 没人要求的主动工作，必须由团队**提前写好规则**才允许做；
- 默认先跑**观察模式**，只记录打算做什么，不真动手；
- 等你确认判断靠谱了再放开。

### 从对讲机到电话

ReAct Loop 是**半双工**的——像对讲机，同一时间只能一方说话，所以一干活就忽视新消息。Super Agent 要做**全双工**：把耗时工具调用改成**异步**，命令一启动就立刻返回，Agent 继续跟你聊天，结果跑完再作为一条新消息送回来。（素材提到该机制在很多 AI 工具中已经实现。）

### 分渠道说话

冗长的推理过程都关在 Worker 里，只有 Router 对外说话，且不同渠道有规矩：

- **飞书**：只在需要你拍板时才发消息，单次回复不超过 100 个词；
- **GitHub / 邮件**：写清问题背景、改动和验证结果。

## 六、持久化：存算分离 + BYOM

本地 Agent 把三样东西绑在同一台电脑上：**计算**、**会话状态**、**执行环境**。电脑一休眠，三样全部停摆。DeepSeek 借鉴存算分离，分两步拆开。

**第一步：计算与状态分离**

计算放在云端可随时替换的容器里，会话状态存进数据库。容器挂了换一个，记录一条不丢——像靠谱团队把工作记录放进档案室，谁来接班都能接着干。

**第二步：计算与执行环境分离**

代码、密钥、内网服务都在你本地，很难整体搬到云上。那就「环境搬不动就别搬」：**大脑留在云端**，本地只装一个很轻的 **Daemon**。它不保存会话记录，只按云端指令执行命令、回传结果——像远程专家指挥现场助手。

这就是 **BYOM（Bring Your Own Machine）**：带上你自己的电脑。笔记本今天没开机也没关系，重新上线后云端会自动把该在这台机器上做的事做完。

### Watchdog：看的是进展，不是存活

主系统之外单独配一个 **Watchdog（看门狗）会话**，相当于值班主管，定时巡查。它不只看员工在不在岗，更看**任务有没有进展**——因为 Agent 出问题很多时候程序没挂，而是模型在原地打转或跑偏。发现异常就及时介入修复。

## 七、效果与代价

据 DeepSeek 做的对比试验（素材转述，未见原始数据）：

- **速度**：Super Agent 比传统单对话 Agent **快一倍**，工作更稳定；
- **代价**：同时维护多个会话，读缓存的 token 是单会话方案的 **两倍到将近四倍**。

## 八、两个实例

1. **群里的需求**：用户提需求「正文、代码、终端的字体分开配置」，维护者 @ 了一下 Super Agent，它很快到 GitHub 提交改进代码，并根据群里追问和维护者在 GitHub 上的建议，一路推进到代码合并。
2. **自己发现的 bug**：从产品用户群里识别出 bug，自主在后台复现、找到根因，直接把修复代码和前后对比截图发出来——不用人催。

## 九、开放问题

DeepSeek 自己抛出的四个问题：

1. 任务规模继续变大，一个项目经理还够用吗？连续跑几个月，长期记忆怎么办？
2. 不再盯着会话之后，人该用什么方式跟 Agent 协作？聊天窗口还是最好的界面吗？
3. 每个人的私人助理与团队共用的 Super Agent 之间，如何在不泄露隐私的前提下配合？
4. Agent 越主动，接触的不可信信息越多，被**提示词注入**攻破怎么办？

> 讲者的个人判断：安全是 Agent 落地最大的一道坎——敢不敢让 AI 全天 24 小时盯群聊、操作你的电脑？一条恶意消息就可能把 AI 忽悠了。但他仍看好这个方向：它把一套成熟的团队管理方法搬进了 AI 世界。

## 附：一页速查

| 概念 | 一句话 |
|---|---|
| ReAct Loop | 想一步做一步看结果的单会话循环 |
| Super Agent | 跨会话记忆、并行多任务、互不干扰的连续工作者 |
| Router | 项目经理：常驻、沟通、派活，轻量模型 |
| Worker | 工程师：独立上下文、最强模型，可拉 sub agent |
| Trigger | 环境事件触发的入口（群消息、PR 评论、构建失败） |
| Fast / Slow path | 门卫按来源秒判；秘书用大模型读内容 |
| Thread | 同一 PR / 群话题 / 邮件串，Worker 订阅后直连 |
| Inline / Spill | 附上相关片段 / 只给摘要与指针 |
| Chain of Recall | 一切编号，卡片只留摘要与关联编号，顺藤摸瓜 |
| 全双工 | 工具调用异步化，边干活边聊天 |
| BYOM | 云端大脑 + 本地轻量 Daemon，环境不搬 |
| Watchdog | 独立看门会话，巡查任务进展而非仅存活 |
