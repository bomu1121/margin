# Super Agent 用路由层解绑单次会话

## 结论

它是把 Agent 从单次会话解绑成「项目经理加工程师」的项目团队架构。值得抄的是常驻的项目经理层接全局、工单订阅直达工程师、事件触发加两级过滤。不搬的是多会话带来的缓存 token 成本，以及没有团队规则就放开主动执行。

## 1. 它要解的问题

现在主流 Agent 以会话为工作单位：开一个会话布置一个任务，Agent 在想一步、做一步、看结果再想下一步的 ReAct Loop 里把活干完。单任务上这套很好用，所以流行了很久。问题出在同时有几件事要办：修 bug、写文档、跑测试各开一个会话，群里同事又来一句「这个需求改一下」，又得新开一个会话。会话之间不知道彼此在干什么，所有跨任务信息只能靠人记住再手动搬运，人不知不觉成了一群 AI 之间的传话筒。

视频里 DeepSeek 的判断是，单任务的上限取决于模型能力，多任务的上限取决于人的注意力。他们观察到，一个人通常只能同时跟进三到五个活跃会话，AI 越能干，人反而越累。那给 Agent 接上飞书、让它自己去群里看消息接任务行不行？借助 CLI 和 MCP 确实能做到，但只要底层还是单个会话，就会撞上三个卡点：执行耗时命令时整个循环卡住，命令跑完才能处理新消息；好几个需求塞进同一个会话，上下文越来越乱；Agent 跑在本地电脑上，电脑一休眠它就罢工。

所以它的判断不是「再做一个更强的单任务 Agent」，而是必须把 Agent 和单次会话解绑，让它变成能跨会话记住上下文、同时推进多件事、而且互不干扰的连续工作者。限定条件也在这里：单任务能力仍取决于模型，Super Agent 要补的是多任务下的连续性、主动性和持久性；不是所有任务都需要团队，单会话 ReAct 在单任务上并没有被否定。

## 2. 一条消息从进来到回你，经过谁

```figure
kind: flow
title: 一条群消息或 PR 事件如何到达 Worker
lines: 群消息/PR 评论/构建失败 -> 门卫按来源快筛 -> 秘书按规则读内容 -> 项目经理 Router 首次分派 -> 工程师 Worker 订阅工单 Thread 后直达
note: 首次过 Router，后续同一工单的消息不再经过 Router。
```

### Router 与 Worker：项目经理不干活，工程师决定交付

**职责**：Router 层是常驻的项目经理，接所有渠道消息、记住全局、跟你沟通、给工程师派活并统一回复；Worker 层是工程师，各自有独立上下文，专心干一件事，干完向项目经理汇报。

**怎么做**：视频用「招一个项目经理，再配几个工程师」解释这套分工。Router 不亲自干活，所以用轻量模型就够；真正决定交付质量的是 Worker，才需要配最强模型。所有消息都过 Router 会不会忙不过来？它的做法是批处理：项目经理处理上一批消息时，新消息先攒着，等他忙完再一起看、一起派活，消息越多平均处理反而越快。Worker 之间一般不直接沟通；两个 Worker 改同一个 PR，会同时收到这个 PR 的新动态，自己协调；任务太复杂，Worker 还能再拉几个 Sub Agent，相当于工程师自己带了实习生。

**失效时**：Router 是单点，批处理会带来延迟，紧急消息可能被攒住；多个 Worker 改同一 PR 只靠同时收到动态来协调，冲突时没有仲裁者；Sub Agent 拉得越多，上下文和汇报链越容易乱。

**原文说法**：「现实中的团队早就给出了解决方案，那就是招一个项目经理，再配几个工程师。」

### Trigger 与两级过滤：门卫看来源，秘书读内容

**职责**：把环境里发生的事情变成可处理的任务，而不是老板说一句才动一下。

**怎么做**：群里来了新消息、PR 下有人评论、代码构建失败，DeepSeek 把这些统一叫 Trigger，触发事件。可让 AI 直接盯群，废话太多；每条都让大模型判断要不要管，又慢又烧钱。它的办法是两级过滤：门口先有个门卫，后面再有个秘书。门卫只看消息从哪儿来，比如是不是监听的群、发消息的人在不在白名单，用普通代码就能秒判；秘书负责读内容，通过门卫的消息再交给大模型，由它按提示词里写好的规则判断要不要处理。这就是快慢路径：能用代码秒判的走快路径，需要读内容的走慢路径。

**失效时**：门卫按来源过滤，白名单外的紧急消息可能被挡；秘书的规则写死，新事件类型可能没人认领；规则过严会让 Agent 该管的也不管，规则过松则又回到每条都烧模型的老路。

**原文说法**：「门口先有个门卫，后面再有个秘书。」

### Thread 订阅：工单分给谁，后续消息直接抄送

**职责**：让同一件连续的事有归属，后续消息不再反复经过 Router。

**怎么做**：同一个 PR、同一个群话题、同一串邮件里的连续消息叫一个 Thread，可以理解为一个工单。现实团队里，一个工单第一次进来时经理把它分给小王，之后这个工单的消息直接抄送小王就行。Super Agent 也这样：首次由 Router 分派，Worker 接手后订阅这个工单，后续新消息由程序直接送到他手上，不再经过项目经理，省下大量 token。

**失效时**：话题跨 Thread、旧事在新工单里被提起时，订阅关系会断；同一工单被多个 Worker 订阅，协调又回到「自己看动态」；订阅状态过期或编号错，消息会漏接或重复分派。

**原文说法**：「一个工单第一次进来时，经理把它分给小王，之后这个工单的消息直接抄送小王就行。」

### 上下文与全双工：按编号召回，工具调用改异步

**职责**：给干活的 Worker 刚好够用的资料，并让 Agent 边干活边回消息。

**怎么做**：资料给多了重点被淹没，给少了 Worker 反复回头问。视频说「浪费上下文窗口就是浪费模型的智能」，于是借了编译器里的两个概念：inline 内联，像同事转消息时顺手附上前后几句聊天和相关工单号，让你一眼看懂来龙去脉；spill 溢出，像遇到几万字文档只给摘要和一句「完整内容见这里」，需要时再去翻。用到整个系统里就是链式召回：每条消息、每个工单、每个 Worker 都编号，每张卡片只写摘要和关联编号，跨平台提起旧事时顺着编号一路往下翻，像侦探找线索。它还把 CPU 里的投机执行搬过来：收到会议邀请，先在后台核对日程、查背景资料、备好回复草稿，你确认一下就能发。工具调用则改成异步：命令一启动立刻返回，Agent 可以继续聊天，结果跑完再作为新消息送回来，把半双工的对讲机换成全双工的电话。渠道表达也收敛：飞书里只在需要你拍板时发消息，单次回复不超过一百个词；GitHub 邮件里写清问题背景、改动和验证结果。

**失效时**：摘要和编号一旦断链，Worker 会反复问或答错旧事；投机执行可能白算；异步结果回来时任务状态已变，需要合并和过期判断；渠道压缩过度会丢掉关键上下文。

**原文说法**：「把对讲机换成电话，也就是全双工。」

### 执行环境与看门狗：存算分离、BYOM、值班主管

**职责**：让 Agent 不随本地电脑休眠而下班，并在它跑偏时介入。

**怎么做**：本地 Agent 把计算、会话状态、执行环境绑在同一台电脑上，电脑一休眠三样全停。它借存算分离分两步拆：第一步，计算放云端可随时替换的容器，会话状态存数据库，容器挂了换一个，记录不丢；第二步，计算和执行环境分开，代码、密钥、内网服务搬不上云，那就不搬，大脑留在云端，本地只装一个很轻的 Daemon，不保存会话记录，只按云端指令执行命令、回传结果，像远程专家指挥现场的助手，这叫 BYOM，带上你自己的电脑。主系统外还配一个 Watchdog 看门狗会话，相当于值班主管，定时巡查，不只看员工在不在岗，更看任务有没有进展；Agent 出问题很多时候程序没挂，而是模型原地打转或跑偏。

**失效时**：网络断或笔记本没开机，云端只能等它重新上线；容器替换会丢内存态；Watchdog 自己也可能误判，修复动作本身需要权限边界；密钥和内网仍在本地，云端指令一旦被注入，信任边界比纯本地更复杂。

**原文说法**：「大脑留在云端，你的电脑上只装一个很轻的小程序。」

## 3. 它放弃了什么

- 放弃「所有消息都由 Router 逐条判断」：换来门卫秒判和批处理吞吐，代价是新来源、新事件类型可能卡在门卫或秘书规则外，需要人工补规则。
- 放弃「每个任务一个完全独立会话」：Thread 订阅让后续消息直达 Worker，省 Router token，但同一工单多 Worker 订阅时冲突要靠 PR 动态自己协调，协调失败没人仲裁。
- 放弃「把完整历史塞进上下文」：inline/spill/链式召回省窗口，代价是摘要和编号一旦断链，Worker 会反复回头问或答错旧事。
- 放弃「同步 ReAct 的简单顺序」：异步工具调用换来边干活边聊天，代价是结果回来时任务状态可能已变，需要额外的合并与过期判断。
- 放弃「Agent 必须跑在本地电脑」：云端容器加数据库换来持久，代价是依赖网络和本地 Daemon，密钥、内网服务仍在本地，信任边界更复杂。

## 4. 数字与口径

- 视频口播的 DeepSeek 对比实测：Super Agent 比传统单对话 Agent「速度快了一倍」，工作更稳定；没有给任务集、硬件、延迟定义和重复次数，不能当基准测试。
- 同一对比里，Super Agent 读缓存的 token 是单会话方案的「两倍到将近四倍」；这是代价在涨的那一项，说明并行和全局记忆不是免费。
- 视频用「一个人通常只能同时跟进三到五个活跃会话」解释旧模式瓶颈；这是经验口径，不是压测容量。
- 飞书渠道规定单次回复「不超过一百个词」；这是表达约束，不是性能指标，目的是不让群消息炸掉。
- 举例说手里同时有「二十件事」要处理；这是用来说明为什么需要项目经理加工程师分层，不是系统容量承诺。

## 5. 落地时先做什么

- 接入事件入口与两级过滤：触发条件 群消息、PR 评论、构建失败等事件已能稳定入站；最小改动 先用来源白名单做快路径，只把通过门卫的消息交给模型读内容；成功判据 每条进入模型的消息都有判定理由，误报和漏报能逐条复盘。
- 把连续消息收成 Thread 并直达 Worker：触发条件 同一 PR、群话题或邮件串出现连续消息；最小改动 首次由 Router 分派，后续消息按订阅直接送给已接手的 Worker；成功判据 Router 转发量下降，同时同一工单不漏接、不重复分派。
- 主动工作先跑观察模式：触发条件 团队已有书面规则、白名单和可回滚动作；最小改动 只记录打算做什么，不真正执行；成功判据 人工确认判断靠谱后，再按动作类型逐项放开。

## 6. 明确不做什么

- 不要把所有消息直接丢给大模型判断：门卫能用普通代码秒判来源，先过滤再读内容才不慢不烧钱。
- 不要让 Worker 之间自由群聊：同一 PR 的新动态会同时到达，各自协调即可，额外通信只会增加上下文和冲突。
- 不要把主动执行默认打开：没人要求的主动工作必须有提前写好的团队规则，先观察再放开。

## 7. 还没答案的问题

- Router 单点扩容：任务规模继续变大、连续跑上几个月时，全局记忆如何分片或归档，批处理延迟与召回准确性怎么权衡？
- 人机界面：不再盯着会话之后，拍板、追问、审计应该落在哪个渠道和什么消息粒度上？
- 隐私边界：个人助理与团队共用的 Super Agent 之间，如何在不泄露隐私的前提下交换任务状态？
- 提示词注入：Agent 越主动接触的不可信信息越多，门卫、秘书、Worker 哪一层做信任隔离，工具权限如何最小化？

## 8. 术语 ↔ 它在系统里的位置

- **Session（会话）** → 旧模式的工作单位，一个任务一个循环，Super Agent 要把它和 Agent 解绑。
- **ReAct Loop** → 想一步、做一步、看结果再想下一步的循环，半双工卡点就出在这里。
- **Router 层** → 常驻的项目经理，接所有渠道消息、记全局、派活、统一回复。
- **Worker 层** → 独立上下文的工程师，真正干活并向 Router 汇报。
- **Trigger** → 环境里发生的事，如群消息、PR 评论、构建失败，驱动 Agent 而不是老板说一句才动。
- **Thread** → 同一 PR、群话题或邮件串的连续消息，相当于工单，Worker 订阅后直达。
- **fast path / slow path** → 门卫用代码秒判来源，秘书用模型读内容，两级过滤的两种路径。
- **inline / spill / chain of recall** → 上下文按摘要加编号组织，需要时顺编号召回，省窗口。
- **BYOM 与 Daemon** → 云端大脑加本地轻量执行器，环境不搬，只按指令执行并回传。
- **Watchdog** → 主系统外的值班主管会话，定时巡查任务有没有进展，发现打转或跑偏就介入。

## 9. 出处与边界

- 本文结论来自视频口播对 DeepSeek Harness 团队「Super Agent」原文的二手转述；未核对原文措辞，具体模块命名以口播为准。
- 对比数字只有「速度快了一倍、读缓存 token 两倍到将近四倍」的口播结论，没有任务集、硬件、延迟定义和统计口径，不能当基准测试。
- 「三到五个活跃会话」「二十件事」「一百个词」是视频里的经验或约束口径，不是容量承诺或 SLA。
- Claude Code、CodeX、DeepSeek Harness 在视频里是作为现有会话式 Agent 的同类参照，不是 Super Agent 的同源实现。
- 开源原型、观察模式、团队规则等细节来自视频对原型的描述；仓库名、链接、日期视频未给，本文不补。
