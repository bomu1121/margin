# Super Agent：把“一个外包”换成“一个项目团队”

> 素材来源：一期介绍 DeepSeek Harness 团队提出的 Super Agent 架构的讲解。原文术语很多，这篇笔记按“为什么需要 → 它是什么 → 怎么搭起来 → 代价与开放问题”的顺序重排了一遍。

---

## 一、先说清楚现在的 Agent 是怎么干活的

不管是 Claude Code、CodeX 还是 DeepSeek Harness，主流 Agent 都以**会话（session）**为单位工作：你开一个会话布置一个任务，它在这个会话里“想一步—做一步—看结果—再想下一步”，直到干完。这个循环叫 **React Loop**。

单看一个任务，这个模式很好用，所以流行了很久。问题出在**同时有好几件事要办**的时候：

- 开一个会话修 bug，一个会话写文档，一个会话跑测试；
- 群里同事一句“这个需求改一下”，又得新开一个会话；
- 这些会话互相不知道对方在干什么，跨任务的信息只能靠你自己记住、手动搬运。

不知不觉，你成了一群 AI 之间的**传话筒**。

用 DeepSeek 官方的话说：**单任务的上限取决于模型能力，多任务的上限取决于人的注意力。** 他们观察到，一个人通常只能同时跟进三到五个活跃会话——AI 越来越能干，人反而越来越累。

### 给 Agent 接上飞书、让它自己去群里接任务，行不行？

借助 CLI 和 MCP 确实能做到，但只要底层还是单个会话，很快会撞上三个问题：

1. 执行耗时命令时，整个循环卡住，命令跑完才能处理新消息；
2. 好几个需求塞进同一个会话，上下文越来越乱；
3. Agent 跑在你的本地电脑上，电脑一休眠它就罢工。

所以 DeepSeek 的结论是：**必须把 Agent 和单次会话解绑**，让它变成一个能跨会话记住上下文、同时推进多件事、而且互不干扰的连续工作者——这就是 Super Agent。

---

## 二、Super Agent 是什么

一个类比：

- 传统 Agent = 一次只能干一件事的**外包**；
- Super Agent = 一个配合默契的**项目团队**：团队内部可能有很多人，但你只需要和一个对接人打交道。

### 四个基础特征

| 特征 | 含义 |
|---|---|
| **连续** | 在飞书群还是 GitHub 跟它聊都行。你在群里说用方案 A，后来在 PR 里改成方案 B，它也能跟上 |
| **高效** | 能同时推进好几件事，上一件没干完也能接下一条指令 |
| **主动** | 自己盯着群消息和工单，该处理的主动处理，不该管的保持安静 |
| **持久** | 一直在线，出了问题还能自己恢复 |

### 两个真实例子

- 有用户在群里提需求，希望正文、代码、终端的字体能分开配置。维护者 @ 了一下 Super Agent，它很快到 GitHub 提交了改进代码，并根据用户在群里的追问、维护者在 GitHub 上提的建议，一路把需求推进到代码合并。
- 它甚至能自己从产品用户群里识别出 bug，在后台自主复现、找到根因，直接把修复代码和前后对比截图发出来。

也就是说：**你都不用催，该干的活它自己就干了。**

## 三、架构：招一个项目经理，配几个工程师

先看两难：假设你手里同时有二十件事。

- 全交给一个人 → 信息不会断，但只能排队一件件做；
- 每件事都找个新人 → 能同时开工，但互相不同步信息，最后还要一人一嘴来找你汇报，很混乱。

连续性和速度怎么选？DeepSeek 说：我全都要。现实团队的答案早就有——**招一个项目经理，再配几个工程师。**

### 1. Router 层 + Worker 层

Super Agent 分上下两层：

- **上层 Router 层 = 项目经理**：常驻在线，所有渠道的消息先到它这里，由它记住全局、跟你沟通、给工程师派活。
- **下层 Worker 层 = 工程师**：每个 worker 有自己独立的上下文，专心干好一件事，干完向项目经理汇报，再由项目经理统一回复你。

于是你面对的始终是同一个对接人，团队内部怎么分工你根本不用关心。

**模型配置也随之分工**：router 不亲自干活、只负责沟通和派活，用轻量模型就够；真正决定交付质量的是 worker，它才需要配最强的模型。

### 2. 项目经理会不会忙不过来？——批处理

实践中 DeepSeek 发现问题不大：经理处理上一批消息时，新消息先攒着，等他忙完再一起看、一起派活。采用批处理机制后，**消息越多，平均处理得反而越快**。

worker 之间一般不直接沟通。如果两个 worker 在改同一个 PR，它们会同时收到这个 PR 的新动态，自己就能协调好。任务太复杂时，worker 还能再拉几个 sub agent 帮忙——相当于工程师自己带了实习生。

### 3. 从“你说一句它动一下”到“事件驱动”

传统 Agent 是你说一句才干一次活；Super Agent 由**环境里发生的事**驱动：群里来了新消息、PR 下有人评论、代码构建失败了……DeepSeek 把这些事件统一叫做 **trigger（触发事件）**。

但群里的废话实在太多，每条消息都丢给大模型判断要不要管，又慢又烧钱。于是有了**两级过滤**（门卫 + 秘书）：

- **门卫**：只看消息从哪儿来——是不是监听的群、发消息的人在不在白名单——用普通代码就能秒判；
- **秘书**：负责读内容，通过门卫的消息才交给大模型，由它按提示词里写好的规则判断要不要处理。

这就是计算机系统里的**快慢路径**（fast path / slow path）思想。

### 4. 工单式订阅：让消息不再都经过经理

如果每条消息都要经理转一手，它压力也很大。现实中的团队，一个工单第一次进来时经理分给小王，之后这个工单的消息就直接抄送小王。

Super Agent 同理：同一个 PR、同一个群话题、同一串邮件里的连续消息叫作一个 **thread**，可以理解为一个工单。Worker 接手后**订阅**这个工单，后续新消息由程序直接送到它手上，不再经过项目经理，**能节省大量 tokens**。

### 5. 该给干活的人看多少资料：inline / spill 与链式召回

资料给多了重点被淹没，给少了干活的人得反复回头问。DeepSeek 的判断是：**浪费上下文窗口就是浪费模型的智能。** 他们借用了编译器里的两个概念：

- **inline 内联**：像同事转消息时顺手附上前后几句聊天和相关工单号，让你一眼看懂来龙去脉；
- **spill 溢出**：像遇到一份几万字的文档，只给你摘要加一句“完整内容见这里”，需要时再去翻。

放到整个系统里，就有了**链式召回（chain of recall）**：系统给每条消息、每个工单、每个 worker 都编了号，每张卡片上只写摘要和关联编号。你跨平台提起一件旧事时，项目经理不用把历史记录全背下来，顺着编号一路往下翻就行——像侦探找线索。

### 6. 投机执行：先替你备好，你再点头

计算机里的**投机执行**是：CPU 不确定某段计算用不用得上时先提前算好，用上了就赚，用不上就扔掉。Super Agent 把它用在干活上：比如你收到一封会议邀请，它先在后台核对日程、查好背景资料、备好回复草稿，你确认一下就能直接发。

**但主动不等于乱来**：在 DeepSeek 开源的原型里，没人要求的主动工作必须有团队提前写好的规则才能做；而且默认先跑**观察模式**——只记录自己打算做什么，并不真的动手；等你确认它的判断靠谱了再放开。

### 7. 从半双工到全双工：边干活边聊天

传统 Agent 一干活就忽视新消息，原因是 React Loop 是**半双工**的——像对讲机，同一时间只能一方说话。Super Agent 要把它换成电话，也就是**全双工**：把耗时的工具调用改成异步，命令一启动就立刻返回，Agent 可以继续跟你聊天，等命令跑完，结果再作为一条新消息送回来。

（这个机制其实在很多 AI 工具里都已经实现了。）

### 8. 不同渠道说不同的话

如果把终端里长篇大论的思考过程原样发到群里，群消息估计要炸。好在冗长的推理过程都关在了 worker 里，只有项目经理对外说话。DeepSeek 还给不同渠道定了规矩：

- **飞书**：只在需要你拍板时才发消息，单次回复不超过一百个词；
- **GitHub / 邮件**：要写清楚问题背景、改动和验证结果。

### 9. 存算分离：让 Agent 不下班

本地 Agent 把三样东西绑在同一台电脑上：**计算**（干活）、**状态**（会话记录）、**执行环境**（代码、工具）。电脑一休眠，三样全部停摆。

DeepSeek 借鉴存算分离，分两步拆开：

- **第一步，计算与状态分开**：像靠谱的团队把工作记录放进档案室，谁来接班都能接着干。计算放在云端可随时替换的容器里，会话状态存进数据库；容器挂了换一个就行，记录一条都不会丢。
- **第二步，计算与执行环境分开**：Agent 上了云，可代码、密钥、内网服务都还在你电脑上，很难完整搬上云。DeepSeek 的办法是——**环境搬不动就别搬了**。大脑留在云端，你的电脑上只装一个很轻的小程序 **Daemon**：它不保存会话记录，只按云端指令执行命令、回传结果，像远程专家指挥现场助手。

这套思路叫 **BYOM（Bring Your Own Machine，带上你自己的电脑）**。哪怕笔记本今天没开机，等它重新上线，云端也会自动把该在这台电脑上做的事做完。

### 10. Watchdog：值班主管

主系统外面单独配一个 **Watchdog（看门狗）会话**，相当于值班主管，定时巡查。它不光看员工在不在岗，更要看**任务有没有进展**——因为 Agent 出问题很多时候程序并没有挂，而是模型在原地打转或者跑偏了。一旦发现异常，它及时介入修复。

## 四、效果与代价

- **效果**：据 DeepSeek 做的对比测试，Super Agent 相比传统单对话 Agent **速度快了一倍，而且工作更稳定**。
- **代价**：因为要同时维护多个会话，Super Agent 读缓存的 token 是单会话方案的**两倍到将近四倍**。

有利有弊。

---

## 五、DeepSeek 自己抛出的四个开放问题

1. 任务规模继续变大，一个项目经理还够用吗？连续跑上几个月，长期记忆怎么办？
2. 不再盯着会话之后，人该用什么方式跟 Agent 协作？聊天窗口还是最好的界面吗？
3. 每个人的私人助理和团队共用的 Super Agent 之间，怎么在不泄露隐私的前提下互相配合？
4. Agent 越主动，接触的不可信信息就越多，万一被提示词注入攻破了怎么办？

---

## 六、讲者的看法

- **安全是 Agent 工作最大的一道坎**：敢不敢让 AI 全天二十四小时盯着群聊、操作你的电脑？万一来了条恶意消息把 AI 忽悠了，你的数据和隐私怎么办？
- 但整体仍然很看好这个项目——它算是**把一套成熟的团队管理方法搬进了 AI 的世界**。感兴趣的话可以到 GitHub 上看这套研究原型。

## 一页速记

```
问题：单会话 React Loop → 卡命令 / 上下文乱 / 本机休眠就罢工
答案：Super Agent = 解绑会话的连续工作者
     ├ router（项目经理，轻量模型，只沟通派活，批处理）
     └ worker（工程师，独立上下文，强模型，可再拉 sub agent）
特征：连续 · 高效 · 主动 · 持久
机制：
  trigger 事件驱动 → 门卫(代码秒判) + 秘书(大模型读内容) 两级过滤
  thread 工单订阅 → 后续消息绕过经理，省 tokens
  inline / spill + 链式召回编号 → 省上下文窗口
  投机执行 → 先备好草稿，你确认即发（默认观察模式）
  半双工 → 全双工（工具调用异步化）
  渠道规矩：飞书 ≤100 词且只在拍板时发；GitHub/邮件写清背景+改动+验证
  存算分离 → 计算/状态分开，计算/执行环境分开 → Daemon + BYOM
  Watchdog 值班主管 → 看任务有没有进展，不只看进程活没活
结果：快一倍、更稳定；代价是读缓存 token 为 2~4 倍
未解：长期记忆 · 人机协作界面 · 隐私协同 · 提示词注入
```
