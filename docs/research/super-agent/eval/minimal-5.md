# Super Agent：把「一个外包」升级成「一个项目团队」

> 素材来源：关于 DeepSeek Harness 团队提出的 Super Agent 架构的解读。原文未说明对应的正式论文/文档标题与链接。

## 一句话结论

传统 Agent 的问题不在模型不够聪明，而在**被单个会话 session 绑死**：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。Super Agent 的思路是把 Agent 与单次会话解绑，变成一个能跨会话记住上下文、同时推进多件事、彼此互不干扰的连续工作者。

## 现在的 Agent 怎么干活，卡在哪

主流 Agent（Claude Code、CodeX、DeepSeek Harness 等）都以会话为单位：开一个会话，布置一个任务，Agent 在这个会话里「想一步 → 做一步 → 看结果 → 再想下一步」直到干完，这个循环叫 **ReAct Loop**。

单任务很好用，但多任务时人变成了瓶颈：修 bug 一个会话、写文档一个会话、跑测试一个会话，同事群里说「这个需求改一下」又要新开一个。会话之间互不知情，跨任务信息只能靠人记住再手动搬运——你成了一群 AI 之间的传话筒。

据官方观察，一个人通常只能同时跟进 **三到五个** 活跃会话。AI 越来越能干，人反而越来越累。

### 给 Agent 接上飞书 / MCP 行不行？

用 CLI 和 MCP 确实能接，但只要底层还是单个会话，就会撞上三个问题：

1. **阻塞**：执行耗时命令时整个循环卡住，命令跑完才能处理新消息。
2. **混乱**：多个需求塞进同一个会话，上下文越来越乱。
3. **掉线**：Agent 跑在本地电脑上，电脑一休眠就罢工。

## 四个基础特征

传统 Agent 像一次只能干一件事的外包；Super Agent 像一个配合默契的项目团队——团队里有很多人，但你只需要和一个对接人打交道。

| 特征 | 含义 |
| --- | --- |
| 连续 | 在飞书群或 GitHub 跟它聊都行；群里说用方案 A，后来在 PR 里改成方案 B，它也能跟上 |
| 高效 | 同时推进好几件事，上一件没干完也能接下一条指令 |
| 主动 | 自己盯着群消息和工单，该处理的处理，不该管的保持安静 |
| 持久 | 一直在线，出了问题还能自己恢复 |

### 内部真实运行的例子

- 用户在群里提需求（正文、代码、终端字体分开配置），维护者 @ 了一下 Super Agent，它很快到 GitHub 提交改进代码，并根据群里追问和 PR 上的建议，一路推进到代码合并。
- 它也能自己从产品用户群里识别出 bug，在后台复现、找到根因，直接发出修复代码和前后对比截图——不用人催。

## 架构：一位项目经理 + 若干工程师

假设你手上有二十件事：全交给一个人，信息不断但只能排队做；每件事找个新人，能并行但互相不同步、汇报混乱。DeepSeek 的选择是「我全都要」——上层 **router 层** 当项目经理，下层 **worker 层** 当工程师。

- **router 层**：常驻在线，所有渠道的消息先到这里，负责记全局、跟你沟通、给工程师派活。它不亲自干活，所以用**轻量模型**就够。
- **worker 层**：每个 worker 有独立上下文，专心干一件事，干完向项目经理汇报，由项目经理统一回复你。**决定交付质量的是 worker**，最强模型配在这里。

好处是你面对的始终是同一个对接人，团队内部怎么分工你不用关心。

**项目经理会不会忙不过来？** 实践中发现问题不大：处理上一批消息时新消息先攒着，忙完再一起看、一起派活。这种批处理机制下，消息越多，平均处理反而越快。

worker 之间一般不直接沟通。两个 worker 改同一个 PR 时会同时收到该 PR 的新动态，自己协调；任务太复杂时，worker 还能再拉几个 **sub agent** 帮忙，相当于工程师自己带实习生。

## 从「你说一句它动一下」到事件驱动

传统 Agent 是人推一下才动一次；Super Agent 由环境里发生的事驱动：群里来了新消息、PR 下有人评论、代码构建失败……这些事件统称 **trigger（触发事件）**。

### 两级过滤：门卫 + 秘书

让 AI 直接盯群消息，废话太多；每条都过大模型判断又慢又烧钱。DeepSeek 的办法是快慢路径（fast path / slow path）：

1. **门卫（快路径）**：只看消息从哪儿来——是不是监听的群、发消息的人在不在白名单。普通代码就能秒判。
2. **秘书（慢路径）**：过门卫的消息再交给大模型，按提示词里写好的规则判断要不要处理。

### thread：让后续消息直达 worker

每条消息都经项目经理转一手，压力还是大。现实团队的做法是：工单第一次进来时经理分给小王，之后的该工单消息直接抄送小王。

Super Agent 里，同一个 PR、同一个群话题、同一串邮件里的连续消息构成一个 **thread**（可理解为一个工单）。worker 接手后订阅该工单，后续新消息由程序直接送到他手上，不再经过项目经理，**节省大量 tokens**。

## 上下文管理：inline、spill 与链式召回

资料给多了重点被淹没，给少了干活的人反复回头来问。DeepSeek 的判断是：**浪费上下文窗口就是浪费模型的智能**。借鉴编译器里的两个概念：

- **inline（内联）**：像同事转消息时顺手附上前后几句聊天和相关工单号，一眼看懂来龙去脉。
- **spill（溢出）**：几万字的文档只给摘要和一句「完整内容见这里」，需要时再去翻。

用到整个系统里就成了 **链式召回（chain of recall）**：系统给每条消息、每个工单、每个 worker 都编号，每张卡片上只写摘要和关联编号。你跨平台提起一件旧事，项目经理不用背下全部历史，顺着编号一路往下翻即可——像侦探找线索。

## 主动工作，但有边界

借用 CPU 的**投机执行**思想：不确定会不会用上，先提前算好，用上就赚了，用不上就扔掉。例如收到会议邀请，先在后台核对日程、查背景资料、备好回复草稿，你确认一下就能直接发。

但主动不等于乱来。在 DeepSeek 开源的原型里：

- 没人要求的主动工作，必须有团队**提前写好的规则**才能做；
- 默认先跑**观察模式**，只记录自己打算做什么，并不真的动手，等你确认判断靠谱了再放开。

## 半双工 → 全双工

传统 Agent 一干活就忽视新消息，因为 ReAct Loop 是**半双工**的——像对讲机，同一时间只能一方说话。Super Agent 要把对讲机换成电话：把耗时的工具调用改成**异步**，命令一启动就立刻返回，Agent 可以继续跟你聊天，命令跑完结果再作为一条新消息送回来。这个机制在很多 AI 工具里已经实现了。

### 分渠道的说话方式

冗长的推理过程都关在 worker 里，只有项目经理对外说话，且不同渠道有不同规矩：

| 渠道 | 规矩 |
| --- | --- |
| 飞书 | 只在需要你拍板时发消息，单次回复不超过一百个词 |
| GitHub / 邮件 | 写清楚问题背景、改动和验证结果 |

## 持久化：存算分离与 BYOM

本地 Agent 把三样东西绑在同一台电脑上：负责干活的计算、会话记录等状态、代码与工具等执行环境。电脑一休眠，三样全停摆。DeepSeek 借鉴存算分离，分两步拆：

1. **计算与状态分开**：计算放在云端可随时替换的容器里，会话状态存进数据库。容器挂了换一个，记录一条不丢——像团队把工作记录放进档案室，谁来接班都能接着干。
2. **计算与执行环境分开**：代码、密钥、内网服务很难整体搬到云端，那就不搬。大脑留在云端，你电脑上只装一个很轻的 **Daemon**，它不保存会话记录，只按云端指令执行命令、回传结果——像远程专家指挥现场助手。这套叫 **BYOM（Bring Your Own Machine）**，带上你自己的电脑。笔记本今天没开机也没关系，重新上线后云端会自动把该在这台电脑上做的事做完。

## 看门狗：盯进展，不只看存活

主系统之外单独配一个 **Watchdog** 会话，相当于值班主管，定时巡查。它不只看员工在不在岗，更看**任务有没有进展**——因为 Agent 出问题很多时候程序没挂，而是模型在原地打转或者跑偏。发现异常就及时介入修复。

## 代价与开放问题

据 DeepSeek 做的对比试验，Super Agent 相比传统单对话 Agent **速度快了一倍**，工作也更稳定；代价是同时维护多个会话，**读缓存的 token 是单会话方案的两倍到将近四倍**。

原文抛出的开放问题：

1. 任务规模继续变大，一个项目经理还够用吗？连续跑上几个月，长期记忆怎么办？
2. 不再盯着会话之后，人该用什么方式跟 Agent 协作？聊天窗口还是最好的界面吗？
3. 每个人的私人助理和团队共用的 Super Agent 之间，如何在不泄露隐私的前提下互相配合？
4. Agent 越主动，接触的不可信信息越多，被提示词注入攻破怎么办？

原文作者认为，**安全是 Agent 落地最大的一道坎**：敢不敢让 AI 全天 24 小时盯群聊、操作你的电脑？一条恶意消息把 AI 忽悠了，数据和隐私怎么办。

## 我的理解

这套架构真正新鲜的地方不是模型，而是把一套成熟的团队管理方法搬进了 AI 世界：分层（经理/工程师）、分派（thread 订阅）、汇报线（统一对接人）、风控（两级过滤 + 看门狗 + 观察模式）。工程上它更像一次系统设计——上下文、并发、持久化、安全，每一条都是老问题在新场景下的重演。
