# Super Agent：把 AI 从「会话外包」变成「项目团队」

## 结论

DeepSeek Harness 团队提出的 Super Agent，核心是把 Agent 与单次会话解绑：它不再是「你说一句它干一件」的外包，而是一个能跨会话记住上下文、同时推进多件事、互不干扰的连续工作者。它用「项目经理 + 工程师」的两层结构，换来了速度与连续性，代价是更高的 token 消耗和尚未解决的安全问题。

## 问题：单会话 Agent 的天花板

主流 Agent（Claude Code、CodeX、DeepSeek Harness）都以 session 为单位干活：你在一个会话里布置任务，Agent 想一步、做一步、看结果、再想下一步，这个循环叫 ReAct loop。单任务好用，但多任务时问题就来了。

你开一个会话修 bug、一个写文档、一个跑测试，同事在群里说「需求改一下」，又得新开一个会话。这些会话互相不知道对方在干什么，跨任务信息只能靠人记住再手动搬运——你成了一群 AI 之间的传话筒。

DeepSeek 的观察是：**单任务的上限取决于模型能力，多任务的上限取决于人的注意力**，一个人通常只能同时跟进三到五个活跃会话。

给 Agent 接上飞书、靠 CLI 和 MCP 去群里接任务，只要底层还是单会话，就会撞上三个问题：

1. 执行耗时命令时整个循环卡住，命令跑完才能处理新消息；
2. 多个需求塞进同一会话，上下文越来越乱；
3. Agent 跑在本地电脑上，电脑一休眠就罢工。

## 四个基础特征

| 特征 | 含义 |
| --- | --- |
| 连续 | 在飞书群或 GitHub 都能聊；群里说用方案 A，后来在 PR 里改成方案 B，它也能跟上 |
| 高效 | 同时推进好几件事，上一件没干完也能接下一条指令 |
| 主动 | 自己盯着群消息和工单，该处理的处理，不该管的保持安静 |
| 持久 | 一直在线，出了问题能自己恢复 |

## 真实案例

- 有用户在群里提需求，希望正文、代码、终端的字体能分开配置。维护者 @ 了一下 Super Agent，它很快到 GitHub 提交了改进代码，并根据用户在群里的追问和维护者在 GitHub 上的建议，一直把需求推进到代码合并。
- Super Agent 还能从产品用户群里自主识别 bug，在后台复现、找到根因，直接把修复代码和前后对比截图发出来。

## 架构：项目经理 + 工程师

如果二十件事全交给一个人，信息不断但只能排队做；每件事找新人，能并行但互不同步、汇报混乱。DeepSeek 的方案是招一个项目经理，再配几个工程师。

- **router 层（项目经理）**：常驻在线，所有渠道消息先到它这里，由它记住全局、跟你沟通、给工程师派活。它不亲自干活，所以用轻量模型就够了。
- **worker 层（工程师）**：每个 worker 有独立上下文，专心干一件事，干完向项目经理汇报，再由项目经理统一回复你。决定交付质量的是 worker，它才需要配最强模型。

你面对的始终是同一个对接人，团队内部怎么分工不用你关心。

**项目经理会不会忙不过来？** 实践中问题不大：它处理上一批消息时，新消息先攒着，忙完再一起看、一起派活。采用批处理机制后，消息越多，平均处理反而越快。

worker 之间一般不直接沟通；如果两个 worker 在改同一个 PR，会同时收到该 PR 的新动态，自己协调。任务太复杂时，worker 还能再拉几个 sub agent 帮忙——相当于工程师自己带了实习生。

## 事件驱动：两级过滤与 Thread 直达

传统 Agent 是你说一句才干一次；Super Agent 由环境里发生的事驱动，比如群里来了新消息、PR 下有人评论、代码构建失败。DeepSeek 把这些事件统一叫 **trigger**。

但群里的废话太多，每条都让大模型判断又慢又烧钱。DeepSeek 的办法是两级过滤：

- **门卫（fast path）**：只看消息从哪来——是不是监听的群、发消息的人在不在白名单，用普通代码秒判。
- **秘书（slow path）**：通过门卫的消息才交给大模型，由它按提示词里写好的规则判断要不要处理。

这就是计算机系统里的快慢路径思想。

分配任务也有省 token 的做法。同一个 PR、同一个群话题、同一串邮件里的连续消息，叫做一个 **thread**，可以理解为一个工单。工单第一次进来时由项目经理分给某个 worker，之后这个工单的新消息由程序直接送到该 worker 手上，不再经过项目经理。

## 上下文管理：inline、spill 与链式召回

资料给多了重点被淹没，给少了干活的人反复回头问。DeepSeek 的原则是：**浪费上下文窗口就是浪费模型的智能**。它借用了编译器里的两个概念：

- **inline（内联）**：像同事转消息时顺手附上前后几句聊天和相关工单号，让人一眼看懂来龙去脉。
- **spill（溢出）**：遇到几万字文档，只给摘要和一句「完整内容见这里」，需要时再去翻。

用到整个系统上就是**链式召回（chain of recall）**：给每条消息、每个工单、每个 worker 编号，每张卡片只写摘要和关联编号。跨平台提起旧事时，项目经理不必背下全部历史，顺着编号一路往下翻即可，像侦探找线索。

## 主动性与安全阀

Super Agent 借鉴了 CPU 的**投机执行**：不确定某段计算会不会用上，先提前算好，用上就赚了，用不上就扔掉。比如收到会议邀请，它先在后台核对日程、查好背景资料、备好回复草稿，你确认一下就能发。

主动不等于乱来。在 DeepSeek 开源的原型里：没人要求的主动工作必须有团队提前写好的规则才能做；而且默认先用**观察模式**，只记录自己打算做什么，并不真的动手，等你确认它的判断靠谱了再放开。

## 全双工与渠道表达

传统 Agent 一干活就忽视新消息，因为 ReAct loop 是半双工的，像对讲机，同一时间只能一方说话。Super Agent 要换成电话，也就是**全双工**：把耗时的工具调用改成异步，命令一启动就立刻返回，Agent 可以继续跟你聊天，命令跑完结果再作为一条新消息送回来。这个机制在很多 AI 工具中已经实现。

能边干活边聊天之后，还要注意不同渠道的说话方式。冗长的推理过程都关在 worker 里，只有项目经理对外说话，而且 DeepSeek 给不同渠道定了规矩：

- **飞书**：只在需要你拍板时才发消息，单次回复不超过一百个词。
- **GitHub / 邮件**：写清楚问题背景、改动和验证结果。

## 存算分离与 Watchdog：让 Agent 不下班

本地 Agent 把三样东西绑在同一台电脑上：负责干活的计算、会话记录这些状态、代码与工具这些执行环境。电脑一休眠，三样全部停摆。DeepSeek 借鉴存算分离，分两步拆开：

1. **计算与状态分离**：计算放在云端可随时替换的容器里，会话状态存进数据库；容器挂了换一个，记录一条不丢。
2. **计算与执行环境分离**：代码、密钥、内网服务很难完整搬到云端，那就不搬。大脑留在云端，你的电脑上只装一个很轻的小程序 **Daemon**，它不保存会话记录，只按云端指令执行命令、回传结果——像远程专家指挥现场的助手。

DeepSeek 管这叫 **BYOM（Bring Your Own Machine）**，带上你自己的电脑。哪怕笔记本今天没开机，等它重新上线，云端也会自动把该在这台电脑上做的事做完。

主系统之外还单独配了一个 **Watchdog** 看门狗会话，相当于值班主管，定时巡查。它不只看员工在不在岗，更看任务有没有进展——因为 Agent 出问题很多时候程序并没挂，而是模型在原地打转或者跑偏。发现异常，它会及时介入修复。

## 效果与代价

根据 DeepSeek 做的对比试验：Super Agent 相比传统单对话 Agent **速度快了一倍**，工作也更稳定；代价是同时维护多个会话，**读缓存的 token 是单会话方案的两倍到将近四倍**。

## 开放问题

1. 任务规模继续变大，一个项目经理还够用吗？连续跑上几个月，长期记忆怎么办？
2. 不再盯着会话之后，人该用什么方式跟 Agent 协作？聊天窗口还是最好的界面吗？
3. 每个人的私人助理和团队共用的 Super Agent 之间，怎么在不泄露隐私的前提下互相配合？
4. Agent 越主动，接触的不可信信息就越多，万一被提示词注入攻破怎么办？

原文作者的观点是：安全是 Agent 工作最大的一道坎——你敢不敢让 AI 全天二十四小时盯着群聊、操作你的电脑？一条恶意消息把 AI 忽悠了，数据和隐私怎么办。不过作者仍看好这个项目：它算是把一套成熟的团队管理方法搬进了 AI 的世界；感兴趣可以到 GitHub 上看这套研究原型（原文未给出具体链接）。
