# 多任务 Agent 的瓶颈是人的注意力，不是模型

## 结论

- **它是什么**：把 Agent 从「一个会话干一件事」改成「常驻的项目经理 + 多个各带独立上下文的工程师」，消息先进门卫，再由工单订阅绕过项目经理中转。
- **值得抄的**：门卫+秘书两级过滤、按工单编号订阅直投、编号+摘要的链式召回，三条不换架构也能单独抄。
- **不搬的**：不要一上手就上多层常驻全家桶。批处理的收益依赖工单量，订阅边界依赖 PR／群话题结构，小规模下只加延迟。

## 1. 它要解的问题

现在主流 Agent 都以会话（session）为单位干活：开一个会话布置一个任务，Agent 在这个会话里想一步、做一步、看结果再想下一步，直到干完，这个循环叫 react loop。单看一个任务，这个模式很顺，所以流行了很久。问题出在同时有好几件事要办的时候——你开一个会话修 bug、一个写文档、一个跑测试，同事在群里说一句「这个需求改一下」，你又得新开一个。这些会话互相不知道对方在干什么，跨任务的信息只能靠你自己记住再手动搬运。作者用 DeepSeek 官方那句话把事说透了：**单任务的上限取决于模型能力，多任务的上限取决于人的注意力**——他们观察到，人通常只能同时跟进三到五个活跃会话，AI 越能干，人越累。

那给 Agent 接上飞书、让它自己去群里看消息接任务行不行？视频承认借助 CLI 和 MCP 确实能做到，但不算解决——只要底层还是单个会话，很快会撞上三件事：执行耗时命令时整个循环卡住，命令跑完才能处理新消息；多个需求塞进同一个会话，上下文越来越乱；Agent 跑在本地电脑上，电脑一休眠就罢工。所以结论是**必须把 Agent 和单次会话解绑**，让它成为能跨会话记住上下文、同时推进多件事、互不干扰的连续工作者。视频给的四条特征是连续（群里说方案 A、后来 PR 里改成方案 B 也跟得上）、高效（上一件没干完也能接新指令）、主动（自己盯群消息和工单）、持久（一直在线，出问题能自己恢复）。

有两处限定必须一起搬走。一是「所有消息都过项目经理，他会不会忙不过来」——视频说实践中问题不大，靠的是新消息先攒着、忙完一起看一起派活，这是**实践观察，不是容量测算**。二是「主动」不等于乱来：开源原型里，没人要求的主动工作必须有团队提前写好的规则才能做，且默认先用观察模式，只记录自己打算做什么、并不真的动手。

## 2. 一条消息从进来到回你，经过谁

### 门卫与秘书：消息先进两道闸

**职责**：在消息到达项目经理之前，用最便宜的手段砍掉绝大多数不值得处理的噪音。

**怎么做**：这套架构不由「你说一句它干一次」驱动，而由环境里发生的事驱动，视频把这些事统称 trigger（触发事件）——群里来了新消息、PR 下有人评论、代码构建失败。但群里的废话太多，每条都让大模型判断要不要管，又慢又烧钱。于是门口先站一个门卫，只看消息从哪儿来：是不是被监听的群、发消息的人在不在白名单，用普通代码就能秒判；门卫放行的再交给秘书，秘书才读内容，交给大模型按提示词里写好的规则决定是否处理。这就是计算机里的快慢路径（fast path／slow path）思想：能靠字段判的走快路，要理解内容才走慢路。

**失效时**：门卫只看来源，等于把「谁说的」当成「值不值得看」的代理指标。白名单里的人贴一条无关长文照样过闸，而不在白名单里的真实用户报的 bug 会在门口被丢掉，丢时没有任何语义，日志只留一条「来源不匹配」。慢路径也不便宜：规则写在提示词里，规则一模糊，模型对同类消息的判断就会摇摆，今天处理、明天忽略。

**原文说法**：「门口先有个门卫，后面再有个秘书。门卫只看消息从哪儿来……秘书负责读内容。」

### 项目经理（router 层）：不干活，只记全局和派活

**职责**：常驻在线，接住所有渠道的消息，记住全局，跟你沟通，给下面派活。

**怎么做**：架构分上下两层。上层 router 层相当于项目经理，所有渠道的消息都先到他这里，由他记全局、跟你沟通、给工程师派活；下层 worker 层相当于工程师，每个 worker 有自己独立的上下文，专心干好一件事，干完向他汇报，再由他统一回复你。所以不管你在飞书群还是 GitHub 说话，面对的始终是同一个对接人。这套分工顺带改了用模型的方式：项目经理不亲自干活，用轻量模型就够了；真正决定交付质量的是 worker，才需要配最强的模型。

**失效时**：这是全系统的单点。它的上下文要同时装下二十件事的当前状态，一旦某条工单的记忆被后来的消息挤掉，派活就会重复或漏派——而且错误在下游才暴露：worker 干得没错，只是干错了事。它对 worker 的进度只能靠汇报得知，汇报丢一条，全局视图偏一次。而「忙不过来问题不大」建立在批处理上，批处理把延迟换成吞吐：紧急消息若赶上处理长任务的中途，要等这批结束才被看见；「忙完」也没定义成时间窗口还是队列水位，攒得越大摊得越薄，尾部延迟越长。批处理还依赖消息同质，二十件互不相关的事攒在一起，一次判断并不比二十次便宜。

**原文说法**：「如果全交给一个人，虽然信息不会断，但他只能把任务排好队一个个做。」项目经理则「不亲自干活，只负责沟通和派活」。

### 工单（thread）与订阅：后续消息绕开中转

**职责**：把一条已分配任务的后续增量，直接送到正在干它的人手里。

**怎么做**：同一个 PR、同一个群话题、同一串邮件里的连续消息被叫做一个 thread，视频让你把它理解为一个工单。现实团队也是这么办的：工单第一次进来时经理分给小王，之后这个工单的消息直接抄送小王。Super Agent 同样——worker 接手后订阅这个工单，后续新消息由程序直接送到他手上，不再经过项目经理，能节省大量 tokens。worker 之间一般不直接沟通：两个 worker 若在改同一个 PR，会同时收到这个 PR 的新动态，自己就能协调好。任务太复杂，worker 还能再拉几个 sub agent 帮忙，相当于工程师自己带了实习生。

**失效时**：订阅是路由器用「放弃全局视野」换来的。工单边界一判错——同一件事在群里和 PR 里被切成两个 thread——两个 worker 各订阅一半，谁也看不到对方，而「自己就能协调好」的前提是双方都收到同一条动态。后建订阅的 worker 还拿不到订阅前的历史。

**原文说法**：「同一个 PR，同一个群话题，同一串邮件里的连续消息叫做一个 thread，你可以理解为一个工单。」

### 资料怎么给：inline、spill 和顺着编号翻

**职责**：决定每个 worker 开工时能看多少资料。

**怎么做**：资料给多了重点被淹没，给少了干活的人反复回头来问。视频把这条上升成一句判断：浪费上下文窗口就是浪费模型的智能。为此借了编译器里的两个概念：inline 内联，就像同事给你转消息时，顺手附上前后几句聊天和相关的工单号，让你一眼看懂来龙去脉；spill 溢出，就像遇到一份几万字的文档，只给你摘要和一句「完整内容见这里」，需要时再去翻。用到整个系统里就成了链式召回（chain of recall）：每条消息、每个工单、每个 worker 都编号，每张卡片上只写摘要和关联编号；你跨平台提起一件旧事，项目经理不用把历史全背下来，顺着编号一路往下翻就行，像侦探找线索一样。

**失效时**：链式召回把「记得」换成了「能查到」，代价是每一跳都可能断：编号指向的原文被删或过期、摘要写偏、一条消息其实横跨两个工单而卡片只记了一个关联。任何一处出问题，顺着它往下翻的人都继承了同一个错误。摘要是有损压缩，若写摘要也是模型做的，偏差会被下游当成事实。

**原文说法**：「inline 内联，就像同事给你转消息时，顺手附上前后几句聊天和相关的工单号。」

### 回你的一侧：全双工与渠道话术

**职责**：让活还没干完时你也能说话，并决定这段话以什么形式出现在你面前。

**怎么做**：传统 Agent 一干活就忽视新消息，因为 react loop 是半双工的，像对讲机，同一时间只能一方说话。Super Agent 把对讲机换成电话，也就是全双工：把耗时的工具调用改成异步，命令一启动就立刻返回，Agent 可以继续跟你聊天，等命令跑完，结果再作为一条新消息送回来。能边干活边聊天之后还要管渠道：把终端里长篇大论的思考过程原样发到群里，群消息估计要炸，好在冗长推理都关在 worker 里，只有项目经理对外说话；飞书里只在需要你拍板时才发消息、单次回复不超过一百个词，GitHub 和邮件里则要写清问题背景、改动和验证结果。

**失效时**：异步化把「命令跑完」和「我知道它跑完了」拆成两件事，中间那段窗口里你和它的状态理解不同步——你可能基于旧结果下了新指令，结果回来时又把它覆盖掉。渠道话术的问题是硬规矩会误伤：一百个词的上限在解释复杂取舍时会逼着项目经理省略前提，省略的部分正是你会误判的地方。

**原文说法**：「React Loop 是半双工的，它就像对讲机，同一时间只能一方说话。Super Agent 要做的是把对讲机换成电话。」

## 3. 它放弃了什么

- **放弃「一个会话一条连续上下文」的直觉**，换来 worker 之间互不污染；代价是跨 worker 的信息必须靠编号加摘要串起来，串错一环就丢线索，且丢了不容易被发现。
- **放弃让派活的人亲自干活**，换来项目经理可用轻量模型、成本压得住；代价是所有判断都压在提示词规则上，规则写得糙就是漏派或乱派，没有第二个人复核。
- **放弃每条消息都过项目经理**，换来大量 token 节省；代价是订阅之后路由器失去这条工单的视野，工单间的冲突交回 worker 自行协调，没人仲裁。
- **放弃把计算、状态、执行环境绑在同一台电脑上**（改为计算进可替换容器、会话状态进数据库、本机只留一个不存记录的 Daemon），换来容器挂了换一个、记录一条不丢、笔记本没开机时云端等它上线后再补上；代价是多一条云端到本机的指令通道，以及 BYOM 这个妥协——环境搬不动就不搬。
- **放弃「主动等于随时动手」**，默认先跑观察模式，换来临界前的安全；代价是主动性收益被推迟，而从记录到放开的判据视频没说清。

## 4. 数字与口径

- **三到五个活跃会话**：DeepSeek 对「一个人通常能同时跟进几个会话」的观察，不是受控实验，用来论证多任务上限取决于人的注意力。
- **速度快了一倍**：视频称这是 Super Agent 相比传统单对话 Agent 的对比实测，但没给任务类型、模型、并发数和测量窗口，只能当方向，不能当验收基线。
- **读缓存的 token 是单会话方案的两倍到将近四倍**：同一次对比的另一侧，和上一条方向相反——**这是代价在涨的那项**。worker 越多、并行度越高，前缀复用越差，缓存读取量越大。
- **单次回复不超过一百个词**：飞书渠道的硬规矩，不是性能数字，但它把「回复长度」变成一条可写进验收的约束。

## 5. 落地时先做什么

- **把耗时工具调用改成异步**：触发条件 单次调用已长到你在等它时无法插话；最小改动 调用一启动就返回句柄，结果作为一条新事件回灌给同一上下文；成功判据 长命令还在跑时新消息能被接住并回复，且回灌结果不覆盖你期间下的指令。
- **在进模型之前加一级代码门卫**：触发条件 群里的噪音已让模型调用成本或判断噪音明显；最小改动 先用来源、白名单、是否被监听这类字段做硬过滤，剩下的才交给模型读内容；成功判据 进模型的条数明显下降，而事后确认的漏判条数不上升。
- **给同一工单的后续消息开直连通道**：触发条件 同一 PR、同一群话题的连续消息反复被同一中转节点转发；最小改动 给工单编号，接手方订阅该编号，后续消息按编号直投；成功判据 单工单在转发侧消耗的 token 下降，而首条消息的响应延迟不变。

## 6. 明确不做什么

- **不做没有规则的主动执行**：原型要求没人要求的主动工作必须由团队提前写好规则，否则「主动」和「乱动」之间没有边界。
- **不做 worker 之间的直接对话**：现有设计靠订阅同一 PR 动态自行协调，一旦加互相通话的通道，就多出「谁仲裁冲突」这个没人负责的角色。
- **不把内部推理直接投到对外渠道**：长推理关在 worker 里，只让项目经理按渠道规矩说话，否则群消息会被思考过程淹没。

## 7. 还没答案的问题

- 批处理窗口是时间驱动还是队列水位驱动？「消息越多平均处理越快」这个结论只在消息同质时成立。
- thread 的边界靠什么字段判定？同一件事同时出现在群话题、PR 和邮件串里时，是合成一个编号还是各算一个，合并规则在哪维护？
- 观察模式记录下的「打算做什么」，用什么判据转成放开的规则——自动归并，还是人读完手工写？
- 看门狗怎么区分「模型在原地打转」和「长任务里正常等待」？巡检间隔与误杀率的取舍没有给出。

## 8. 术语 ↔ 它在系统里的位置

- **react loop** → 单会话内「想一步、做一步、看结果」的循环，是这套架构要拆掉的约束。
- **router 层** → 常驻的项目经理，所有渠道消息的第一入口，记全局、沟通、派活，自己不干活。
- **worker** → 带独立上下文的工程师，真正决定交付质量，因此是唯一值得配最强模型的那一层。
- **sub agent** → worker 任务太复杂时临时拉的下手，相当于工程师带的实习生。
- **thread 工单** → 同一 PR、同一群话题、同一串邮件的连续消息，是订阅与直投的寻址单位。
- **trigger 触发事件** → 环境里发生的事（新消息、PR 评论、构建失败），它是驱动源。
- **fast path／slow path** → 门卫用代码秒判来源、秘书用模型读内容的二级过滤。
- **inline／spill** → 给 worker 投递资料的两种方式：附带上下文，或只给摘要加一个「完整内容见这里」的指针。- **chain of recall 链式召回** → 消息、工单、worker 全部编号，卡片只写摘要和关联编号，需要时顺着编号往下翻。
- **watchdog** → 主系统之外单独配的值班会话，定时巡查任务有没有进展，而不只是进程在不在。
## 9. 出处与边界

- 分层架构、四条特征、五个模块、渠道话术与四个开放问题，都来自视频口播对 DeepSeek 原文与实践的**转述**，不是原文直引，措辞是讲者的说法。
- 「快了一倍」「缓存 token 两倍到将近四倍」来自视频所述的对比实测，但**没有测试条件**——任务类型、模型、并发数、测量窗口全缺，不能直接当基线。
- 「三到五个活跃会话」是观察性结论，「二十件事」是假设例子，两者都不是测量数据。
- Claude Code、CodeX、DeepSeek Harness 在视频里是同期主流做法的同类参照（用于说明「会话为中心」是普遍现状），不同源。
- 视频说研究原型开在 GitHub 上，但没给仓库名，本文不补；「全双工在很多 AI 工具里已实现」也只是讲者判断。
