# 别再加会话了，给 Agent 配个项目经理

## 结论

它是什么：DeepSeek Harness 团队提出的 Super Agent 把 Agent 从"一个会话干一件事"改成"常驻的项目经理加一组有独立上下文的工程师"，由环境事件驱动、可跨会话并行。

值得抄的：入口两级过滤、thread 订阅绕开调度、按编号做链式召回、长命令异步化——这四件事不换整套架构也能先落地。

不搬的：不搬它的全量主动模式，也不搬"worker 之间不需要直连"这条在写冲突下过于乐观的假设。

## 1. 它要解的问题

不管是 Claude Code、CodeX 还是 DeepSeek Harness，现在主流 Agent 都以会话（session）为单位干活：你开一个会话布置一个任务，它在会话里想一步、做一步，看结果再想下一步，直到活干完。这个循环叫 react loop。单看一个任务，这个模式好用，所以流行了很久；这是作者自己保留的判断，他没说 react loop 错了。

问题出在同时有好几件事要办的时候。修 bug 一个会话、写文档一个会话、跑测试一个会话，群里同事一句"这个需求改一下"又要新开一个。这些会话互相不知道对方在干什么，所有跨任务的信息只能靠你自己记住再手动搬运，你于是成了一群 AI 之间的传话筒。作者给出的判断很硬：单任务的上限取决于模型能力，多任务的上限取决于人的注意力——他观察到一个人通常只能同时跟进三到五个活跃会话，AI 越来越能干，人反而越来越累。

那给 Agent 接上飞书，让它自己去群里看消息接任务行不行？作者说借助 CLI 和 MCP 确实能做到，但只要底层还是单个会话，就会撞上三个具体故障：执行耗时命令时整个循环卡住，命令跑完才能处理新消息；好几个需求塞进同一个会话，上下文越来越乱；Agent 跑在你本地电脑上，电脑一休眠它就罢工。所以他主张必须把 Agent 和单次会话解绑，让它变成能跨会话记住上下文、同时推进多件事、且互不干扰的连续工作者。

## 2. 一条消息从进来到回你，经过谁

### 2.1 入口：环境开口，门卫放行

**职责**：把群消息、PR 评论、构建失败这类环境变化收成一个统一入口，并在付模型的钱之前先把无关消息扔掉。

**怎么做**：传统 Agent 是你说一句它才干一次活，Super Agent 反过来由环境里发生的事情驱动，这些事件被统一叫做 trigger（触发事件）。但群里废话太多，于是做两级过滤：门口先有个门卫，只看消息从哪儿来——是不是监听的群、发消息的人在不在白名单里，用普通代码就能秒判；后面再有个秘书，负责读内容，通过门卫的消息才交给大模型，由它按提示词里写好的规则判断要不要处理。这就是计算机系统里的快慢路径（fast path / slow path）思想：能便宜判断的绝不上贵的判断。

**失效时**：门卫只看来源不看内容，白名单内的群如果来了一条恶意或无关的长消息，照样进到秘书那里；秘书的规则写在提示词里，规则漏写一条就漏一类活，而且它只给"处理/不处理"的结论，判断错了不会有人复核。两级都通过，等于默认每条白名单消息都值得花模型的钱。

**原文说法**："如果每条消息都让大模型判断一遍要不要管，又慢又烧钱。"

### 2.2 Router：不亲自干活的项目经理

**职责**：常驻在线，所有渠道的消息先到它这里；它记住全局、跟你沟通、给下层派活，但不自己动手。

**怎么做**：整套架构分上下两层，上层 router 层相当于项目经理，下层 worker 层相当于工程师。每个 worker 有自己独立的上下文，专心干好一件事，干完向项目经理汇报，再由项目经理统一回复你——所以你面对的始终是同一个对接人，团队内部怎么分工你不用关心。因为项目经理不亲自干活、只沟通和派活，router 用轻量模型就够了；真正决定交付质量的是 worker，他才需要配最强的模型。至于"所有消息都经过经理，他会不会忙不过来"，作者引用实践结论说问题不大：经理处理上一批消息时，新消息先攒着，等他忙完再一起看、一起派活。

**失效时**：批处理换来吞吐，代价是最新一条消息要等到当前批次结束才被看见，紧急指令插不进来；router 用自己的轻量模型做"该不该管、派给谁"的全局判断，这是整条链上最便宜也最容易错的一环，它错一次整队都白跑；而且它是唯一对外接口，它自己卡住，你就收不到任何回复，也没人知道任务停了。

**原文说法**："消息越多，平均处理得反而越快。"

### 2.3 Thread 订阅：后续消息绕过经理

**职责**：让已经有人在办的活，其后续消息直接送到那个人手上，不再逐条过经理。

**怎么做**：同一个 PR、同一个群话题、同一串邮件里的连续消息叫做一个 thread，可以理解为一个工单。现实中的团队里，一个工单第一次进来时经理把它分给小王，之后这个工单的消息直接抄送小王就行；Super Agent 也是这样，worker 接手之后会订阅这个工单，程序把新消息直接投递给他，不再经过 router，能省下大量 token。

**失效时**：订阅是静态绑定，接手的 worker 判断错人也不会自动纠正；worker 挂了或换人时，已订阅的 thread 由谁接下、会不会重复投递，作者没有交代；跨 thread 的关联仍然只能落在 router 的全局记忆里，比如你在群里说用方案 A、后来在 PR 里改成方案 B，这层"同一件事的两条线"并没有被 thread 机制本身覆盖。

**原文说法**："你可以理解为一个工单。"

### 2.4 Worker 与上下文：给多少资料

**职责**：在自己的上下文里把一件活干完并交付，上下文预算由系统按需装配。

**怎么做**：worker 相当于工程师，任务太复杂时还能再拉几个 sub agent 帮忙，相当于工程师自己带了实习生。核心权衡是"该给干活的人看多少资料"：给多了重点被淹没，给少了干活的人反复回头来问。作者借了编译器里的两个概念——inline 内联，就像同事给你转消息时顺手附上前后几句聊天和相关的工单号，让你一眼看懂来龙去脉；spill 溢出，就像遇到一份几万字的文档，只给你摘要和一句"完整内容见这里"，需要时再去翻。用到整个系统里就是链式召回（chain of recall）：给每条消息、每个工单、每个 worker 都编号，每张卡片只写摘要和关联的编号，你跨平台提起一件旧事时，项目经理不用把历史记录全背下来，顺着编号一路往下翻就行，像侦探找线索。同一个思路还用在主动性上：借鉴投机执行——CPU 在不确定某段计算会不会用上时先提前算好，用上了就赚，用不上就扔——比如收到会议邀请，它先在后台核对日程、查好背景资料、备好回复草稿，你确认一下就能发。

**失效时**：编号链的强度完全取决于编号稳定，消息被删、工单迁移、编号复用都会断链，断链时 router 只能退回重新检索；摘要由谁写、写歪了怎么发现，作者没说。投机执行那一侧的成本是显性的：备好的草稿如果十次有八次用不上，预热消耗的 token 和工具调用就是纯亏损，而"用得上"的比例没人测过。

**原文说法**："浪费上下文窗口就是浪费模型的智能。"

### 2.5 出口：全双工、渠道规矩、看门狗

**职责**：把结果按各渠道的规矩回给你，并在模型跑偏时把任务拉回来。

**怎么做**：传统 Agent 一干活就忽视新消息，原因是 react loop 是半双工的——它像对讲机，同一时间只能一方说话；Super Agent 要做的是把对讲机换成电话，也就是全双工。具体做法是把耗时的工具调用改成异步：命令一启动就立刻返回，Agent 可以继续跟你聊天，等命令跑完结果再作为一条新消息送回来。对外说话还得守渠道规矩：冗长的推理过程都关在 worker 里，只有项目经理对外说话；在飞书里只在需要你拍板时才发消息，单次回复不超过一百个词；在 GitHub 邮件里则要写清楚问题背景、改动和验证结果。另外主系统外面单独配一个 Watchdog（看门狗会话），相当于值班主管定时巡查，它不光看员工在不在岗，更要看任务有没有进展。

**失效时**：异步化之后同一会话里同时存在"在跑的命令"和"你在说话"两条流，谁先写回、写回时上下文已经被改过怎么办，需要一层顺序保证，作者没展开；watchdog 判"原地打转或跑偏"依赖什么信号也没说，阈值松了不起作用，紧了就会打断本来正常的长任务；把回复压到一百个词，需要背景才能拍板的决策会被压掉，反而多一轮来回。

**原文说法**："Agent 出问题，很多时候程序并没有挂，而是模型在原地打转或者跑偏了。"

## 3. 它放弃了什么

- 放弃"一个会话从头到尾"的连续性：换来了多任务并行，代价是任何跨任务的线索都必须由系统用编号和摘要重建，凡是没进过系统的口头结论（一句"还是按上次那个来"）就得人再讲一遍。
- 放弃 worker 之间直接沟通：省下了每条链路的上下文成本，代价是两个 worker 改同一个 PR 时没有仲裁者，只能各自收到该 PR 的新动态后"自己协调好"，冲突解决交给模型自觉。
- 放弃逐条实时处理：改批处理后 router 不会被消息量压垮、平均处理更快，代价是单条消息的响应被推迟到当前批次结束，插队能力归零。
- 放弃"路由也用最强模型"：router 用轻量模型省下的是按消息量计费的那部分钱，代价是全局性判断交给最弱的模型做，误判的成本被放大到整队。
- 放弃本地三合一（计算、状态、执行环境绑在同一台机器）：拆开之后休眠不再停工，代价是你机器上必须常驻一个只执行不回想的 daemon，笔记本关机期间相关任务只能等它上线；而代码、密钥、内网服务搬不上云，就得长期接受"云端大脑 + 本地手脚"的跨网络开销。

## 4. 数字与口径

- **三到五个活跃会话**：作者转述的官方观察，指一个人通常能同时跟进的会话数上限；这是观察不是实验，没有样本和任务条件，但它是整篇"人的注意力才是瓶颈"的立论基础。
- **快一倍**：Super Agent 相对传统单对话 Agent 的速度对比，来自作者所说的"对比实测"；口径只有"速度"，没给任务类型、并发度、模型和硬件，只能当方向看。
- **缓存 token 两倍到将近四倍**：同样是对比单会话方案，随并行会话数增加而上升——这是代价在涨的那个数字，并行度越高越贵，它跟"快一倍"是同一笔交易的两面。
- **一百个词**：飞书渠道单次回复的长度上限，是产品规则而不是性能指标，不要拿它换算成本。
- **二十件事**：讲分层动机时的假设数字（"手里同时有二十件事"），不是测量值，别当容量结论引用。

## 5. 落地时先做什么

- 入口加一层纯代码门卫：触发条件 群里大部分消息与当前任务无关、每条都进模型判断既慢又贵；最小改动 在调模型前按来源直接判定（是否监听的群或话题、发送者是否在白名单、事件类型是否在清单内）并丢弃，只把通过的交给模型读内容；成功判据 单位时间内进入模型的判断次数明显下降，同时人工抽查的漏活数为零。
- 把长命令改成异步：触发条件 单次工具调用（跑测试、构建、装依赖）比一次对话轮次还长，期间循环被占住、新消息没人接；最小改动 工具调用启动即返回句柄，结果完成后作为一条新消息回注同一上下文；成功判据 长命令执行期间仍能接收并回应新指令，结果不丢、不乱序。
- 先把状态从进程里搬出去：触发条件 机器休眠、容器重启或执行进程被杀后任务无法续跑；最小改动 会话记录与任务状态外置到可持久化的存储，执行侧保持无状态、可随时替换；成功判据 强杀执行进程后任务能从断点继续，记录一条不丢。

## 6. 明确不做什么

- 不做 worker 之间的直接对话通道：额外链路会把上下文成本按并发数乘上去，而"共享同一 PR 的新动态"已经够用。
- 不一开始就开主动模式：没人要求的主动工作必须先有团队提前写好的规则，且默认只记录打算做什么、不动手。
- 不把执行环境整体搬到云端：代码、密钥、内网服务搬不动，硬搬只是把可用性问题换成网络与合规问题。

## 7. 还没答案的问题

- 一个 router 到底能撑多大：批处理窗口在多少条消息、多少个并发 worker 时会超过人愿意等的延迟？视频只给了"消息越多平均处理越快"的方向。
- 长期记忆怎么落地：连续跑几个月后，编号链的规模、摘要的压缩与淘汰策略是什么，被淘汰的卡片还能不能被召回。
- thread 的归属与迁移：worker 挂掉、换人或任务被取消时，已订阅的 thread 归谁，重复投递和漏投递靠什么发现。
- 提示词注入的边界：门卫只判来源，白名单内的群消息被投毒时，worker 侧有没有"这段输入不可信"的标记和权限隔离。

## 8. 术语 ↔ 它在系统里的位置

- **React Loop** → 单个会话里"想一步、做一步、看结果再想"的循环，是被解绑掉的那个旧单位。
- **Router** → 常驻的对外唯一接口，管全局记忆、跟你沟通、派活，不亲自执行。
- **Worker** → 有独立上下文、真正交付的执行单元，模型质量和上下文装配质量在它这里兑现。
- **Trigger** → 环境事件（新群消息、PR 评论、构建失败）的统一入口，取代"你说一句它干一次"。
- **Fast path / Slow path** → 入口的两级过滤：门卫按来源用代码秒判，秘书按内容用模型慢判。
- **Thread** → 同一 PR、同一群话题、同一串邮件里的连续消息，是订阅与直接投递的绑定单位。
- **Chain of Recall** → 消息、工单、worker 全部编号，卡片只带摘要加编号，靠顺编号翻找回历史。
- **Inline / Spill** → 上下文装配的两种粒度：顺手附上前后文，或只给摘要加一句"完整内容在这儿"。
- **Watchdog** → 主系统之外的巡查会话，按"任务有没有进展"而不是"进程在不在"判断异常。
- **BYOM（Bring Your Own Machine）** → 云端大脑配本地轻量 daemon，daemon 不存会话记录，只按云端指令执行命令并回传结果。

## 9. 出处与边界

- 全部结论来自一期视频口播的转述，讲的是 DeepSeek Harness 团队提出的 Super Agent 架构及其研究原型；视频只提到"GitHub 上的研究原型"，没有给出仓库名，这里也不补。
- "快一倍"和"缓存 token 两倍到将近四倍"只说明了对比对象是传统单对话 Agent，没有任务类型、并发规模、模型版本与硬件条件，不能当基准数字引用。
- "三到五个活跃会话"是观察性说法，不是实验结论，别拿它做容量规划。
- 视频里两个内部运行例子（群里提字体分开配置的需求、被 @ 后一路推进到代码合并；从产品用户群自主识别 bug、后台复现并发出修复与前后对比截图）属于举例说明，无外部材料可核对。
- Claude Code、CodeX 在文中只作为"同样以会话为单位"的同类对照，和这套架构不是同源实现，别把它们的行为当成 Super Agent 的既定行为。
