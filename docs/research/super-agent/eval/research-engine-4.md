# Agent 的上限不在模型，在人的注意力

## 结论

**它是什么**：把 Agent 从单个会话里解绑，拆成「常驻的项目经理 + 多个各自独立上下文的工程师」两层，改由环境事件驱动推进多件事。**值得抄的**：router/worker 分层、门卫加秘书的两级过滤、thread 订阅绕过 router、用 inline/spill 卡住上下文预算。**不搬的**：存算分离与 BYOM 只有在你有云端可替换容器和可靠会话存储时才成立，单机小工具照搬一套 daemon，收益抵不过运维成本。

## 1. 它要解的问题

现在主流 Agent 都以会话为单位干活：开一个会话布置一个任务，Agent 在这个会话里想一步做一步、看结果再想下一步，直到干完，这个循环叫 react loop。单个任务上它很好用，所以流行了很久。问题出在同时有好几件事要办的时候——修 bug 一个会话、写文档一个会话、跑测试一个会话，同事在群里说需求改一下又得新开一个；这些会话互相不知道对方在干什么，所有跨任务信息只能靠人记住再手动搬运，于是人成了一群 AI 之间的传话筒。作者引的 DeepSeek 判断是：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。他们的观察是，一个人通常只能同时跟进三到五个活跃会话，AI 越来越能干，人反而越来越累。

有人会问：给 Agent 接上飞书，让它自己看群消息接任务行不行？借助 CLI 和 MCP 确实能做到，但作者给了限定——只要底层还是单个会话，很快就会撞上三个问题：执行耗时命令时整个循环卡住，命令跑完才能处理新消息；好几个需求塞进同一个会话，上下文越来越乱；Agent 跑在你本地电脑上，电脑一休眠它就罢工。

所以这套设计的判断是把 Agent 和单次会话解绑，让它变成能跨会话记住上下文、同时推进多件事、彼此互不干扰的连续工作者，特征是连续、高效、主动、持久。但作者保留了反例和边界：主动不等于乱来，在开源原型里没人要求的主动工作必须有团队提前写好的规则才能做，而且默认先用观察模式，只记录自己打算做什么、并不动手，等确认判断靠谱再放开。

## 2. 一条消息从进来到回你，经过谁

### Router 层：常驻的项目经理

**职责**：所有渠道的消息都先到这里，由它记住全局、跟你沟通、给 worker 派活，自己不动手。

**怎么做**：类比是这样展开的——手里同时有二十件事，全交给一个人虽然信息不断但他只能排队做；每件事都找个新人也行，可大家互不同步信息，最后一人一嘴来找你汇报，很混乱。现实团队的解法是招一个项目经理配几个工程师。router 层就是这个项目经理，常驻在线；worker 层是工程师，每个有独立上下文，专心干一件事，干完汇报，再由经理统一回你。因为 router 不亲自干活，配轻量模型就够，最强模型留给决定交付质量的 worker。

**失效时**：所有消息都过一手，就意味着它是单点。视频里的解法是批处理——经理忙时新消息先攒着，忙完一起看一起派。这在消息稀疏、又需要立刻拍板的场景里会变成纯排队延迟；更要紧的是 router 一旦判断错，整条链都跟着错，而 worker 不会替它纠偏。

**原文说法**：「问题不大，因为项目经理处理上一批消息时，新消息会先攒着，等他忙完再一起看，一起派活。」

### Trigger 两级过滤：门卫与秘书

**职责**：决定环境里发生的哪件事值得叫醒 Agent。

**怎么做**：传统 Agent 是你说一句它才干一次，这套系统由环境里发生的事情驱动——群里来新消息、PR 下有人评论、代码构建失败，统一叫 trigger。但群里的废话实在太多，每条都让大模型判一遍又慢又烧钱，于是做两级过滤：门口先有个门卫，只看消息从哪儿来，比如是不是监听的群、发消息的人在不在白名单里，用普通代码秒判；秘书负责读内容，通过门卫的消息再交给大模型，由它按提示词里写好的规则判断要不要处理。这就是计算机系统里的快慢路径（fast path / slow path）思想。

**失效时**：门卫只有「来源」这一个维度，群列表或白名单配错，整类事件就永远进不来，而且不会产生任何「我漏了」的信号；秘书的判据写在提示词里，规则写含糊就退化成两条路——全都进来烧钱，或者全被丢掉且无人知道。

**原文说法**：「门口先有个门卫，后面再有个秘书。门卫只看消息从哪儿来。」

### Worker 与 thread 订阅：工单抄送给谁

**职责**：接手一个具体任务，并让这件事的后续消息直接落到它手上。

**怎么做**：同一个 PR、同一个群话题、同一串邮件里的连续消息叫做一个 thread，可以理解为一个工单。现实团队里工单第一次进来时经理把它分给小王，之后这个工单的消息直接抄送小王就行；系统照此办理——worker 接手后订阅这个工单，后续新消息由程序直接送到他手上，不再经过 router，能省大量 token。worker 之间一般不直接沟通；两个 worker 在改同一个 PR 时会同时收到这个 PR 的新动态，自己就能协调。任务太复杂，worker 还能再拉几个 sub agent，相当于工程师自己带了实习生。

**失效时**：订阅关系本质上是路由表，thread 归属一旦判错（话题被叉开、邮件改了标题、跨平台 id 对不上），消息就会投错人或重复投。省 token 的代价是 router 失去这条工单的现场视野，它只有在 worker 汇报时才重新知情。

**原文说法**：「之后这个工单的消息直接抄送小王就行。」

### 上下文预算：inline、spill 与链式召回

**职责**：决定干活的人该看到多少资料、看到哪一份。

**怎么做**：资料给多了重点会被淹没，给少了干活的人得反复回头来问；作者的说法是浪费上下文窗口就是浪费模型的智能。他们借了编译器里的两个概念：inline 内联，像同事给你转消息时顺手附上前后几句聊天和相关的工单号，让你一眼看懂来龙去脉；spill 溢出，像遇到一份几万字的文档，只给你摘要和一句「完整内容见这里」，需要时再去翻。用到整个系统里就是链式召回：给每条消息、每个工单、每个 worker 都编号，每张卡片上只写摘要和关联编号，你跨平台提起一件旧事时，router 不用把历史记录全背下来，顺着编号一路往下翻就行。

**失效时**：编号链一断（消息被删、摘要丢掉了关键约束、跨平台没有 id 映射），worker 就会照着残缺卡片干活，而且它不知道自己缺了什么——这是最难被发现的一类错，因为输出看起来很自信。摘要由谁写、什么时候重写，也直接决定这条链可不可信。

**原文说法**：「就像同事给你转消息时，顺手附上前后几句聊天和相关的工单号，让你一眼看懂来龙去脉」「顺着编号一路往下翻就行，就像侦探找线索一样。」

### 全双工、存算分离与 Watchdog：别在干活时聋掉，也别一休眠就下班

**职责**：保证 Agent 边干活边能接收新消息，并且机器不在线时任务不丢。

**怎么做**：react loop 是半双工的，「就像对讲机，同一时间只能一方说话」，一干活就忽视新消息。换成电话就是全双工：把耗时的工具调用改成异步，命令一启动就立刻返回，Agent 继续跟你聊天，等命令跑完结果再作为一条新消息送回来（作者也承认这机制在很多 AI 工具中都已实现）。主动的一步借的是投机执行——CPU 在不确定某段计算会不会用上时先提前算好，用上就赚、用不上就扔；对应到 Agent，收到会议邀请先在后台核对日程、查好背景资料、备好回复草稿，你确认一下就能发。存活上借存算分离分两步：先把计算和状态拆开，计算放在云端可随时替换的容器里，会话状态存进数据库，容器挂了换一个，记录一条不丢；再把计算和执行环境拆开，代码、密钥、内网服务搬不上云，那就别搬——大脑留在云端，你的电脑上只装一个很轻的 Daemon，它不保存会话记录，只按云端指令执行命令、回传结果，叫 BYOM。系统外面另配一个 Watchdog 会话当值班主管，定时巡查，不只看员工在不在岗，更看任务有没有进展，因为 Agent 出问题很多时候是程序没挂、模型在原地打转。

**失效时**：BYOM 把可用性押在你的机器上，笔记本关机期间该在这台机器上做的事只能等它重新上线补做；多一次云端往返，延迟和本地直连不是一个量级。Watchdog 只能看见「没进展」，很难区分「卡住了」和「这活本来就慢」，误杀一次长任务比不救更贵。

**原文说法**：「就像靠谱的团队会把工作记录放进档案室，谁来接班都能接着干」「就像一个远程专家在指挥现场的助手。」

## 3. 它放弃了什么

- 放弃「一个进程里什么都有」的单会话形态：换来并行与互不干扰，代价是要同时维护多个会话，读缓存的 token 涨到单会话方案的两倍到将近四倍。
- 放弃每条消息都由大模型判断：门卫用普通代码秒判，省时省钱，代价是判断力被压成「来源」一维，规则没写的来源永远进不来。
- 放弃 router 对所有消息的直连：thread 订阅让后续消息绕过经理、省下大量 token，代价是经理对这条工单的后续进展只剩「worker 汇报」一条信息通路。
- 放弃把执行环境搬上云：BYOM 让代码、密钥、内网服务原地不动，代价是可用性与延迟绑在你那台机器上。
- 放弃立即响应：批处理把零散消息攒成一批再统一派活，换来吞吐（作者称消息越多平均处理反而越快），代价是第一条消息的等待时间不再由模型速度决定。
- 放弃无约束的主动性：主动工作必须有预先写好的规则、默认跑在观察模式，代价是它对你「没说出口的期待」一律不动手。

## 4. 数字与口径

- 三到五个活跃会话：DeepSeek 观察到的一个人通常能同时跟进的上限，是「多任务上限在人的注意力」的经验依据；视频没给样本量和统计口径。
- 快一倍：视频转述的对比实测结论，Super Agent 相比传统单对话 Agent 速度快一倍；没交代任务集、时长、硬件。
- 两倍到将近四倍：同一个对比里，Super Agent 读缓存的 token 是单会话方案的这么多倍。这就是代价在涨的那个数字，而且口径只到「读缓存 token」，不等于总 token 消耗。
- 一百个词：飞书渠道单次回复的字数上限，是产品规则而非测试结果，和「卡死上下文预算」是同一套思路的对外延伸。
- 二十件事：作者举的假设场景（全交给一个人 vs 每件事找新人），不是压测数据，别当容量指标引用。

## 5. 落地时先做什么

- 先把调度层和执行层拆开：触发条件 你已经同时跟进两件以上任务、并发现自己在会话之间手动搬运信息；最小改动 保留现有单会话执行体当 worker，只加一个不直接调用工具的调度层，负责收消息、派活、汇总回复；成功判据 你只面对一个入口说话，worker 数量翻倍而你要记的东西不变。
- 再上门卫：触发条件 事件来源超过一类（群消息、PR 评论、构建失败）且「要不要管」的模型调用量与成本开始刺眼；最小改动 先用纯代码按来源与白名单过滤，只把通过的消息交给模型判定，规则外置可改；成功判据 拦住的消息里抽样看不到本该处理的，且模型调用量随群里的闲聊量脱钩。
- 最后做订阅与上下文卡片：触发条件 同一件事的后续消息反复经过调度层，token 花在搬运而不是干活上；最小改动 给消息、工单、worker 建稳定编号，后续消息按编号直投，卡片只放摘要加编号；成功判据 同一工单的第二条消息不再消耗调度层的上下文预算，worker 也不再回头问「上文是什么」。

## 6. 明确不做什么

- 不在没有云端可替换容器与可靠会话存储之前上 BYOM：这套拆分的前提是云端那一半真能接着干，否则你只是把单点从一台笔记本摊到两台机器上。
- 不让 router 配强模型：它的产出是派活和话术，把最强模型放在这里只会把成本压在不会提升交付质量的地方。
- 不给主动性开全域权限：默认观察模式、主动工作必须有预写规则，是提示词注入还没有答案时唯一能兜住的边界。

## 7. 还没答案的问题

- 一个 router 撑到多少并发派活会开始丢约束？作者自己问了「任务规模继续变大，一个项目经理还够用吗」，但没给分层或分片方案。
- 连续跑几个月后长期记忆存在哪、怎么淘汰？口播只留了一句「长期记忆怎么办」，检索、压缩、过期策略全部空缺。
- Daemon 与云端之间怎么防伪造指令？BYOM 让云端能指挥你机器上的命令执行，这条通道的鉴权与超时回收在视频里没有出现。
- Watchdog 判「没有进展」的具体判据是什么？如果它自己也是模型，谁来看住它？
- 门卫规则和秘书提示词由谁维护、怎么回归测试？两级过滤的误杀率目前没有可观测口径。

## 8. 术语 ↔ 它在系统里的位置

- **React Loop** → 单个会话里「想一步、做一步、看结果再想」的循环，是被解绑的那个旧单位，半双工是它的先天缺陷。
- **Super Agent** → 解绑会话之后的整体形态，连续、高效、主动、持久的连续工作者，内部拆两层。
- **Router 层** → 上层的常驻调度者：收全部渠道消息、记全局、跟你沟通、派活、统一回复，不亲自干活，配轻量模型。
- **Worker 层** → 下层的执行者：独立上下文、专心干一件事、干完汇报，可以再拉 sub agent，配最强模型。
- **Trigger** → 环境事件的统一名字（群消息、PR 评论、构建失败），用它取代「你说一句才动一下」的输入方式。
- **快慢路径（fast path / slow path）** → 门卫用普通代码秒判来源、秘书用大模型读内容的两级过滤分工。
- **Thread** → 同一 PR / 同一群话题 / 同一串邮件的连续消息，被当作工单，是订阅与直投的路由单位。
- **Chain of Recall（链式召回）** → 靠消息、工单、worker 的编号加卡片摘要逐层回溯历史；inline（顺手附上下文）和 spill（只给摘要加「见完整内容」）是它的两种粒度。
- **BYOM** → 执行环境留在你自己的机器、只装轻量 Daemon 的分工：大脑在云端，你的电脑只执行和回传。
- **Watchdog** → 主系统之外的值班主管会话，定时巡查任务有没有进展，而不只是进程还在不在。

## 9. 出处与边界

- 两层拆分、四个特征、两级过滤、thread 订阅、inline/spill、BYOM、Watchdog 都来自视频口播对 DeepSeek Harness 团队 Super Agent 的转述；口播只提到 GitHub 上有这套研究原型，没给仓库名，此处不补。
- 「快一倍」和「读缓存 token 两倍到将近四倍」出自视频转述的对比实测，缺任务集、时长、硬件与统计口径，只能当方向性结论，不能当基准。
- 「三到五个活跃会话」是经验观察，「一百个词」是渠道规则，两者都不是测出来的阈值。
- fast path/slow path、投机执行、存算分离、inline/spill 是借来的既有概念，属同类思路而非同源实现；口播也明说异步工具调用在很多 AI 工具里已经实现了。
- 口播称架构拆成五个模块，但没有逐一列名；本文按口播出现顺序归为 router、worker、trigger、上下文召回、执行与存活五块，属整理而非原文。提示词注入、多 router 扩展、长期记忆、人机界面、私人助理与团队 Agent 的协作，都是作者列出的开放问题，视频没有给出答案。
