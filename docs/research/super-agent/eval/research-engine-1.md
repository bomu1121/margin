# Agent 不该绑在会话上：拆成项目经理和工人

## 结论

- 它是什么：把 Agent 从「一次会话干一件事」里解绑，拆成常驻的路由层（项目经理）和多个独立上下文的 worker（工程师）。
- 值得抄的：路由层只派活不干活、thread 订阅绕开路由、门卫/秘书两级过滤、编号+摘要卡片的链式召回。
- 不搬的：默认打开的主动模式、router 用强模型、worker 直接把推理过程甩到对外渠道。

## 1. 它要解的问题

现在主流 Agent（Claude Code、CodeX、DeepSeek Harness）都以会话 session 为单位干活：开一个会话布置一个任务，Agent 在这个会话里想一步做一步，看结果再想下一步，直到干完，这个循环叫 react loop。单个任务看，这个模式很好用，所以流行了很久。问题出在你同时有好几件事要办的时候——开一个会话修 bug、一个写文档、一个跑测试，同事在群里说需求改一下，你又得新开一个会话。这些会话互相不知道对方在干什么，跨任务的信息只能你自己记住再手动搬运。作者的说法是：你不知不觉成了一群 AI 之间的传话筒。

DeepSeek 官方的判断是：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。他们的观察是，一个人通常只能同时跟进三到五个活跃会话——AI 越来越能干，人反而越来越累。

那接上飞书让 Agent 自己看群消息接任务行不行？作者给了这个反例：借 CLI 和 MCP 确实能做到，但只要底层还是单个会话，很快撞上三件事——执行耗时命令时整个循环卡住，命令跑完才处理新消息；多个需求塞进同一个会话，上下文越来越乱；Agent 跑在你本地电脑上，电脑一休眠它就罢工。所以结论不是「给会话加插件」，而是把 Agent 和单次会话解绑，变成一个能跨会话记住上下文、同时推进多件事、互不干扰的连续工作者。

## 2. 一条消息从进来到回你，经过谁

### 2.1 路由层：只派活的项目经理

**职责**：常驻在线，接住所有渠道的消息，记住全局，跟你沟通，把活派给 worker。

**怎么做**：作者用一个团队类比来定它的形状。你手上同时有二十件事，全交给一个人做，信息不会断但他只能排队一件件做；每件事都找个新人，能同时开工但互相不同步，最后一人一嘴来找你汇报。现实里的答案是招一个项目经理配几个工程师。于是 Super Agent 也分上下两层：上层 router 层就是项目经理，下层 worker 层是工程师。项目经理不亲自干活，只负责沟通和派活，因此 router 用轻量模型就够了；真正决定交付质量的是 worker，它才需要配最强的模型。你面对的始终是同一个对接人，内部怎么分工你不需要关心。

**失效时**：项目的全部上下文压在一个轻量模型 + 一份常驻记忆里，一旦它记错了派工关系或漏了一条批处理里的消息，下游 worker 再强也救不回来——它没有旁路可以自查。

**原文说法**：「这个 router 层的项目经理还有个特别之处，他不亲自干活，只负责沟通和派活。」

### 2.2 Worker 层与 thread 订阅

**职责**：每个 worker 有自己独立的上下文，专心干好一件事，干完向项目经理汇报，由项目经理统一回复你。

**怎么做**：消息过滤完该分活了，但如果每条消息都过项目经理转一手，他的压力会很大。作者又用团队类比：一个工单第一次进来时经理分给小王，之后这个工单的消息直接抄送小王就行。Super Agent 里同一个 PR、同一个群话题、同一串邮件里的连续消息叫一个 thread，可以理解为一个工单。worker 接手后订阅这个工单，后续新消息由程序直接送到他手上，不再经过项目经理，作者指出这一下能省大量 tokens。至于 worker 之间的配合，他们一般不直接沟通：两个 worker 同时在改同一个 PR，会同时收到这个 PR 的新动态，自己就能协调。任务太复杂时，worker 还能再拉几个 sub agent 帮忙，相当于工程师自己带了实习生。

**失效时**：「自己就能协调好」说的是两个 agent 靠同一份 PR 动态各自推断边界。一旦两边的改动互相冲突，系统里没有一个有裁决权的角色，只能等某个 worker 自己发现，或者等 Watchdog 从「任务没进展」这个外部信号上看出问题。

**原文说法**：「两个 worker 如果在改同一个 PR，会同时收到这个 PR 的新动态，自己就能协调好。」

### 2.3 两级过滤：门卫和秘书

**职责**：把环境里发生的事筛成「要不要处理」，尽量不用大模型判断。

**怎么做**：传统 Agent 是你说一句它才干一次活，Super Agent 由环境里发生的事情驱动——群里来新消息、PR 下有人评论、代码构建失败，这些事件被统一叫 trigger。但让 AI 直接盯群会发现群里废话太多，每条都过一遍大模型又慢又烧钱。作者的办法是两级过滤：门口先有个门卫，后面再有个秘书。门卫只看消息从哪儿来——是不是监听的群、发消息的人在不在白名单里，用普通代码就能秒判；秘书负责读内容，过了门卫的消息才交给大模型，由它按提示词里写好的规则判断要不要处理。作者把这个叫计算机系统里的快慢路径（fast path / slow path）思想。

**失效时**：门卫判的是来源而不是内容，白名单里的群一旦混进无关话题或者恶意消息，门卫会全部放行，压力原封不动落到秘书身上；反过来，规则写得严一点就会漏掉该处理的事，而漏掉是静默的。

**原文说法**：「门口先有个门卫，后面再有个秘书。」「如果每条消息都让大模型判断一遍要不要管，又慢又烧钱。」

### 2.4 上下文怎么塞：inline、spill 和链式召回

**职责**：决定每张工单给 worker 看多少资料，让上下文窗口不被浪费。

**怎么做**：资料给多了重点被淹没，给少了干活的人得反复回头问，作者的判断很直接：浪费上下文窗口就是浪费模型的智能。他们从编译器借了两个概念。inline 内联，就像同事给你转消息时顺手附上前后几句聊天和相关的工单号，让你一眼看懂来龙去脉；spill 溢出，就像遇到一份几万字的文档，只给你摘要和一句「完整内容见这里」，需要时再去翻。用到整个系统里就有了链式召回（chain of recall）：系统给每条消息、每个工单、每个 worker 都编了号，每张卡片上只写摘要和关联的编号。你跨平台提起一件旧事，项目经理不用把历史记录全背下来，顺着编号一路往下翻就行，作者形容「就像侦探找线索一样」。

**失效时**：这套东西的全部价值建立在编号一直被正确维护上。卡片上的摘要是压缩过的，一旦摘要写得不准或者编号断了，worker 会拿着一条看似完整、实际指错方向的上下文去干活，而错误不会当场暴露。

**原文说法**：「系统给每条消息、每个工单、每个 worker 都编了号，每张卡片上只写摘要和关联的编号。」

### 2.5 对讲机换电话，以及各渠道怎么说话

**职责**：让 Agent 边干活边接收新消息，并且只把该说的话送到该去的渠道。

**怎么做**：传统 Agent 一干活就忽视新消息，作者的解释是 react loop 是半双工的——它像对讲机，同一时间只能一方说话；Super Agent 要做的是把对讲机换成电话，也就是全双工。具体做法是把耗时的工具调用改成异步的：命令一启动就立刻返回，Agent 可以继续跟你聊天，等命令跑完结果再作为一条新消息送回来。作者补了一句，这个机制其实在很多 AI 工具里都已实现。能边干活边聊天之后还要管渠道：把终端里长篇大论的思考过程原样发到群里，群消息估计要炸，好在冗长的推理都关在了 worker 里，只有项目经理对外说话。规矩是——飞书里只在需要你拍板时才发消息，单次回复不超过一百个词；GitHub 邮件里则要写清楚问题背景、改动和验证结果。

**失效时**：只有项目经理一张嘴，意味着所有对外信息都要经过它二次压缩。worker 发现的细节（失败的日志行、被否决的备选方案）在压缩里丢掉，你在群里看到的永远是结论，回头追问要重新走一轮召回。

**原文说法**：「如果把终端里长篇大论的思考过程原样发到群里，群消息估计要炸了。」

## 3. 它放弃了什么

- 放弃了「翻会话记录就能知道 Agent 在干什么」。好处是人不用再当传话筒；代价是可观测性从你眼睛转交给编号卡片和 Watchdog，出事时你得先信系统，再信自己。
- 放弃了「本地 Agent 天生拥有执行环境」的便利。改成云端大脑 + 本地一个轻量 Daemon（BYOM，带上你自己的电脑）后，电脑休眠不再让 Agent 下班；代价是多了一条云到本地的指令往返和一层鉴权信任。
- 放弃了 router 的智能，只给它轻量模型。这换来了派活延迟和成本都很低；代价是路由判断本身比较糙，只能靠批处理把粗糙度摊平。
- 放弃了同步工具调用。命令启动即返回，循环不再被长命令卡死；代价是结果回来的顺序和因果不再天然对齐，要靠 thread 编号把「哪条结果属于哪件活」重新缝起来。
- 放弃了主动模式的自由度。原型里没人要求的主动工作必须事先有团队写好的规则，且默认观察模式只记录打算做什么、不真动手；代价是前期必须有人把规则写出来，好处是它不会替你做主。

## 4. 数字与口径

- 快一倍：视频的说法是「Super Agent 相比传统的单对话 Agent 速度快了一倍，而且工作更稳定」。这是唯一一句性能结论，没有给任务集、并发数、模型版本，无法复现。
- 缓存 token 是单会话方案的两倍到将近四倍：这就是代价在涨的那个数字。它跟同一组对比实测一起出现，但同样没说缓存命中率、上下文长度、也没有区分 router 和 worker 各吃多少。
- 三到五个活跃会话：DeepSeek「观察到」一个人通常只能同时跟进这么多，是经验观察值，不是测出来的注意力上限。
- 一百个词：飞书渠道单次回复的字数上限，属于渠道约定，没有说明是硬限制还是提示词里的要求。
- 二十件事：讲两层架构时用的假设数字（「假设你手里同时有二十件事要处理」），是类比的设定，不是任何测试的规模。

## 5. 落地时先做什么

- 拆出路由层：触发条件 同一个会话开始被塞进第二个需求，或长命令让循环明显卡住；最小改动 把「谁来决定派给谁」从执行上下文里抽出来，单独一层只做派活和对外回话，配最便宜的模型；成功判据 派活不再占用干活方的上下文，且人只需要在一个入口收到回复。
- 把工具调用改成异步：触发条件 单条命令的耗时超过人愿意等的时长；最小改动 命令启动即返回，跑完的结果作为一条新消息回灌到原 thread；成功判据 命令还在跑的时候，系统仍能接住并回应新指令。
- 两级过滤前置：触发条件 来的消息量已经大到逐条过大模型又慢又贵；最小改动 先用纯代码做来源判定（是不是监听的群、发消息的人在不在白名单），通过者才交模型按提示词规则判；成功判据 大部分消息在模型调用之前就被挡掉或放行。

## 6. 明确不做什么

- 不让 router 亲自干活，也不给它配强模型：它只是项目经理，让它干活等于把最贵的模型花在沟通上。
- 不让 worker 的推理过程直接对外发言：不同渠道的读者不同，长篇过程发到群里只会制造噪音，结论必须由项目经理统一出口。
- 不默认打开主动模式：原型默认只记录打算做什么，因为在规则还没写完、判断还没被验证的时候动手是不可逆的。

## 7. 还没答案的问题

- thread 的边界怎么合并：同一件事同时出现在群话题、PR 评论和邮件串里，是按来源算三个工单，还是有一个跨渠道的合并键？合并键由谁维护？
- 批处理到底压了什么延迟：作者说消息越多平均处理反而越快，但单条消息的首响应时间由谁兜底，攒批的上限是多少条或多长时间，视频没有给。
- Watchdog 怎么判定「在原地打转或跑偏」：它看的是任务有没有进展，可判据是什么、误报率多少、巡查本身花多少 token，都没有说。
- BYOM 的信任边界在哪：本地 Daemon 不保存会话记录、只按云端指令执行命令，那它靠什么鉴权、本地被改了怎么发现？这一层是整套持久性方案的根。

## 8. 术语 ↔ 它在系统里的位置

- **react loop** → 单会话里「想一步做一步」的循环，正是被替换掉的那个对象。
- **router 层** → 常驻的项目经理，所有渠道消息的入口，也是对外唯一的出口。
- **worker 层** → 每个持有独立上下文的执行单元，交付质量由它决定。
- **trigger** → 环境事件（群消息、PR 评论、构建失败）的统一入口名，用来替换「人说一句才动一次」。
- **fast path / slow path** → 门卫用代码做来源判定、秘书用模型读内容的两级过滤分工。
- **thread** → 同一 PR、同一群话题、同一串邮件里的连续消息，被当作一个工单，worker 订阅它后绕过路由。
- **inline / spill** → 两种给上下文的装法：附上前后几句原文，还是只给摘要加一句「完整内容见这里」。
- **chain of recall** → 消息、工单、worker 统一编号加摘要卡片形成的召回链，让项目经理不必背全部历史。
- **BYOM** → 云端放大脑、你的电脑上只放一个执行命令的 Daemon，用来把计算和执行环境拆开。
- **Watchdog** → 主系统之外单独值班的会话，看的是任务有没有进展而不只是进程在不在。

## 9. 出处与边界

- 本篇全部内容来自这一期视频的口播，作者自称是对 DeepSeek Harness 团队 Super Agent 架构的「更接地气」转述；我没有读原始设计文档，凡是原文措辞与我这里的归纳不一致，以原文为准。
- 「快一倍」「缓存 token 两倍到将近四倍」都只有一句口播支撑（「根据 DeepSeek 做的对比实测」），没有测试条件，属于必须自己复测才能用的数字。
- 「三到五个活跃会话」是 DeepSeek 的观察值，不是测量结果，不要当成并发上限来设计。
- 原型在 GitHub 上，但视频没有给仓库名、链接或日期，本篇也不编造；Claude Code、CodeX 在这里只是被举为「主流会话式 Agent」的同类，与这套架构并非同源。
- fast path / slow path、inline / spill、存算分离、投机执行都是被借用的通用计算机概念，不是这套架构的发明；作者借它们是为了解释设计，不是宣称来源。
