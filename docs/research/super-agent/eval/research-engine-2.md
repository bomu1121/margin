# Agent 不该绑在会话上：上层派活，下层干活

## 结论

- 它是什么：Super Agent 把 agent 从「一个会话干一件事」改成常驻路由层加多个独立上下文 worker 的连续工作者。
- 值得抄的：两级事件过滤、工单订阅后直送、编号加摘要的上下文投放，这三招不用改动模型调用就能先落地。
- 不搬的：router 单点加批处理带来的延迟、worker 之间不直接沟通只靠自觉协调、以及翻倍的缓存 token 账单。

## 1. 它要解的问题

现在主流的 agent，不管是 Claude Code、CodeX 还是 DeepSeek Harness，都以会话（session）为单位干活：你开一个会话布置一个任务，它就在这个会话里想一步做一步，看结果再想下一步，直到把活干完，这个循环叫 react loop。单看一个任务这套很好用，所以流行了很久。问题出在你同时有好几件事要办的时候——开一个会话修 bug、一个写文档、一个跑测试，同事在群里说这个需求改一下，你又得再开一个。这些会话互相不知道对方在干什么，所有跨任务的信息只能靠人记，再手动搬运。作者的原话是：「单任务的上限取决于模型能力，多任务的上限取决于人的注意力。」他们观察到一个人通常只能同时跟进三到五个活跃会话，AI 越来越能干，人反而越来越累。

那给 agent 接上飞书，让它自己去群里看消息接任务行不行？借助 CLI 和 MCP 确实能做到，但只要底层还是单个会话，就会撞上三堵墙：执行耗时命令时整个循环卡住，命令跑完才能处理新消息；好几个需求塞进同一个会话，上下文越来越乱；agent 跑在你的本地电脑上，电脑一休眠它就罢工。所以 DeepSeek 的判断是：必须把 agent 和单次会话解绑，让它变成一个能跨会话记住上下文、同时推进多件事、而且互不干扰的连续工作者。

它也给了这套东西四条验收标准：连续（在群里说用方案 A、后来在 PR 里改成方案 B，它跟得上）、高效（上一件没干完也能接下一条指令）、主动（自己盯着群消息和工单）、持久（一直在线，出问题能自己恢复）。但作者的限定条件写得很清楚：主动不等于乱来，在开源原型里，没人要求的主动工作必须有团队提前写好的规则才能做，而且默认先跑观察模式，只记录自己打算做什么、不真动手。同样，worker 之间一般不直接沟通，两个 worker 在改同一个 PR 就各自收这个 PR 的动态自己协调，任务太复杂时才允许 worker 再拉 sub agent。这些边界比架构本身更容易被抄漏。

## 2. 一条消息从进来到回你，经过谁

### router 层：常驻的项目经理

**职责**：所有渠道的消息都先到这里，由它记住全局、跟你沟通、给下层派活，最后也由它统一回复你。

**怎么做**：作者先摆了一个算术题：手上二十件事全给一个人，信息不会断但他只能排队一件件做；每件事都找个新人，能同时开工但互相不同步、最后一人一嘴来找你汇报。现实团队早给出了答案——招一个项目经理，再配几个工程师。对应到系统里就是上下两层：router 层是项目经理，常驻在线；worker 层是工程师，每个 worker 有自己独立的上下文，专心干好一件事，干完汇报。项目经理的特殊之处是不亲自干活，只负责沟通和派活，所以 router 用轻量模型就够，真正决定交付质量的是 worker，它才需要配最强的模型。至于「所有消息都过经理会不会忙不过来」，实测结论是问题不大：经理处理上一批消息时，新消息先攒着，等他忙完再一起看、一起派活。

**失效时**：批处理窗口开得越大，单条消息等得越久，紧急消息没有插队通道；router 是单点，它一卡住全系统没人派活也没人回话；轻量模型判断复杂需求时可能分错活，而分错要等 worker 干完才暴露，返工成本落在最贵的模型上。

**原文说法**：「如果全交给一个人，虽然信息不会断，但他只能把任务排好队一个个做。」

### trigger：门口一个门卫，后面一个秘书

**职责**：决定环境里发生的这一堆事情中，哪一件值得叫醒模型。

**怎么做**：群里来了新消息、PR 下有人评论、代码构建失败，DeepSeek 把这些事件统一叫 trigger（触发事件），agent 由事件驱动，而不是等你说一句才动一下。可是群里的废话太多，每条都让大模型判断要不要管，又慢又烧钱。办法是两级过滤：门口先有个门卫，只看消息从哪儿来——是不是监听的群、发消息的人在不在白名单——用普通代码就能秒判；后面再有个秘书，负责读内容，通过门卫的消息才交给大模型，由它按提示词里写好的规则判断要不要处理。这就是计算机系统里的快慢路径（fast path、slow path）思想。

**失效时**：门卫只看来源不看内容，白名单里的人发一堆废话照样全放进去，白名单外的人报真 bug 会直接死在门口；秘书的规则写在提示词里，规则没覆盖的情形就漏判，而漏判通常没有痕迹，你只会觉得「它怎么没反应」。

**原文说法**：「门口先有个门卫，后面再有个秘书。」

### thread：工单派出去，后续消息直接抄送

**职责**：让同一条线索上的后续消息绕开 router，直达已经接手的那个 worker。

**怎么做**：同一个 PR、同一个群话题、同一串邮件里的连续消息，叫做一个 thread，你可以理解为一个工单。现实团队里，一个工单第一次进来时经理把它分给小王，之后这个工单的消息就直接抄送小王就行。worker 接手之后会订阅这个工单，后续新消息由程序直接送到他手上，不再经过项目经理，能节省大量 token。这也是「消息都过经理会忙不过来」这个担忧的第二个出口：只有第一次分派要过经理。

**失效时**：订阅按 thread 绑定，话题一旦被拆到新 PR、新群或新邮件标题，链路就断了，消息又得回到 router 重新分派；worker 已经订阅但迟迟不处理时，消息在它那里堆积，router 看不到这部分压力，也就不会重派；两个 worker 改同一个 PR 靠「各自收到动态就能协调好」是自觉而非协议，真冲突时没有仲裁者。

**原文说法**：「之后这个工单的消息直接抄送小王就行。」

### 上下文投放：内联、溢出、链式召回

**职责**：决定每个 worker 开工时到底该看到多少资料。

**怎么做**：资料给多了重点被淹没，给少了干活的人反复回头来问，作者的判断是「浪费上下文窗口就是浪费模型的智能」。他们借了编译器里的两个概念：inline 内联，就像同事给你转消息时顺手附上前后几句聊天和相关的工单号，让你一眼看懂来龙去脉；spill 溢出，就像遇到一份几万字的文档，只给你摘要和一句「完整内容见这里」，需要时再去翻。把这个思路铺到整个系统里，就有了链式召回（chain of recall）：每条消息、每个工单、每个 worker 都编号，每张卡片上只写摘要和关联的编号；你跨平台提起一件旧事，项目经理不用把历史记录全背下来，顺着编号一路往下翻就行，像侦探找线索。同一套逻辑还撑起了投机执行——CPU 在不确定某段计算会不会用上时先提前算好，用上了就赚，用不上就扔；放到干活上就是你收到会议邀请，它先在后台核对日程、查好背景资料、备好回复草稿，你确认一下就能直接发。

**失效时**：摘要是有损压缩，没写进摘要的细节等于当场丢失；链式召回要多跳才拿得到原文，跳数多了既慢又可能在半路断链，而断链时 agent 不会报错，它只会拿着一半的信息继续往下干；编号体系本身需要维护，编号一旦错位，后面顺着编号翻到的全是错的东西。

**原文说法**：「顺着编号一路往下翻就行，就像侦探找线索一样。」

### 全双工与值守：对讲机换成电话

**职责**：让 agent 在跑长任务的同时还能接你的话，并在它原地打转时把它拽回来。

**怎么做**：传统 agent 一干活就忽视新消息，根子在 react loop 是半双工的，它像对讲机，同一时间只能一方说话。要换成电话，也就是全双工：把耗时的工具调用改成异步，命令一启动就立刻返回，agent 继续跟你聊天，等命令跑完，结果作为一条新消息送回来。作者也说了，这个机制在很多 AI 工具里已经实现。再往下是持久性。本地 agent 把三样东西绑在同一台电脑上：干活的计算、会话记录这类状态、代码和工具这些执行环境，电脑一休眠三样全停。他们借存算分离分两步拆：先把计算和状态分开，计算放进云端可随时替换的容器，会话状态存进数据库，容器挂了换一个，记录一条不丢；再把计算和执行环境分开，环境搬不动就不搬，大脑留在云端，你的电脑上只装一个很轻的小程序 Daemon，它不保存会话记录，只按云端指令执行命令、回传结果，像一个远程专家在指挥现场的助手，这套叫 BYOM（Bring Your Own Machine，带上你自己的电脑）。主系统外面再单独配一个 Watchdog 看门狗会话，相当于值班主管定时巡查，它不光看员工在不在岗，更要看任务有没有进展。

**失效时**：异步化的前提是结果能当新事件回投，回投链路一丢任务就悬空，而且没人知道它悬着；Daemon 所在机器没开机，该在这台机器上做的事只能等它上线；Watchdog 判断「没进展」靠阈值，方向对但就是慢的任务可能被它误判、打断或重派；它修的是流程，修不了模型本身跑偏的根因。

**原文说法**：「Agent 出问题，很多时候程序并没有挂，而是模型在原地打转或者跑偏了。」

## 3. 它放弃了什么

- 放弃「一件事只在一个会话里」：换来并行和互不污染，代价是同一件事的上下文被切成 router 的全局视角和 worker 的局部视角两份，worker 看不到别的任务正在改什么，只能靠订阅到的动态自己拼。
- 放弃 worker 直接对人说话：换成只由 router 对外，好处是你面对的始终是同一个对接人，渠道话术也能统一（飞书只在要你拍板时发、单次不超过一百词；GitHub 和邮件要写清背景、改动和验证）；代价是任何回复都要等 router 汇聚，worker 的即时反馈被抹平。
- 放弃把历史全量塞进上下文：换成编号加摘要，把窗口省给真正要干的活；代价是召回有损、要多跳，摘要里没写到的细节只能回去翻原文，翻不到就永久丢了。
- 放弃逐条实时判断事件：换成批处理加两级过滤，换来消息越多平均处理越快、模型调用量下降；代价是单条消息的延迟被窗口拉长，门卫判错就整条消息死在门口。
- 放弃把计算、状态、执行环境绑在一台机器上：拆开换来容器可替换、任务可续、换班能接着干；代价是多一条 daemon 回传链路和一台可能不开机的机器。

## 4. 数字与口径

- 3 到 5 个活跃会话：这是他们观察到的人同时能跟进的会话数量，属经验口径，没给测量方法和样本，用来说明瓶颈从模型挪到了人。
- 速度快了一倍：Super Agent 相比传统单对话 Agent，原文只有「根据 DeepSeek 做的对比测试」一句，没有任务集、并发数、模型配置和时长，只能当方向性结论用。
- 读缓存 token 是单会话方案的两倍到将近四倍：同一批活，干得快了，缓存读取量涨到 2 至近 4 倍，这就是代价在涨的那个数字，token 账单会跟着涨。
- 单次回复不超过一百词：这是飞书渠道的产品约定，不是性能指标；它和 GitHub、邮件里要求写清背景、改动和验证结果的规矩并存，口径差别来自渠道而不是负载。

## 5. 落地时先做什么

- 在事件入口前加一道来源判断：触发条件 <群里大部分消息与任务无关、每条都进模型太贵>；最小改动 <用普通代码判断消息来源与发言人白名单，通过的才交给模型读内容判断>；成功判据 <进入模型判定的消息量明显下降，且被拦下的消息仍可回捞复查>。
- 把耗时工具调用改成异步回投：触发条件 <一次命令跑起来就收不到新消息>；最小改动 <调用立即返回句柄，结果跑完作为一条新事件送回同一任务>；成功判据 <长任务执行期间仍能接新指令，且结果不会因此漏收>。
- 先把状态从执行机器上搬走：触发条件 <换机器或休眠就丢进度>；最小改动 <会话状态外置到数据库，执行侧只保留一个按指令执行、回传结果、不存记录的轻量进程>；成功判据 <执行容器被替换后任务能接着跑，记录一条不丢>。

## 6. 明确不做什么

- 不让 router 亲自干活：它的价值是常驻、记全局、统一对外，一旦它开始干活，派活和对你的响应就一起被拖住。
- 不让 worker 之间互相对话：同一 PR 的 worker 各自收到动态就足以协调，拉起群聊只会把各自的独立上下文重新搅乱。
- 不在无人要求时放开主动行为：原型里要求主动工作必须先有团队写好的规则，且默认只跑观察模式，因为误判的代价由你的群和你的电脑承担。

## 7. 还没答案的问题

- 批处理窗口该开多大：窗口越大平均吞吐越好，但紧急消息的等待时间没有上界，需不需要一条按来源分级的插队通道，原文没给。
- 一个 router 在任务规模继续变大时还够不够：如果不够，是按项目再分一层经理，还是按事件类型拆路由，判据是什么。
- 连续跑几个月的长期记忆存在哪里、怎么过期：编号加摘要的卡片由谁维护、何时失效，召回跳数随历史线性增长时怎么截断。
- 主动执行和提示词注入怎么划边界：agent 越主动就接触越多不可信信息，哪些事件来源可以触发写操作、哪些只能触发读，原文只把它列为开放问题。
- 私人助理与团队共用的 Super Agent 怎么在不泄露隐私的前提下配合，谁持有权限的最终判断权。

## 8. 术语 ↔ 它在系统里的位置

- **react loop** → 单个会话里「想一步、做一步、看结果再想」的循环，也是这套架构要拆掉的单位。
- **session** → 现在主流的任务容器，被解绑的对象；活跃会话数就是人的注意力预算。
- **router 层** → 常驻的项目经理，所有渠道消息的入口和所有回复的出口，只沟通派活。
- **worker** → 独立上下文的工程师，真正干活、决定交付质量，因此配最强的模型。
- **sub agent** → worker 自己拉来的实习生，只在任务太复杂时出现，不对 router 负责。
- **trigger** → 环境事件（新群消息、PR 评论、构建失败）的统一入口名，让 agent 从被叫才动变成被事件驱动。
- **fast path / slow path** → 门卫用普通代码秒判来源、秘书用模型读内容的两级过滤，用来省钱省时延。
- **thread** → 同一 PR、同一群话题、同一串邮件，等同工单；被 worker 订阅后消息直送，绕开 router。
- **inline / spill / chain of recall** → 上下文投放的三种手法：附上前后文、只给摘要加指路、按编号串成可追的链。
- **BYOM / Daemon** → 云端大脑加本机轻量执行程序，把不会搬的执行环境留在你机器上而不留状态。
- **Watchdog** → 主系统外定时巡查的值班主管，看的是任务有没有进展，不是进程在不在。

## 9. 出处与边界

- 全部内容来自一期技术视频的口播，讲的是 DeepSeek Harness 团队提出的 Super Agent 架构和他们开源的研究原型；视频没有给论文标题、仓库名或链接，这里一律不补。
- 「速度快了一倍」「缓存 token 两倍到近四倍」这两个数字只有「对比测试」的说法，没有任务集、轮次、并发、模型配置等测试条件，引用时要自己重测。
- 3 到 5 个活跃会话、二十件事都属于经验观察和类比，不是测量结果；不要在容量规划里当常数用。
- Claude Code、CodeX、DeepSeek Harness 在口播里只作为「同为主流的会话式 agent」被提及，是同类不是同源；异步工具调用、快慢路径、存算分离、投机执行也都是既有概念的借用。
- 项目经理配工程师、门卫加秘书、对讲机换电话、远程专家指挥现场助手这些说法是作者的讲解手法，不是架构规范；读设计时要还原成机制，别把类比当组件。
