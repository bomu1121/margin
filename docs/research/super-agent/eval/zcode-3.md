# DeepSeek Super Agent 拆解笔记

> **一句话**：传统 Agent 是"一次只能干一件事的外包"，Super Agent 是"一个项目经理 + 一群工程师"的项目团队 —— 能跨会话记上下文、并行推进多件事、被事件驱动、云端常驻。
>
> **关键数字**：速度 **2×**；读缓存 token **2× ~ 近 4×**；一个人能同时跟进的会话上限 **3~5 个**。

## 一页速览

| 维度 | 传统会话式 Agent | Super Agent |
| --- | --- | --- |
| 工作单位 | 一个 session 一个任务 | 跨会话的连续工作者 |
| 上下文 | 会话内累积，跨任务靠人搬运 | 全局由 router 掌握，worker 各自独立 |
| 并发 | 一次一件事，命令跑完才能响应 | 多 worker 并行，上一件没完也能接新指令 |
| 触发方式 | 你说一句，它干一次 | 环境事件驱动（消息、评论、构建失败） |
| 在线方式 | 绑在本机，电脑休眠即停 | 计算在云端，执行靠本机 Daemon |
| 人机接口 | 人当"传话筒"，在多个会话间切换 | 只跟一个对接人打交道 |
| 成本 | 基准 | 缓存 token 翻 2~4 倍 |

## 1. 起点：现在的 Agent 怎么干活

不管是 Claude Code、Codex 还是 DeepSeek Harness，主流 Agent 都以**会话（session）**为单位：

```
布置任务 → 想一步 → 做一步 → 看结果 → 再想下一步 → …… → 干完
                        ↑__________________________|
                              React Loop
```

单任务下这个循环很好用，所以流行了很久。问题出现在**你同时有好几件事要办**的时候：

- 一个会话修 bug，一个会话写文档，一个会话跑测试；
- 群里同事一句"这个需求改一下"，又得新开一个会话；
- 会话之间互不知情，跨任务信息只能靠你记住、再手动搬运。

不知不觉，你成了一群 AI 之间的**传话筒**。

> **DeepSeek 的判断**：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。
> 观察到的现实是，一个人通常只能同时跟进 **3~5 个**活跃会话。AI 越来越能干，人反而越来越累。

## 2. 接上飞书就够了吗：三个硬伤

用 CLI + MCP 让 Agent 自己去群里看消息、接任务，技术上做得到。但只要底层还是**单个会话**，就会撞上三堵墙：

| # | 问题 | 表现 |
| --- | --- | --- |
| 1 | **循环被卡住** | 执行耗时命令时整个 React Loop 阻塞，命令跑完才能处理新消息 |
| 2 | **上下文变脏** | 好几个需求塞进同一个会话，信息越堆越乱 |
| 3 | **本地绑定** | Agent 跑在你电脑上，电脑一休眠它就罢工 |

所以结论是：**必须把 Agent 和单次会话解绑** —— 让它变成一个能跨会话记住上下文、同时推进多件事、而且互不干扰的**连续工作者**。

## 3. Super Agent 是什么

> 传统 Agent 是**一次只能干一件事的外包**；
> Super Agent 是**一个配合默契的项目团队** —— 团队内部有很多人，但你只需要和一个对接人打交道。

DeepSeek 给它总结了四个基础特征：

| 特征 | 含义 | 具体表现 |
| --- | --- | --- |
| **连续** | 跨渠道、跨时间都接得上 | 在飞书群说"用方案 A"，后来在 PR 里改成"方案 B"，它也能跟上 |
| **高效** | 多线程推进 | 同时推进好几件事，上一件没干完也能接下一条指令 |
| **主动** | 自己找活 | 盯着群消息和工单，该处理的主动处理，不该管的保持安静 |
| **持久** | 一直在线 | 出了问题能自己恢复 |

## 4. 两个真实场景

**场景一：从群聊需求到代码合并**

1. 用户在群里提需求：正文、代码、终端的字体希望分开配置；
2. 维护者 @ 了一下 Super Agent；
3. 它很快到 GitHub 提交了改进代码；
4. 根据群里的追问 + 维护者在 GitHub 上的建议，一路推进到**代码合并**。

**场景二：自己发现 bug**

它从产品用户群里识别出 bug → 自主在后台复现 → 找到根因 → 直接把修复代码和**前后对比截图**发了出来。

> 也就是说，你甚至不用催 —— 该干的活它自己就干了。

## 5. 架构总览：五个模块

先看一个选择题：手里同时有 20 件事。

- **全交给一个人**：信息不断，但只能排队一件件做（连续，但不快）。
- **每件事找个新人**：能同时开工，但互不同步，最后每个人都要来找你汇报（快，但乱）。

DeepSeek 的答案是"我全都要"，而现实团队早就给出了解法：**招一个项目经理，再配几个工程师。**

```
        你：飞书群 / GitHub / 邮件 / 终端
                     │  所有渠道的消息
                     ▼
        Router 层 · 项目经理            ← 常驻在线、轻量模型、只沟通派活
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
     Worker A     Worker B     Worker C     ← 各自独立上下文 · 最强模型

     Worker 之间一般不直接沟通；复杂任务可再拉 Sub Agent（实习生）
```

按原文的叙述顺序，可以归成五块能力，外加一层兜底：

| # | 模块 | 解决的问题 |
| --- | --- | --- |
| 1 | **Router + Worker 分层** | 谁对用户说话、谁干活 |
| 2 | **Trigger 事件驱动** | 什么时候动、动之前怎么筛消息 |
| 3 | **上下文管理**（inline / spill / chain of recall） | 干活的该看多少资料 |
| 4 | **全双工**（异步工具调用 + 渠道表达规范） | 干活时还能不能聊天 |
| 5 | **存算分离 + BYOM** | 电脑休眠了怎么办 |
| 外 | **Watchdog** | 干着干着跑偏了怎么办 |

## 6. Router / Worker：项目经理与工程师

| 角色 | 职责 | 模型 | 上下文 |
| --- | --- | --- | --- |
| **Router（项目经理）** | 接收所有渠道消息、记住全局、跟你沟通、给 worker 派活 | **轻量模型即可**（不亲自干活） | 全局 |
| **Worker（工程师）** | 专心干好一件事，干完向 router 汇报 | **最强模型**（决定交付质量） | 独立 |

几个容易被忽略的细节：

- **用户始终只面对同一个对接人**，团队内部怎么分工你不用关心。
- **批处理**：所有消息都经过 router，会不会忙不过来？实践发现问题不大 —— 它处理上一批消息时，新消息先攒着，忙完再一起看、一起派活。结果是**消息越多，平均处理反而越快**。
- **worker 之间一般不直接沟通**。两个 worker 改同一个 PR 时，会同时收到这个 PR 的新动态，自己就能协调好。
- **worker 可以再拉 sub agent**，相当于工程师自己带了实习生。

## 7. Trigger：事件驱动与两级过滤

传统 Agent 是"你说一句它干一次"；Super Agent 由**环境里发生的事**驱动 —— 群里来新消息、PR 下有人评论、代码构建失败。这些事件统一叫 **trigger**。

但群里的废话太多，每条都让大模型判断"要不要管"，又慢又烧钱。DeepSeek 的办法是**两级过滤**：

```
消息 ──▶ 门卫（fast path）──▶ 秘书（slow path）──▶ Router 派活
         普通代码秒判          大模型读内容
         只看来源：            按提示词里的规则
         是否监听的群 /        判断要不要处理
         是否白名单
```

| 关卡 | 名字 | 看什么 | 谁来判 |
| --- | --- | --- | --- |
| 门卫 | **fast path**（快路径） | 消息**从哪儿来**：是不是监听的群、发消息的人在不在白名单 | 普通代码，秒级 |
| 秘书 | **slow path**（慢路径） | 消息**内容** | 大模型 + 提示词规则 |

这就是计算机系统里的快慢路径思想。

**再省一层：thread 订阅。** 现实中，一个工单第一次进来时经理分给小王，之后这个工单的消息直接抄送小王。Super Agent 同理 —— 同一个 PR、同一个群话题、同一串邮件里的连续消息叫一个 **thread**（可以理解为一个工单）。Worker 接手后**订阅**这个 thread，后续新消息由程序直接送到它手上，不再经过 router，**节省大量 tokens**。

## 8. 上下文：inline / spill / chain of recall

> **DeepSeek 的原则**：浪费上下文窗口就是浪费模型的智能。

资料给多了，重点被淹没；给少了，干活的人反复回头来问。解法借自编译器：

| 概念 | 类比 | 做法 |
| --- | --- | --- |
| **inline（内联）** | 同事转消息时顺手附上前后几句聊天和工单号 | 把小段相关上下文直接塞进去，一眼看懂来龙去脉 |
| **spill（溢出）** | 几万字的文档只给摘要 + "完整内容见这里" | 大块内容留在外面，需要时再去翻 |

把两者用到整个系统里，就是 **chain of recall（链式召回）**：

- 系统给每条消息、每个工单、每个 worker 都**编了号**；
- 每张卡片上只写**摘要 + 关联编号**；
- 你跨平台提起一件旧事，router 不用背下全部历史，**顺着编号一路往下翻**就行。

> 像侦探顺着线索查案，而不是把整个卷宗抱在怀里。

## 9. 主动：投机执行与观察模式

计算机里的**投机执行**：CPU 在不确定某段计算会不会用上时先提前算好 —— 用上了就赚了，用不上就扔掉。Super Agent 把它用在了干活上：

> 你收到一封会议邀请 → 它在后台先核对日程、查好背景资料、备好回复草稿 → 你确认一下就能直接发。

但**主动不等于乱来**。开源原型里的两条安全闸：

1. 没人要求的主动工作，**必须有团队提前写好的规则**才能做；
2. 默认先跑**观察模式**：只记录自己打算做什么，不真的动手。等你确认它的判断靠谱了，再放开。

## 10. 全双工：边干活边聊天

传统 Agent 一干活就忽略新消息，根因是 **React Loop 是半双工的** —— 像对讲机，同一时间只能一方说话。

Super Agent 要做的，是把对讲机换成电话（**全双工**）：

- 把耗时的工具调用改成**异步**：命令一启动就立刻返回；
- Agent 继续跟你聊天，命令跑完的结果**作为一条新消息**送回来。

> 这个机制在很多 AI 工具里其实已经实现了。

能边干活边聊天之后，还要管住"在不同渠道怎么说话"：

| 渠道 | 规矩 |
| --- | --- |
| 飞书 | 只在需要你拍板时才发消息；单次回复**不超过 100 词** |
| GitHub / 邮件 | 写清楚：问题背景、改动、验证结果 |

冗长的推理过程都关在 worker 里，只有 router（经理）对外说话 —— 否则群消息要炸。

## 11. 在线：存算分离与 BYOM

本地 Agent 把三样东西绑在同一台电脑上：**计算**、**状态**（会话记录）、**执行环境**（代码、工具）。电脑一休眠，三样全停。

借鉴**存算分离**，分两步拆开：

**第一步：计算 ↔ 状态**

- 计算放在云端**可随时替换的容器**里；
- 会话状态存进**数据库**；
- 容器挂了换一个就行，记录一条都不丢。
- 类比：靠谱的团队把工作记录放进档案室，谁来接班都能接着干。

**第二步：计算 ↔ 执行环境**

Agent 上了云，可代码、密钥、内网服务都还在你电脑上，搬不动。DeepSeek 的办法是 —— **环境搬不动，那就别搬**：

| 层 | 放在哪里 | 负责什么 | 关键特点 |
| --- | --- | --- | --- |
| **大脑** | 云端容器 | router + worker | 随时可替换，挂了换一个 |
| **状态** | 数据库 | 会话记录、编号卡片 | 记录一条都不丢 |
| **执行** | 你电脑上的 Daemon | 按指令执行命令、回传结果 | 很轻，**不保存会话记录** |

```
云端 ──指令──▶ 本机 Daemon ──结果──▶ 云端（写回数据库）
```

这套叫 **BYOM（Bring Your Own Machine，带上你自己的电脑）**。哪怕笔记本今天没开机，等它重新上线，云端也会自动把该在这台电脑上做的事做完。

## 12. 兜底：Watchdog

主系统外面单独配一个 **Watchdog（看门狗）会话**，相当于值班主管，定时巡查。

- 它不只看员工在不在岗，更看**任务有没有进展**；
- 因为 Agent 出问题，很多时候程序没挂，而是**模型在原地打转或跑偏**；
- 一旦发现异常，及时介入修复。

> 这一条很关键：健康检查要检查"有没有往前走"，而不是"进程还在不在"。

## 13. 效果与代价

DeepSeek 自己做的对比试验结果：

| 指标 | 结果 |
| --- | --- |
| 速度 | 比传统单对话 Agent **快一倍**（约 2×） |
| 稳定性 | 更稳定 |
| 缓存 token 消耗 | 单会话方案的 **2 倍到将近 4 倍**（因为要同时维护多个会话） |

一句话：**用 token 换并发和稳定性**。原文没有给出试验的样本量、任务集和统计口径，这组数字属于**官方自述**，不宜当成独立复现的结论。

## 14. 四个开放问题

DeepSeek 自己坦诚抛出的问题：

1. **规模**：任务继续变大，一个项目经理还够用吗？连续跑上几个月，长期记忆怎么办？
2. **界面**：不再盯着会话之后，人该用什么方式跟 Agent 协作？聊天窗口还是最好的界面吗？
3. **隐私**：每个人的私人助理和团队共用的 Super Agent 之间，怎么在不泄露隐私的前提下互相配合？
4. **安全**：Agent 越主动，接触的不可信信息越多，万一被**提示词注入**攻破了怎么办？

> 原文作者的观点：**安全是 Agent 工作最大的一道坎。**
> 就问你敢不敢让 AI 7×24 盯着群聊、操作你的电脑？万一来了条恶意消息把 AI 忽悠了，数据和隐私怎么办？

尽管如此，这个项目的价值在于：**把一套成熟的团队管理方法搬进了 AI 的世界**。
