# Super Agent：把「一个会话干一件事」变成「一个团队持续干活」

> 素材来源：一篇介绍 DeepSeek Harness 团队 Super Agent 架构的科普解读。以下内容只做整理与结构化，未补充原文之外的数据。

## 结论

主流 Agent（Claude Code、CodeX、DeepSeek Harness 等）都以 **session（会话）** 为单位工作：想一步、做一步、看结果、再想下一步，这个循环叫 **ReAct Loop**。单任务很好用，但多任务时就露馅——会话之间互不知情，跨任务的信息只能靠人脑记住再手动搬运。

DeepSeek 的判断是：**单任务的上限取决于模型能力，多任务的上限取决于人的注意力**（原文提到，一个人通常只能同时跟进三到五个活跃会话）。因此要把 Agent 与单次会话解绑，做成能跨会话记住上下文、同时推进多件事且互不干扰的连续工作者——这就是 **Super Agent**。

一句话类比：传统 Agent 是「一次只能干一件事的外包」，Super Agent 是「一个配合默契的项目团队，你只需要和一个对接人打交道」。

## 一、为什么单会话 Agent 不够用

场景很真实：一个会话修 bug、一个会话写文档、一个会话跑测试，群里同事一句「这个需求改一下」又要新开一个会话。结果人成了一群 AI 之间的传话筒。

给 Agent 接飞书、靠 CLI 和 MCP 让它自己去群里接任务，看似可行，但只要底层仍是单会话，就会撞上三个问题：

| 问题 | 表现 |
| --- | --- |
| 阻塞 | 执行耗时命令时整个循环卡住，命令跑完才能处理新消息 |
| 上下文污染 | 多个需求塞进同一会话，上下文越来越乱 |
| 生命周期绑定本机 | Agent 跑在本地电脑上，电脑一休眠就罢工 |

## 二、Super Agent 的四个基础特征

1. **连续**：在飞书群还是 GitHub 跟它聊都行。群里说用方案 A，后来在 PR 里改成方案 B，它跟得上。
2. **高效**：同时推进好几件事，上一件没干完也能接下一条指令。
3. **主动**：自己盯着群消息和工单，该处理的处理，不该管的保持安静。
4. **持久**：一直在线，出了问题能自己恢复。

### 一个内部实例

有用户在群里提需求：希望正文、代码、终端的字体能分开配置。维护者 @ 了一下 Super Agent，它很快到 GitHub 提交了改进代码，并根据用户在群里的追问和维护者在 GitHub 上的建议，一路把需求推进到代码合并。

更强的一种情况：它可以自己从产品用户群里识别出 bug，在后台自主复现、定位根因，直接把修复代码和前后对比截图发出来——不用人催。

## 三、架构：router 层 + worker 层

设计问题很直白：手里同时有二十件事，全交给一个人则只能排队；每件事都找个新人则并行但信息不同步、汇报混乱。DeepSeek 的选择是「我全都要」——照搬现实团队的做法：招一个项目经理，再配几个工程师。

| 层 | 角色 | 职责 | 模型选择 |
| --- | --- | --- | --- |
| **Router 层** | 项目经理 | 常驻在线，所有渠道消息先到它这里；记住全局、与你沟通、给 worker 派活；不亲自干活 | 轻量模型即可 |
| **Worker 层** | 工程师 | 独立上下文，专心干一件事，干完汇报 | 最强模型（真正决定交付质量） |

要点：

- 你面对的始终是同一个对接人，团队内部分工不用你操心。
- **批处理**：router 处理上一批消息时，新消息先攒着，忙完一起看、一起派活。原文称消息越多，平均处理反而越快。
- **worker 之间一般不直接沟通**。两个 worker 改同一个 PR 时会同时收到该 PR 的新动态，自己协调。
- 任务太复杂时，worker 还能再拉几个 **sub agent** 帮忙——相当于工程师自己带实习生。

## 四、事件驱动：trigger 与两级过滤

传统 Agent 是「你说一句它干一次活」；Super Agent 由环境里发生的事驱动：群里来了新消息、PR 下有人评论、代码构建失败……这些事件统称 **trigger**。

难点在于群里废话太多，若每条消息都让大模型判断一遍，又慢又烧钱。原文的做法是 **两级过滤**：

- **门卫（fast path）**：只看消息来源——是否监听的群、发消息的人是否在白名单。普通代码即可秒判。
- **秘书（slow path）**：通过门卫的消息才交给大模型，按提示词里写好的规则判断要不要处理。

这正是计算机系统里 **快慢路径（fast path / slow path）** 的思想。

### thread 订阅：绕过项目经理

同一个 PR、同一个群话题、同一串邮件里的连续消息构成一个 **thread**，可以理解为一个工单。

- 工单第一次进来时由 router 分给某个 worker；
- worker 接手后**订阅**该 thread，后续新消息由程序直接送到它手上，不再经过 router，节省大量 token。

现实类比：经理把工单第一次分给小王，之后的邮件直接抄送小王。

## 五、上下文管理：inline、spill 与链式召回

给多了重点被淹没，给少了干活的人反复回头问。原文的原则是：**浪费上下文窗口就是浪费模型的智能**。

借用编译器里的两个概念：

- **inline（内联）**：像同事转消息时顺手附上前后几句聊天和相关工单号，一眼看懂来龙去脉。
- **spill（溢出）**：几万字的文档只给摘要加一句「完整内容见这里」，需要时再去翻。

放到系统层面就是 **链式召回（chain of recall）**：给每条消息、每个工单、每个 worker 都编号，卡片上只写摘要和关联编号。你跨平台提起一件旧事，router 不必背下全部历史，顺着编号一路往下翻即可——像侦探找线索。

## 六、主动与克制：投机执行 + 观察模式

**投机执行**借自 CPU：不确定某段计算会不会用上时先提前算好，用上了就赚，用不上就扔。用在 Agent 上：收到一封会议邀请，先在后台核对日程、查背景资料、备好回复草稿，你确认一下就能发。

但主动不等于乱来。在 DeepSeek 开源的原型里：

- 没人要求的主动工作，必须有团队**提前写好的规则**才允许做；
- 默认先跑 **观察模式**：只记录自己打算做什么，不真的动手；确认判断靠谱后再放开。

## 七、全双工：边干活边聊天

传统 Agent 一干活就忽略新消息，因为 ReAct Loop 是**半双工**的——像对讲机，同一时间只能一方说话。Super Agent 要换成电话，也就是**全双工**。

具体做法：把耗时的工具调用改成**异步**，命令一启动立刻返回，Agent 继续跟你聊天，命令跑完的结果作为一条新消息送回来。原文提到这个机制在很多 AI 工具中已经实现。

### 分渠道的表达规范

冗长的推理过程都关在 worker 里，只有 router 对外说话，且不同渠道有不同规矩：

- **飞书**：只在需要你拍板时才发消息，单次回复不超过一百个词。
- **GitHub / 邮件**：写清楚问题背景、改动和验证结果。

## 八、持久化：存算分离与 BYOM

本地 Agent 把三样东西绑在同一台电脑上：干活的计算、会话记录等状态、代码与工具等执行环境。电脑一休眠，三样全停。DeepSeek 借鉴**存算分离**，分两步拆开：

1. **计算与状态分离**：计算放在云端可随时替换的容器里，会话状态存进数据库。容器挂了换一个，记录一条不丢——像靠谱团队把工作记录放进档案室，谁来接班都能接着干。
2. **计算与执行环境分离**：代码、密钥、内网服务很难整体搬到云上。那就别搬——大脑留在云端，本机只装一个很轻的小程序 **Daemon**，它不保存会话记录，只按云端指令执行命令并回传结果。

这套思路叫 **BYOM（Bring Your Own Machine）**：带上你自己的电脑。笔记本今天没开机，等它重新上线，云端也会自动把该在这台电脑上做的事做完。

## 九、Watchdog：值班主管

主系统之外单独配了一个 **Watchdog（看门狗）会话**，定时巡查。它不只看员工在不在岗，更看**任务有没有进展**——因为 Agent 出问题，很多时候程序并没挂，而是模型在原地打转或跑偏。发现异常就及时介入修复。

## 十、收益与代价

据原文的对比试验：

- Super Agent 比传统单对话 Agent **速度快了一倍**，且工作更稳定；
- 代价是同时维护多个会话，**读缓存的 token 是单会话方案的两倍到将近四倍**。

## 十一、原文留下的开放问题

1. 任务规模继续变大，一个项目经理还够用吗？连续跑上几个月，长期记忆怎么办？
2. 不再盯着会话之后，人该用什么方式跟 Agent 协作？聊天窗口还是最好的界面吗？
3. 每个人的私人助理和团队共用的 Super Agent 之间，如何在不泄露隐私的前提下互相配合？
4. Agent 越主动，接触的不可信信息越多，被**提示词注入**攻破怎么办？

## 十二、值得记住的几句

- 单任务上限看模型能力，多任务上限看人的注意力。
- 浪费上下文窗口就是浪费模型的智能。
- 把对讲机换成电话：从半双工走向全双工。
- 环境搬不动就别搬，大脑在云端，手脚在本地。

原文作者的态度是：安全是 Agent 落地最大的一道坎——敢不敢让 AI 全天盯着群聊、操作你的电脑？但他仍看好这个方向，因为它把一套成熟的团队管理方法搬进了 AI 的世界。原型已在 GitHub 开源（具体仓库地址原文未说明）。
