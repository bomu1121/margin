# Super-agent 技术调研：值得抄的是进展判定和事件分诊

> 2026-11-17 · 源视频 12:19，2026-11-05 · 官方文章 2026-10-31 · 原型 `deepseek-ai/dsh-superagent-prototype`（MIT，约 2.35 万星，最后提交 2026-11-03）

## 结论

- 它是一层**常驻调度**：把「人同时管 3–5 个会话」换成「系统管 N 个工单」，模型不换。
- 对我有用的只有两件：**进展判定**（看产出不看进程）和**事件分诊**（先规则后模型）。
- 两层架构和云端拆分不搬：单机单用户没有并发可调，多一层只多一次模型往返和一个状态机。

## 1. 它要解的问题

现在主流的 agent（Claude Code、Codex、DeepSeek Harness）以会话为单位：开一个会话布置一件事，在里面想一步做一步，这个循环叫 react loop。单任务没问题，多任务就出事——修 bug 一个会话、写文档一个会话、跑测试一个会话，同事再丢来一个需求，又得新开一个。会话之间互不知情，跨任务的信息全靠人记着再搬。

DeepSeek 的判断是：**单任务上限看模型能力，多任务上限看人的注意力**，一个人通常只能同时跟进 3–5 个活跃会话。给 agent 接飞书、靠 MCP 进群接活都不能根治，只要底层还是单会话，就会撞上三件事：跑耗时命令时循环卡死；几个需求塞进一个会话，上下文越来越乱；agent 跑在本地，电脑一休眠就罢工。

## 2. 一条消息从进来到回你，经过谁

原型把系统拆成五段。下面每段都按「职责 / 怎么做 / 失效时怎样 / 出处」写，因为读代码时你只需要这四样。

### 2.1 事件怎么进来：门卫看来源，秘书看内容

**职责**：决定这条事件要不要有人管。事件在原型里统一叫 Trigger——群消息、PR 评论、CI 失败都算。

**怎么做**：两级过滤。门卫是普通代码，只看来源（是不是监听的群、发消息的人在不在白名单），秒判；过了门卫的才交给模型，由它按提示词里写好的规则读内容。这就是计算机里的 fast path / slow path。

**失效时**：门卫规则写太宽等于没有；写太窄，真需求会被静默吞掉。所以没匹配上的消息必须落盘待查，不能直接丢。

**出处**：`docs/002-authorization.md`（admission table 与 policy）、`src/sources/`。

### 2.2 谁决定、谁干活：项目经理不干活，工程师才配强模型

**职责**：把「理解需求、记住全局、对外沟通」和「实际动手」分开。

**怎么做**：上层 Router 常驻在线，所有渠道的消息先到它这里，由它派活，自己不执行——所以用轻量模型就够。下层 Worker 每个有独立上下文，带全部工具，干完向 Router 汇报，Router 统一回你。消息都过 Router 会不会堵？它处理一批时新消息先攒着，忙完一起看、一起派，所以消息越多，平均处理反而越快（批处理）。两个 Worker 改同一个 PR 会各自收到动态，自己协调；任务太复杂，Worker 还能再拉 sub agent。

**失效时**：Router 是所有渠道的单点，它的判断错了，整条链都跟着错；批处理的代价是延迟——触发率越高，单次请求越慢。

**出处**：`docs/007-architecture.md`（Main Session / Executor 的职责切分）、`src/core/engine.ts`。

### 2.3 同一件事后来的消息去找谁：工单抄送

**职责**：让后续消息不必再经过 Router。

**怎么做**：同一个 PR、同一个群话题、同一串邮件里的连续消息算一个 thread，也就是工单。Worker 接手后订阅这个工单，后续消息由程序直接送到它手上。这是省 token 最直接的一处。

**失效时**：Worker 死了，订阅要回收，否则消息投给一个不存在的会话；工单被改成另一个话题时，要能退订。

**出处**：`docs/001-domain.md`（Thread 与 Subscription）、`src/core/engine.ts`。

### 2.4 干活的人该看到多少上下文：卡片加编号

**职责**：既不把窗口塞满，也不让 Worker 反复回头问。

**怎么做**：借了编译器两个概念——inline 是转消息时顺手附上前因，spill 是只给摘要加一句「完整内容见这里」。落到系统里是 chain of recall：消息、工单、Worker 都编号，卡片上只写摘要和关联编号，要细节就顺着编号取。

**失效时**：编号体系一旦和存储不同步，卡片指向空记录；摘要生成有损，关键限定条件可能在摘要里丢掉。

**出处**：`docs/007-architecture.md`（Session 事件与 Input 的读写记账）、`src/app/outbox.ts`。

### 2.5 出事时谁发现：两种失联，两种处理

**职责**：区分「卡住」和「下线」。

**卡住**用 Watchdog：主系统之外的一个独立会话，定时巡查。它不看进程在不在，看任务有没有进展——因为 agent 出问题很多时候程序没挂，是模型在原地打转。

**下线**用存算分离加 BYOM：计算放云端可替换容器、状态进数据库，容器挂了换一个；环境搬不走，所以本机只留一个不存记录的 daemon，按云端指令执行、回传结果。笔记本关机，等它上线云端再补做。

**失效时**：Watchdog 的阈值定太紧会误杀长任务；daemon 和云端的指令通道断了，任务会卡在「已派发」状态。

**出处**：`docs/007-architecture.md`（Watchdog、Outbox、Execution）、`docs/006-deployment.md`。

## 3. 它放弃了什么

- **确定性**：流程写成图（fabro 那种 DOT）比让 Router 临场判断便宜得多，它选了后者，换的是「不需要提前画流程」。
- **简单**：OpenHands、SWE-agent 用单 agent 加强工具接口也能跑，不拆层。拆层解决的是并发和注意力，不是单任务能力。
- **token**：视频自己说读缓存 token 是单会话方案的 2–4 倍，这是买并发的价钱。
- **适用范围**：README 写明原型是「for one GitHub repository」，可选接飞书；不是通用多任务平台。
- **成熟度**：README 同时写明「not an official product」「文章里有些设计在原型里没有实现」。文章是设计探索，代码是单仓库的编码 agent，两者不是一回事。

## 4. 数字与口径

- p50 12.4 分钟、p95 15.7 分钟；对照「单会话 + Subagent」的 p95 是 29.5 分钟，约 1.88 倍，视频口播说的「快一倍」指这个。
- 测试条件：约 300 条消息、其中约 20 条工作请求，每套方案跑 5 次，合成负载与简化环境，评的是调度与协作，不是单任务完成质量。
- 批处理：触发率从每分钟 1 条升到 40 条时，平均批大小 1.0→2.8，单次请求 2.5→3.9 秒，分摊到单个决定是 6.4→1.6 秒。**延迟在涨，只是被摊薄了**——触发率再往上，Router 就是新瓶颈。
- 渠道规矩：飞书只在需要拍板时发消息，单次不超过 100 词。

## 5. 我要改的三处

### 5.1 停滞检测（做）

现状：任务有有序 step、每步 checkpoint、retry / cancel / interrupted，但全库没有 `stalled`、`last_progress`、`heartbeat`。也就是说它只会因为「报错」失败，不会因为「在转圈」失败，而后者才是 agent 最常见的死法。

改法：每个 step 落一个「最后一次有产出」的时间，产出定义成 checkpoint 前进、写出新文件、状态迁移中的任意一种；后台 tick 比对阈值，按 step 类型分档；命中就把任务转成已有的 interrupted，从上一个 checkpoint 续跑。不新增状态机，`stalled` 只是 interrupted 的一个来源。

验收：对一个执行中的 step 发 SIGSTOP，两倍阈值内任务变成 stalled；恢复后从原 checkpoint 继续，step 产出不丢；同一任务不因停滞触发重试风暴。

### 5.2 事件分诊（先做最小一版）

现状：触发全部来自本地 UI 和文件监听，没有 inbound 端口。所以不需要 Router，但需要「先判再建任务」这一步：现在点一下就可能建任务、扣预算、调模型。

改法：在建任务的入口加一层纯代码判断——重复 BV、超出每日上限、来源不在白名单，直接挡掉并给一行原因。模型调用应当为 0。

验收：构造一条重复事件和一条超预算事件，两者都不产生模型请求；日志里能看到被挡的原因。

### 5.3 上下文卡片（和 5.1 一起做）

现状：笔记和事实都有 id，但拼 prompt 时塞的是正文。

改法：喂给模型的是「摘要 + 关联 id」，需要细节再按 id 取；超过阈值的正文走 spill，只留引用。判据是单 step 输入 token 不超上限，且 prompt 里出现的是 id 而不是全文。

## 6. 明确不做

- **Router / Worker 两层**：单机单用户，没有并行工单可分流；多一层只多一次模型往返、一个状态机和一份没人看的状态。真要抄，只抄「派活用轻模型、干活用强模型」这一条。
- **存算分离与 BYOM daemon**：计算、状态、执行环境本来就绑在一台机器上，硬拆只会多一个 daemon 和一套状态同步。
- **按渠道分档的回复话术**：输出只落在本地 UI，没有第二个出口要收敛。

## 7. 我的未解问题

- 「有产出」怎么定义才不会把「模型在输出但没推进」算成进展？checkpoint 前进是硬信号，写文件是软信号，两者要不要给不同权重？
- 阈值按 step 类型分几档？能不能从已有任务的历史耗时里估，而不是拍一个全局值？
- 停滞之后该重试一次还是直接等人工？重试会不会把一次卡死放大成两次花费？

## 8. 术语 ↔ 代码里的名字

读原型代码会用到的对照，其余名词不进这张表。

- **Router** → Main Session 的角色，`src/core/engine.ts` 里对外的那组接口。
- **Worker** → Executor Session，一个工单一个执行会话。
- **Trigger** → 事件，`src/sources/` 的入口。
- **Thread** → 工单线程，后续消息的挂载点。
- **Subscription** → Worker 对 Thread 的订阅，决定消息直投。
- **Ticket / Assignment** → 派出去的工作项与它的授权范围。
- **Eval / Decision** → 对事件要不要接的判断与结论。
- **Outbox** → 消息出口，唯一写回执的地方。
- **Observation（observe）** → 默认 accept 模式，只记录「本来会接」。
- **Watchdog** → 外部独立会话，按进展判活。
