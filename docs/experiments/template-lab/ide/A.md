# 从 AI 插件到 AI 原生工作台：一个 IDE 使用者的观察

作者从“已经想不起来上次打开 IntelliJ IDEA 是什么时候”这件事出发，讨论 AI 时代开发工具的重心正在从代码编辑转向 agent 编排。他的结论是：装在宿主 IDE 里的 AI 插件只是一个过渡状态，真正的工作流重构要靠 AI native IDE；但 JetBrains 这类工具不会因此被淘汰，只是结束赢家通吃的局面。这是一段个人观察与判断，原文明确声明不含广告，也没有给出使用数据或具体工具清单。

## 一个被自己遗忘的工具，引出的是重心问题

论述的起点不是行业数据，而是作者对自身的观察：他已经忘了上次打开 IntelliJ IDE 是什么时候。随后他把问题抛给观众——不知道现在还有多少人在用这种传统 IDE 工具。这里需要留意他的限定：他强调这是“我观察下来，我周围的同事”已经不再通过插件方式使用 AI，而不是一个覆盖面更广的统计结论。原文没有说明这种转变发生在什么时间、涉及多少人。

## AI 插件的限制：能力有边界，且随时可能被宿主挤掉

作者并不否认插件路径的合理性：很多同学最开始接触 AI 开发，就是通过安装 AI coding 插件，让工具帮忙补全、修改文件；他也明确说“不排除现在还有一些同学依旧通过这种方式在使用 AI”。但他给出两条具体限制：

- **能力受制于宿主。** 插件的能力是有边界的，会受制于宿主 IDE 提供给它的能力。
- **存在结构性竞争。** 哪一天宿主 IDE 自己开发了 agent，就会与这些 AI 插件直接形成竞争关系。

这两条不是“插件不好用”，而是插件的位置决定了它的上限：它借宿主的接口做事，也随时可能被宿主替代。

## 传统 IDE 的设计落点，与今天的工作方式错位

第二条论证指向设计目标本身。传统 IDE 的核心仍是老模式，整个任务开发的核心关注点是代码编辑，以及开发完成后的调试、验证。

而按作者的判断，现在开发模式的核心已经变成 agent 的编排、任务管理、需求约束——这些属于“最根本的工作方式”层面的东西。当重心从“我怎样编辑这段代码”变成“我怎样组织 agent 完成任务”，传统 IDE 就显得跟不上时代。这里作者用的词是“跟不上”，不是“不能用”；他也没有否认代码编辑仍然存在，后文明确说 AI native IDE 仍然允许编辑代码。

## 为什么插件解决不了：能力边界之外还有结构问题

作者抛出一个反问：“这些东西不是开发一个插件就能解决的，能不能去重构呢？”这正是他理解中许多公司要做 AI native IDE（原生的 AI 开发环境）的原因——去重构整个 AI 开发的工作流。关键区别不在于是否保留代码编辑，而在于工作台的重心从代码编辑上抽离出来。

## JetBrains 不会被淘汰，但赢家通吃结束了

对“JetBrains 会不会被淘汰”这个问题，作者的答案是“应该不会”：JetBrains 仍然有它的工程化壁垒。他把变化定位在竞争格局，而不是存亡：它不会再像以前那样处于赢家通吃的状态。

支撑这个判断的另一半理由是进入门槛下降——现在只是从功能上开发一个 IDE，其实并没有太多门槛，完全可以基于开源的、MIT 协议的 VS Code 快速构建一个新的 IDE 出来。也就是说，壁垒从“能不能做出 IDE 的功能”转移到了别处；原文没有进一步说明具体是哪些工程化壁垒。

## 结论：插件是过渡，工作台才是战场

整段论述的落点是一句明确表态：插件只是一个过渡状态。作者没有给出时间表，也没有推荐具体产品，而是把问题交回给观众——大家现在都在用什么 AI 工作台。原文提到这期视频的文字版整理在 Bilibili 社区，链接在视频简介中；除此之外没有提供其他外部资料。
