# AI 插件只是过渡：作者判断开发重心已从代码编辑转向 agent 编排

## 一句话结论

作者认为，装在传统 IDE 里的 AI coding 插件只是一个过渡形态，真正变化的是开发工作台的重心从代码编辑转向 agent 编排与任务管理，所以出现了 AI 原生 IDE；但 JetBrains 这类工具靠工程化壁垒不会被淘汰，只是不再赢家通吃。

## 速览

- 作者已经想不起上次打开 IntelliJ 是什么时候，周围同事也不再通过 IDE 插件用 AI。
- 插件的能力边界由宿主 IDE 决定，宿主一旦自研 agent 就会和插件直接竞争。
- 传统 IDE 围绕代码编辑与调试验证设计，与以 agent 编排为核心的新工作流已经错位。
- 作者认为 AI 原生 IDE 的价值在于重构工作流，而不是给老工具加功能。
- 做 IDE 功能本身门槛不高，JetBrains 不会消失，但赢家通吃的格局结束了。

## 插件式 AI 的能力上限由宿主 IDE 决定

作者认为，AI coding 插件路线的根本问题不在功能多少，而在它寄生在别人的工具里：能做什么、能改多少文件，都受制于宿主 IDE 愿意开放的能力。这也是他判断这条路走不远的技术理由——插件的天花板是宿主画出来的。

素材给出的第二层依据是利益结构：哪一天宿主 IDE 自己做 agent，插件和宿主就变成直接竞争关系，插件方并没有防守位置。作者用"我周围的同事已经不通过这种方式使用 AI"作为观察依据。

需要限定的地方是，这个观察只是作者身边同事的使用情况，素材没有给出范围、人数或行业数据，因此它更接近一个个人观察，而不是可推广的统计结论。作者也承认"不排除现在还有一些同学依旧通过这种方式在使用 AI"。

## 传统 IDE 的重心与现在的开发方式已经错位

按作者的描述，传统 IDE 的核心关注点是代码编辑，以及开发完成后的调试和验证——整套交互是为"人写代码"设计的。而现在的开发模式，核心变成了 agent 的编排、任务管理、需求约束这些工作方式层面的东西。

由此得出的判断是：这种错位不是开发一个插件就能解决的，因为插件只能在原有重心上做加法，改不动工作台以什么为中心。作者因此认为，真正的解法是重构整个 AI 开发工作流。

这一节同样带有作者视角的限定：他没有说明"agent 编排、任务管理、需求约束"具体指哪些操作，也没有举出对照的产品实例，属于方向性判断而非可验证的对比。

## AI 原生 IDE 的关键是重构工作流，而不是增加功能

作者对 AI 原生 IDE 的定义很清楚：它仍然允许编辑代码，但整个工作台的重心已经从代码编辑上抽离出来。也就是说，"AI native"的标志是重心的迁移，不是有没有 AI 功能。

这也解释了为什么他认为很多公司要做自己的 AI native IDE——目的是重构 AI 开发的工作流，而不是在老 IDE 上叠一层助手。作者把这归为传统工具"跟不上时代"的应对方式，而不是单纯的商业选择。

素材没有给出任何具体的 AI 原生 IDE 名称或功能清单，因此这一节只能停在"重心迁移"这一层判断上，无法验证各家的实现差异。

## JetBrains 靠工程化壁垒不会被淘汰，但赢家通吃结束

作者明确回答了自己提出的问题：JetBrains 这类工具以后应该不会被淘汰，因为它仍然有工程化壁垒。这是全篇唯一一处给传统厂商的正面判断。

但他同时判断格局会变：现在单纯从功能上开发一个 IDE 并没有太多门槛，完全可以基于 MIT 协议的 VS Code 快速构建一个新的 IDE 出来。护城河从"有没有 IDE 功能"转移到工程化积累，于是从赢家通吃变成多方分食。

这里的限定是，"工程化壁垒"具体指什么，素材没有展开——是调试能力、重构、语言支持还是别的，作者并未说明；"门槛不高"也只是他的判断，没有给出例证或成本数据。

## 关键数字与专名

- **IntelliJ**（产品）：作者用它代指传统 IDE，并说自己已想不起上次打开它的时间。
- **JetBrains**（公司）：作者认为它有工程化壁垒、不会被淘汰，但难再赢家通吃。
- **VS Code**（产品）：作者提到它采用 MIT 协议，可据此快速构建新的 IDE。
- **AI coding 插件**（产品类别）：作者判断它只是过渡状态，能力受宿主 IDE 限制。
