# AI 编码插件只是过渡形态，工作台的重心正从代码编辑上抽走

作者认为，靠装一个 AI 编码插件来写代码的方式会退成过渡状态，接下来的 AI 工作台会被重构成以 agent 编排为中心的"AI native IDE"。最强理由有两条：插件的能力天花板由宿主 IDE 划定，而现在的开发重心已经从代码编辑换成了 agent 编排、任务管理和需求约束，这些不是加一个插件能补上的。最大的限定是他并不认为 JetBrains 这类传统工具会被淘汰，只是不会再维持过去那种赢家通吃的局面。

## AI 编码插件的能力边界由宿主 IDE 划定，写插件绕不过去

这个判断把插件从"竞争者"降格成了"租客"：插件能补全多少、能改多少文件，取决于宿主 IDE 愿意开放多少能力，天花板不在插件自己手里。作者还指出一个更被动的后果——宿主 IDE 一旦自己做了 agent，插件立刻变成它的直接竞争对手。

他的观察起点很日常：已经忘了上次打开 IntelliJ IDE 是什么时候。他承认很多人最早接触 AI 开发就是装 AI coding 插件，"能够帮你去做一些补全、修改很多文件"，但周围同事已经不这么用了，理由是"它的能力是有边界的，它会受制于宿主 IDE 给它提供的这个能力"，以及"哪一天宿主 IDE 一旦开发了自己的 agent，也会跟这些 AI 插件直接形成竞争关系"。不过他并没有把话说死，"不排除现在还有一些同学依旧通过这种方式在使用 AI"。

## 开发重心已从代码编辑转到 agent 编排，传统 IDE 的骨架接不住

传统 IDE 的组织方式是为"写代码—调试—验证"这条链路长的，功能再多也只是把这条链路做厚。作者认为现在的工作方式换了根：主要精力放在编排 agent、管理任务和约束需求上，编辑器从主场变成了其中一环，所以"这些东西不是开发一个插件就能解决的"。

他的对照很直接：传统 IDE"整个任务开发的核心关注点都是在于这个代码的编辑，还有开发完的调试、验证这些功能"，而现在的"核心在于这个 agent 的编排、任务管理、需求约束这些最根本的工作方式"。这是作者对工具演进的判断，不是对现有 IDE 功能清单的评价。

## AI native IDE 重构的是整个开发工作流，不只是编辑器

这一节回应"为什么不能改造老 IDE"：所谓原生 AI 开发环境，动的是工作流的骨架，不是往旧界面上贴一层 AI 按钮。作者的说法是重构"整个 AI 开发的工作流"——代码编辑被保留，但不再是工作台的重心。

他的原话是"它们仍然是允许编辑代码，但是整个工作台的重心已经从代码编辑上给抽离出来了"，并由此给出结论："插件只是一个过渡状态"。也正因为重心被抽走，他判断"很多公司都需要去开发自己的 AI native IDE"，而不是等着别人把插件做好。

## JetBrains 有工程化壁垒不会被淘汰，但赢家通吃的局面结束了

作者的判断是"工具不会消失，垄断会消失"：从功能上做出一个 IDE 已经没有太多门槛，工程化积累却仍然是门槛，两者叠加的结果是市场从一家通吃变成多家并存。这意味着新玩家能靠开源底座快速入场，老玩家也不会因为少做了几项功能就出局。

他先用一个反例压低了入场难度——"现在只是从功能上开发一个 IDE，其实并没有太多的门槛，完全可以基于这种开源的、MIT 协议的 VS Code 去快速地构建一个新的 IDE 出来"；再解释 JetBrains 为什么还在场上，"JetBrains 它其实还是有它的这个工程化的壁垒的，只是它应该不会像以前那种赢家通吃的状态"。注意这里是"应该不会"的口气，属于节目判断，不是定论。
