# 传统 IDE 的重心正让位给 agent 编排，AI 编码插件只是过渡状态

## 一句话结论

作者认为，开发的中心已经从"编辑代码"转向"编排 agent 与管理任务"，因此 AI 编码插件受宿主 IDE 能力边界所限只是过渡形态，厂商会重做 AI 原生 IDE，而 JetBrains 不会被淘汰、只是不再赢家通吃。

## 速览

- 作者已经想不起上次打开 IntelliJ 是什么时候，身边同事也不再靠插件用 AI。
- 插件的能力被宿主 IDE 框住，宿主自建 agent 后还会与插件直接竞争。
- 传统 IDE 仍以代码编辑、调试验证为核心，而新工作方式的核心是 agent 编排、任务管理与需求约束。
- 作者判断插件路线解决不了这个问题，重做 AI 原生 IDE 才是厂商的选择。
- 做 IDE 的功能门槛在下降，但 JetBrains 的工程化壁垒仍在，格局会从赢家通吃变成多方并存。

## 传统 IDE 的重心仍是代码编辑与调试，这套工作方式已经跟不上 agent 时代的开发节奏

作者的判断是传统 IDE 落后于当前的开发方式，依据是自己的使用习惯和同事的做法。他开场说"我已经忘了我上次打开 IntelliJ IDE 这个工具是什么时候了"，并坦诚"我不知道现在还有多少同学在使用这种传统的 IDE 工具"；同时他观察到周围的同事已经不通过装插件的方式使用 AI，尽管"不排除现在还有一些同学依旧通过这种方式在使用 AI"。

落差的根源在关注点。作者认为传统 IDE"整个任务开发的核心关注点都是在于这个代码的编辑，还有开发完的调试、验证这些功能"，而现在的开发模式"核心在于这个 agent 的编排、任务管理、需求约束这些最根本的工作方式"。也就是说，变化发生在工作流层面，而不是某个功能缺失。

## AI 编码插件受宿主 IDE 的能力边界限制，作者判断它只是过渡状态

作者对插件的核心判断是能力天花板不在自己手里："这些 AI 的插件，它的能力是有边界的，它会受制于宿主 IDE 给它提供的这个能力"。更麻烦的是竞争关系——"哪一天宿主 IDE 一旦开发了自己的 agent，也会跟这些 AI 插件直接形成竞争关系"。

因此他认为这条路向上重构走不通："这些东西不是开发一个插件就能解决的"，结论也很直接——"插件只是一个过渡状态"。需要留意语气：这是作者的个人看法，他在片头就声明"这期没有任何广告，完全就是我对以后 AI 工作台的一些看法"，属于观察与推演，不是行业定论。

## 厂商重做 AI 原生 IDE，实质是把工作台重心从代码编辑上抽离出来

作者的描述是，很多公司去开发所谓原生的 AI 开发环境，"去重构了整个 AI 开发的工作流"。关键不是丢掉编辑能力，而是重心的迁移："它们仍然是允许编辑代码，但是整个工作台的重心已经从代码编辑上给抽离出来了"。

这也解释了他为什么不看好"插件+老 IDE"的组合：既然差异出在工作流编排上，就只能靠重做一个工作台来承载。限定在于，作者只给了方向性描述，没有列举任何具体产品、公司或实现方式，评论区的提问也是开放式的——"大家现在都用了什么 AI 工作台呢？"

## JetBrains 这类工具不会被淘汰，但赢家通吃的格局会结束

面对"JetBrains 以后是不是就会被淘汰了"，作者的答案是"我认为应该不会"。理由是它仍有工程化积累："JetBrains 它其实还是有它的这个工程化的壁垒的"，只是"它应该不会像以前那种赢家通吃的状态"。

支撑"格局会分散"的另一半理由是入场门槛下降："现在只是从功能上开发一个 IDE，其实并没有太多的门槛"，并且"完全可以基于这种开源的、MIT 协议的 VS Code 去快速地构建一个新的 IDE 出来"。这里的限定也要保留：作者用的是"我认为""应该"，属于预判而非事实；对于壁垒具体是什么、能守多久，素材没有展开。
