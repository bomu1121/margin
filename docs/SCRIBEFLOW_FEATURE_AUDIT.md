# ScribeFlow 功能盘点与整合取向

> 状态：**只做调研，不写实现**。本文是“把 ScribeFlow 收进页边笔记”的决策底稿。
> 你要做的是从第 3 节选保留项；选完再定第 4 节的执行架构。
> 日期：2026-11-05。

## 1. 结论先行

1. **ScribeFlow 的 Web 平台不再作为产品入口。** 画布、工程文件夹、节点面板、Obsidian/坚果云设置都不进页边笔记。
2. **页边笔记内置固定模板，不做通用画布编辑器。** 模板是代码里的枚举/配置，用户只选模板和少量参数；不暴露节点连线。
3. **执行主体优先做页边笔记内的 Rust 任务引擎。** 不常驻第二个服务、不占端口、不加 Node 运行时；空闲开销接近 0。
4. **只有在你选了大量高级能力、Rust 首版工期不可接受时，才用“无界面 Node sidecar”过渡。** 它能把 ScribeFlow 引擎原样搬过来，但实测空闲 +85MB 私有内存、启动 670ms，安装包也会明显变大。
5. **无论选哪种，执行器都套一个稳定接口。** 今天本地 Rust，明天云端 worker，页边笔记的 UI 和 Artifact/笔记契约不变。

### 2.1 你实际怎么用 ScribeFlow

从 `apps/server/data/scribe-flow.sqlite` 聚合（只统计结构，不导出正文）：

| 指标 | 实测 |
| --- | --- |
| 工程数 | 43 |
| 运行数 | 157（success 84 / error 66 / interrupted 5 / cancelled 2） |
| 项目图里的节点 | `prompt` 58、`bili` 38、`refine` 35、`transcribe` 34、`obsidian` 20、`output` 12、`text` 5、`gameguide` 3、`mindmap` 3、`drill` 2、`flow.pick` 2、`file` 2、`chapter` 1、`merge` 1、`flow.if` 0 |
| 运行结果里的节点 | `prompt` 144、`refine` 104、`transcribe` 103、`obsidian` 80、`bili` 67、`output` 38、`text` 7、`gameguide` 6、`mindmap` 2、`merge` 2 |
| B 站登录 | `bili_cookies` 0 行；67 次 B 站运行仍成功，说明主路径是公开链接，不依赖扫码/收藏夹 |
| 媒体库 | `media_assets` 0、`run_media` 0；没有用“保留可播放视频” |
| 工程数据 | `scribe-flow.sqlite` 20MB；`apps/server/data` 2.8GB（历史产物为主） |

**解读**：你的真实主路径非常集中——B 站公开视频 / 文本 → 转写 → 校对 → AI 加工 → 入库。画布分支、条件分支、媒体库、收藏夹登录几乎没有进入运行记录。这决定了首版不需要把整个平台搬过来。

### 2.2 运行时开销

| 对象 | 实测 | 说明 |
| --- | --- | --- |
| ScribeFlow server 空闲 | 私有 **85.2MB** / 工作集 88.2MB | 临时数据目录、端口 8899、启动后空闲；`node --import tsx` |
| ScribeFlow server 启动到 `/api/health` | **670ms** | 同一台机，临时数据目录 |
| SF Web 构建产物 | 4.6MB | `apps/web/dist`，不含 Node 运行时 |
| SF 开发依赖 | 430MB | `node_modules`；生产可裁，但没有实测裁剪后的安装包 |
| 页边笔记当前空闲私有内存 | 约 260MB（历史实测） | 再加 85MB 约 +33%；这是分开测的，不是同进程叠加实测 |

> 结论：Node sidecar 不是“不能接受”，但它是**运行制作时才该出现**的进程，不能常驻。常驻会把页边笔记从“轻笔记应用”变成“两个运行时”。

## 4. 执行架构：三条路

### 方案 R：页边笔记原生 Rust 制作引擎（推荐）

```text
Vue 制作页
  → Tauri command: start_production(template, source, options)
  → Rust ProductionService
      ├─ Source: bili / file / text
      ├─ Steps: transcribe → refine → prompt → (merge/chapter/mindmap/drill)
      ├─ AI/ASR: reqwest，直接调 OpenAI 兼容接口
      ├─ Bilibili: reqwest + 公开 API + 音频流
      ├─ Publish: 复用现有 Artifact v2 / outbox / 索引
      └─ Events: Tauri event 推送进度
  → SQLite: production_jobs / production_steps
```

- **性能**：不新增进程/端口；空闲只多一个 tokio 任务和几张表。制作时内存主要取决于文稿和音频缓冲，按文件流式处理，不把整个视频读进内存。
- **安装包**：B 站公开链接 + 文本不需要 ffmpeg；如果做本地音视频，才需要 ffmpeg（单独组件或提示系统安装），安装包会明显变大。
- **工期**：核心路径（B 站公开链接 + 文本、转写、校对、1–2 个提示词风格、入库、任务历史/重试）按现有代码拆算约 **3.5–5k Rust LOC，2–3 周**——这是估算，不是实测。
- **风险**：B 站接口/音频流、ASR 兼容性、长任务取消；需要真机跑通，不能只写单测。
- **适合**：你选“核心 + 少量可选”时。

### 方案 N：无界面 Node sidecar（过渡）

```text
Vue 制作页
  → Tauri 启停 sidecar（仅制作时）
  → 本地 stdio/回环 HTTP
  → 复用 ScribeFlow engine.ts + 节点/提示词/ASR/B 站
  → 产物回页边笔记
```

- **性能**：实测空闲私有 **85.2MB**、启动 **670ms**；只在制作时启动可以把常驻开销降为 0，但任务期间仍有这个进程。
- **安装包**：Node 运行时 + 生产依赖，估算 +40–80MB（未构建实测）；与现在 5.49MiB 的安装包不是一个量级。
- **优点**：功能保真度最高，ScribeFlow 现有 525 条测试和 B 站/ASR/提示词逻辑可以直接复用；首版最快。
- **缺点**：两个运行时、进程生命周期、端口/权限、打包复杂度；长期仍是“把旧平台藏在后面”。
- **适合**：你保留大量高级能力（收藏夹、多选、溯源、练一练、攻略、思维导图），且不想等 Rust 重写。

### 方案 H：混合（不推荐首版）

- Rust 做 UI/任务/发布，Node 只做高级节点；或 Rust 做本地核心，云端做重任务。
- 优点：核心路径轻，高级能力不用重写。
- 缺点：两套执行器、两套错误语义、测试矩阵翻倍；最容易重新长出“割裂”。
- 只有在你选的功能里有一半是 Rust 短期做不完的高级节点时，才值得。

### 方案 C：云端执行器（二期）

- 页边笔记只负责模板、任务、结果；执行交给云端 worker，本地保留离线核心。
- 这是商业化的最终形态，但需要账号、配额、对象存储、任务队列、隐私合规；现在做会拖慢本地体验。
- 先把 `ProductionExecutor` 接口留出来，未来加 `RemoteExecutor` 即可。

## 5. 推荐的首版产品形态

**一句话：制作页是一个“模板 + 来源 + 进度 + 结果”的工作台，不是画布。**

```text
制作
├─ 新建制作
│   ├─ 来源：B站链接 / 粘贴文稿 /（可选）本地音视频
│   ├─ 模板：视频笔记 / 长文笔记 /（可选）思维导图 / 练一练 / 攻略
│   ├─ 选项：提示词风格、标题、标签、抽取字段
│   └─ 开始
├─ 任务列表（进行中 / 已完成 / 失败）
│   └─ 任务详情：步骤时间线、日志、结果预览、重试、取消
└─ 入库位置：页边笔记（固定）
```

首版建议只做三个模板：

1. **视频笔记**：B 站/本地音视频 → 转写 → 校对 → 加工 → 入库。
2. **文稿笔记**：粘贴文本 → 校对 → 加工 → 入库。
3. **长文分章**（可选）：长文稿 → 校对 → 切章 → 合并 → 入库。

这样覆盖你实际运行节点结果的 **505 / 553 = 91.3%**（prompt 144 + refine 104 + transcribe 103 + obsidian 80 + bili 67 + text 7；不含 output/gameguide/mindmap/merge）。
项目图里覆盖 **190 / 216 = 88.0%**。思维导图/练一练/攻略作为二期模板，不把节点系统带进来。
