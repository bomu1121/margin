## 1. 优先级规则（后续每条需求先归类）

| 级别 | 含义 | 处理方式 |
| --- | --- | --- |
| **P0** | 数据安全、错误成功、丢笔记、密钥/账号、发布错视频 | 立即停下当前事，单独修，必须补测试 |
| **P1** | 用户能看到的错误、状态不一致、关键流程走不通 | 当批优先；一改一验 |
| **P2** | 体验打磨、文案、间距、空态、小交互 | 成批处理，不单独开大重构 |
| **P3** | 新能力/架构（分篇、冲突、云端、加密） | 先定方案，再排期；不夹在 P2 里做 |

**一条需求的验收必须写清：**
1. 入口在哪里；
2. 操作前/后的可见状态；
3. 数据落在哪个文件/表；
4. 用什么命令或截图验证；
5. 失败时用户看到什么，不能假成功。

## 7. 后续每批改动的执行模板

```text
需求编号：P1-xx
用户入口：制作 / 新建 / 来源 / B站链接
改前：
改后：
数据：SQLite production_jobs / outbox / 笔记 front matter
验收命令：npm run build / cargo test --lib / 打包窗口截图
失败态：用户看到什么；不能假成功
遗留：
```

**约束：**
- 一次只改一个变量；UI、引擎、文档分开提交。
- 不因为“顺手”加新模板、新字段、新重构。
- 涉及 schema/API/发布路径的改动，先停下来写方案，不直接做。
- 每条 P0/P1 改完更新 `docs/PRODUCTION.md` 的状态或本文对应行。
- 最终包只在代码稳定后重打，避免每改一个文案就重装一次。
