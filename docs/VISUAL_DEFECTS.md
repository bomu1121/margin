# 从 ZCode 会话里蒸馏视觉工作流：能抄什么、抄不到什么

> 依据：`sess_320b28bf-…` 的 90 条消息 / 337 个 part（工具调用、推理文本、产物）
> 结论：**流程可以抄，判断力抄不到。** 能蒸馏出来的是「缺陷分类 + 检查规则 + 循环骨架」；抄不出来的是「什么算不好看」。

---

## 1. 为什么「都暴露了」还是抄不到

会话记录里有三样东西，但没有第四样：

| 有 | 内容 |
| --- | --- |
| 动作 | 43 次 Read（全是图片）、23 次 Edit、23 次 Bash、5 次 Write、1 次子 agent |
| 观察 | 截图切片、PDF 逐页图、指标 JSON |
| 部分推理 | "Issues: 1… 2…" 这种问题清单，以及它决定下一批改什么 |

**没有的是产生这些动作的策略**：

- 系统提示词、工具 schema、子 agent（visual-judge）的提示词都没有完整留在记录里；
- 模型的视觉特征（它凭什么觉得「印章压住日期」）在权重里，不在文本里；
- 26.6 分钟的循环是**一条轨迹**，不是可执行策略。同一个模型重跑一次，问题清单和改法都会不同；
- 上下文管理（压缩、截断、子 agent 隔离）是 harness 的隐藏能力，恰好是长循环能跑 26 分钟的原因。

所以「把步骤抄下来」得到的是剧本，不是演员。

---

## 2. 能力分三层，只有一层能直接抄

| 层 | 内容 | 能否从记录里复制 | 我们的现状 |
| --- | --- | --- | --- |
| 工具层 | 读写文件、改 HTML/CSS、跑脚本、看图、派子 agent | **能**（动作可见） | 部分：渲染、测量、改图 spec、改章节；缺 shell 与任意代码编辑 |
| 策略层 | 先骨架后填充、批量列问题、一次只改一处、渲染后复测、预算内停止 | **能抄骨架，抄不到阈值** | 循环已实现（渲染→问题→一个动作→再渲染，≤4 轮） |
| 感知判断层 | 看图判断「空、压、挤、失衡、字号旧式」 | **不能** | 用几何启发式替代；没有视觉模型 |

关键：**流程形状是同一个**（act → observe → judge → patch），差别只在 **observe 的传感器**。ZCode 的传感器是像素，我们的是数字。抄了形状、换了传感器，行为就必然不同。

## 4. 蒸馏的正确产物

不是「把 ZCode 的步骤写进我们的管道」，而是三样东西：

1. **缺陷分类表**（上表）——这是从轨迹里能稳定提取的部分；
2. **每类缺陷对应的检查形式**——几何、样式、分页、还是必须看图；
3. **循环骨架 + 预算**——渲染、列问题、一次改一处、复测、最多 N 轮；预算到了就把未修项交人工。

这三样与模型无关，可复现、可回归。剩下的「判断力」只能靠：

- 接一个视觉模型（把截图交出去，让它输出同样的缺陷清单）；
- 或者接受「规则能覆盖的部分」，其余交人工验收。

---

## 5. 我们的结构性取舍（也是抄不像的原因）

- 笔记是 **Markdown + figure spec**，不是自由 HTML/CSS。好处是可搜索、可标注、可版本化；代价是 agent 改不了样式，只能改 spec。
- 生成器是**命令式模板**，不是通用 agent 运行时。好处是成本可控、可断点续跑；代价是没有「现写一个 QA 脚本」这种自由度。
- 应用内没有 shell / 任意文件写入。这是安全边界，不是疏忽。

要更接近 ZCode，需要放开的是「代码编辑 + 视觉 + 子 agent」，不是再写一个提示词。
