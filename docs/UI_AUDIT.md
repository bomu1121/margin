## 2. 跨页面的结构问题

### 2.1 事实库：范围/状态/搜索三层没有分开

- 范围（全部/历史/其他）和状态（全部/未核验/有证据/有争议/未找到/已拆分）是两个维度，却都用同一种 chip，且都有“全部”。
- 整改：范围用 segmented control，状态用 chips；加「范围」「状态」两个小标签；搜索独立一行或固定在工具栏右侧。
- 目标：1040 不出现孤立按钮；用户一眼知道“先选范围，再筛状态”。

### 2.2 整理工作台：任务感不对

- 页面把 59 条正常事实都算成“未整理”，用户会以为有 59 个待办；真正要处理的是 2 条复合、4 条无来源、0 重复、0 冲突。
- 整改：统计卡只放“可行动项”；“未标记”降级为一行可选进度，不参与任务压力。
- 空 section 折叠：`重复 0 · 冲突 0 · 暂无需要处理` 一行即可；有内容才展开完整卡。

### 2.3 事实详情：阅读顺序和空态

- 现在的顺序是：引用笔记 → 史料 → 候选（折叠）→ 网络证据 → 相关与冲突 → 核验历史。
- 方向对，但空 section 太重，候选太轻；页面应该“有数据的展开，没数据的收成一行”。
- 加 sticky 锚点：引用笔记 / 史料 / 候选 / 网络证据 / 核验；长页面不再迷路。
- 冲突面板按 evidence 类型分支，禁止空数字表。

### 2.4 史料库：自动溯源 vs 手工录入

- 史料库的定位是“自动溯源产出的证据库”，不是“资料柜”。保留手工入口会破坏这个定位，也直接违背用户之前的产品判断。
- 整改：删除「补录离线史料」；只保留“待补录”队列。若以后确实要离线补录，放到设置里的高级功能，不要在史料库主界面出现。

### 2.5 待补录队列：从“列表”变成“工作队列”

- 现在像把所有候选倒在一张长纸上；用户没有“处理完一组”的节奏。
- 整改：按事实组折叠；组头显示候选数 + provider 分布；展开后只显示紧凑候选行；补录后该行消失、组计数减一。
- 可加 provider/authority 过滤，但不要先做批量补录；单条质量优先。

### 2.6 拆分/阅读：保持“阅读层父事实优先”

- 笔记右栏保留父事实原句，子事实只在详情/事实库展开；这是正确的，不要为了“原子化”把阅读拆碎。
- 需要补的是“父事实上有 4 条子事实”的可见性，以及子事实详情的父链接。
- 拆分弹窗结构保留；只补“主语”和“候选来源”提示。

## 5. 诚实边界

- 走查基于当前真实数据：59 条事实（43 历史 + 16 通用）、1 条史料、360 条候选；没有用 0 数据/1000 条数据压测。
- 只截了 1440×900 和 1040×760；没有测 900 宽、125%/150% 缩放、暗色模式、超长中文标题、真实触屏。
- “哪个更好看”是设计判断，不是用户测试；没有招募真实用户做任务完成率/眼动测试。
- 截图里的小布什事实拆分/撤销是真实操作后恢复的；当前库已回到 59 事实 / 63 mentions / 0 reviews / 0 active splits。
- 队列和史料库的整改是布局方案，尚未实现；实现后需要重新截图验收。
